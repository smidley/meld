Plans 1–7 are merged; `uv run pytest -q` → **628 passed**, no warnings. The next plan starts from `main`; there is no open feature branch.

**The claim lock is a label.** Since plan 6b a party holds an issue with a `meld:claimed-by:<group>` label (`board.claim_label`; a human's is `meld:claimed-by:human`), so an App group claims and builds exactly like a PAT group — nothing depends any more on a bot user being an issue assignee, which GitHub never allows for an App (probe, 2026-09-09, read-only, `gh api -i repos/smidley/meld/assignees/<login>`: `smidley` → 204; `github-actions[bot]`, `dependabot[bot]`, `copilot-swe-agent[bot]` → 404 each). Meld neither reads nor writes issue assignees now: humans may assign issues to people as a courtesy, and `meld tick`'s off-protocol sweep still reports assignee changes made by strangers.

**An issue now declares what a worker may do.** Since plan 7 the issue *body* carries the declarations Python enforces (`board.body_section`; workers hold no credentials and cannot edit an issue, so a declaration is always the orchestrator's or a human's word): `## Scope` globs bound what a PR may change and `## May delete` lists the only paths it may delete, both written by `meld tag N --scope GLOB --may-delete PATH`. `rules._merge` refuses a PR that leaves the scope or deletes an unlisted file (`Board.scope_violations`/`blocked_deletions`; a memory PR closes no issue, so neither reaches it), and `meld status` shows both per PR long before anyone tries. Seven `meld:held:<category>` labels (`board.HELD_CATEGORIES`, created by `meld setup`) withhold authority up front: `rules._dispatch` refuses a held issue until a listed human's `RESOLVED #N`/`PROVIDED #N` is newer than the newest `NEEDS-HUMAN #N`, and the worker brief's `## Authorized by a human` section is the only place a worker learns it has that authority. And memory is superseded, never edited — `meld decide --supersedes` writes a two-file PR, `meld remember --supersedes` a first-line reference, and briefs quote only what is still in force.

## What Meld is

Meld lets N independent AI coding systems ("groups", each with a long-lived orchestrator, a long-lived PM, and short-lived headless workers in git worktrees) build one GitHub-hosted product together. Each group authenticates to GitHub as its own bot identity — either a machine-user account with a personal token (`auth = "pat"`, the default), or a GitHub App installation (`auth = "app"`, bot login `<slug>[bot]`) that needs no extra GitHub account or mailbox. GitHub is the only shared state: issues are the work queue, a `meld:claimed-by:<group>` label is the claim lock, an issue body's `## Scope`/`## May delete` sections and `meld:held:<category>` labels are the declarations that bound what its worker may do, a per-milestone coordination issue is the conversation, and every comment there starts with a `[<party>] <VERB> [<ref>]` header. "LLM decides, Python enforces": the `meld` CLI computes the legal actions for the calling party and refuses anything else, posting `PROTOCOL-VIOLATION` where every group and the human can see it — including a merge that would leave a task's declared scope and a dispatch that would hand a worker held authority no human granted. Agreed decisions and lessons persist as versioned files that auto-approved memory PRs carry into the repo (`meld decide`/`meld remember`/`meld recall`), superseded rather than edited when they go stale, a product's own skills reach every worker through the CLI's project skill directory, a human runs the plan gate and talks to every group from one console (`meld plan`, `meld inbox`, `meld chat`), and each PM's `meld tick` handles red CI, off-protocol GitHub changes, stray comments, and Slack nudges without being asked. `meld setup` bootstraps a fresh product repo and `meld doctor` says why it is not working.

## The SDD process used for this plan (repeat this)

1. **Spec first.** Behaviour changes start in the spec; the spec wins over any plan. Plan 5's checklist *was* spec section 21's "Carried into plan 5" list, and the last task of every plan is this one: put a marker on every item, make the body sections describe what now exists, and write down what the plan chose not to do as "Carried into plan 6".
2. **Plan, then execute task by task.** Each task got its own brief, its own failing tests first, a focused-then-whole-suite run, a plain conventional commit, and an independent review whose every finding produced a recorded ruling. The ledger for this plan is `.superpowers/sdd/2026-09-05-plan-5-setup-doctor-skills-sweep/`: a brief and a report per task, a `review-<sha>..<sha>.diff` per reviewed task, `progress.md`, `pr-5a-body.md` and `pr-5b-body.md`. Plan 6a's equivalent is `.superpowers/sdd/2026-09-05-plan-6a-github-app-identity/`, including its whole-branch `final-review.md` and `final-fix-report.md`. Plan 6b's is `.superpowers/sdd/2026-09-10-plan-6b-label-claim-lock/`, and plan 7's is `.superpowers/sdd/2026-09-10-plan-7-guardrails/` (a brief, a report and a `review-<sha>..<sha>.diff` per task, two `task-N-fix-round-1.md` files where a review's findings needed a second pass, `progress.md`, and `pr-7-body.md`).
3. **Hermeticity is a hard rule.** No network, no real CLI, no dependence on the host's `~/.claude`, gitconfig, or wall clock; inject `now`; every `load_context` in tests passes `adapter_for=`. Anything that would reach out — a Slack webhook, an App token mint — takes an injected callable in tests.
4. **Security invariants.** Workers never hold GitHub credentials; only PM-side code pushes, merges, reviews, and commits with the group's token and bot identity (memory PRs included). Anything worker- or stranger-authored that reaches GitHub goes through `neutralise_closers` — and, since plan 5, a worker's own commit messages never reach the default branch either, because the squash message is the PR body. `[joint]`, `LEASE`, `EXPIRED`, `RELEASED`, `IGNORED-COMMENT` are framework-posted only; challenge verbs go only through `meld challenge`. An App's private key never appears in argv, logs, state, result dicts, error messages, worker environments, or the repo.
5. **Reconcile docs at the end of each plan** (the spec sections touched, the README, this file). Verify it with a grep on the *stem* of whatever the plan renamed, not on the exact words the old code used: plan 6b's check was `grep -rn -i "assignee\|assignable" README.md docs/HANDOFF.md docs/superpowers/specs/2026-09-03-meld-design.md src/meld/prompts`, which read clean while six sentences still said *assigned* or *assignment* — so it is `grep -rn -i "assign" ...` now, and the survivors to expect are the off-protocol rows, the history clauses ("was the issue assignee"), the negative statements ("assignees are not read"), and the unrelated sense of the word (a ref number or a review concern is *assigned*). Plan 7 added nothing to rename, so its check was the reverse — that no document still promised the guardrails as future work: `grep -rn "Landing in plan 7" docs/` must print nothing, and `grep -rn "append-only\|held\|## Scope" README.md docs/HANDOFF.md docs/superpowers/specs/2026-09-03-meld-design.md` must read as landed behaviour rather than as a plan. ## Decisions for the owner (plan 5; each is reversible)

Numbered as in the plan header. Each names what was not done and what it costs if the call was wrong.

1. **A verified `[joint]` sticks.** Once the proposer's own bot has closed a round, later `[joint]` comments on that ref are ignored and `meld post --joint` refuses. *Not taken:* keep "the latest `[joint]` wins", which let a hand-written one flip a closed ref back to unverified and freeze `decide`/`plan`. *Cost if wrong:* a round that genuinely needs a corrected joint comment must open a new ref.
2. **A release ends a lease by posting, not by a run-record field.** `meld release` posts a framework-only `RELEASED #<n>`; `derive_leases` drops the lease on it. *Not taken:* make the lease a property of the run record. *Cost if wrong:* one more coordination comment per release, and a lease that lives in the thread rather than in typed state.
3. **The squash commit message is the PR body.** *Not taken:* scrub closing keywords from every worker commit message instead. *Cost if wrong:* the merge commit no longer summarises the individual commits, so `git log` on the default branch is coarser.
4. **A detached worker is never waited on.** `DetachedPopen.__del__` is a no-op; `state.pid_alive`'s `waitpid` reaps. *Not taken:* keep a reference and wait, which is wrong for a child that outlives the `meld` process. *Cost if wrong:* a zombie survives until some `pid_alive` call reaps it.
5. **The author group's request-changes counts toward the ping-pong cap**, carried by a `meld-verdict:` marker line on its COMMENT review. *Not taken:* leave it uncounted, as GitHub does. *Cost if wrong:* a PR reaches `blocked` a round earlier than a reader of GitHub's own review list would expect.
6. **`legal` reports the path `meld review` takes.** `legal_pr_verbs` goes through `review_verdict_rule`; `pr_refusal` stays strict for the memory-PR path. *Not taken:* leave `legal` conservative and let callers discover the truth from a refusal. *Cost if wrong:* `legal` promises an `approve` that a later GitHub-side change could still refuse.
7. **Among several open PRs for one issue, the current claim holder's PR wins**, then the highest number. *Not taken:* keep "highest number wins". *Cost if wrong:* a deliberately-opened alternative PR from another group is not the one the board points at.
8. **A complete milestone makes the audit batch due**, even below `batch_merges` and `batch_hours`. *Not taken:* leave the last few merges of a milestone unaudited until a timer fires. *Cost if wrong:* one small audit batch per milestone that a longer wait might have merged into a bigger one.
9. **One shared nudge throttle, held by the `meld:nudged` label** and read from GitHub's own label events; the per-party `notify.json` is gone. A label event counts as a nudge when its actor is a configured bot *or a listed human* — a human's own `meld notify` labels under their login, so the window has to see it (and a human hand-adding the label snoozes one window, deliberately). Parties are staggered one minute apart by sort order. *Not taken:* keep the per-party file, where N groups meant up to N copies of every nudge. *Cost if wrong:* a group that has gone quiet can no longer independently re-nudge, and two residuals stay open (an item that clears and returns inside the window is not re-nudged; a very slow label event can still produce a duplicate) — both recorded in spec section 21.
10. **A `BUDGET` comment may carry a `budget-<n>` ref**, and then only a human comment on that ref clears it; a ref-less `BUDGET` keeps the old behaviour. *Not taken:* require a ref. *Cost if wrong:* two behaviours to remember, and an old ref-less `BUDGET` still clears on any human comment.
11. **The recall scan's cost is closed by measurement, not an index.** `meld doctor` warns past 2 MB of decisions plus lessons. *Not taken:* build an index or cache now. *Cost if wrong:* brief-rendering latency grows with the memory store until someone reads the warning.
12. **`get_contents` falls back to the blob endpoint** above 1 MB. *Not taken:* switch every read to the `raw` media type. *Cost if wrong:* one extra API call per oversized file.
13. **`remember` escapes lines starting with `#`.** *Not taken:* reject such a lesson, or take the entry boundary from the marker instead of the last heading. *Cost if wrong:* a lesson's Markdown renders with visible `\#`.
14. **Skills: `.meld/skills/<name>/SKILL.md`, matched per brief, materialised into the worktree.** *Not taken:* sync the product's skills into the host's own skill directory (`~/.claude/skills`), or list the whole roster in every brief. *Cost if wrong:* a CLI that only reads skills from the home directory sees none of the product's, and a task whose wording shares no term with a relevant skill's description does not get it offered (the orchestrator's `--skill` pin is the escape hatch).
15. **`meld doctor` is read-only except `--sweep`**, and the commit-status write probe is opt-in behind `--probe-status`. *Not taken:* probe writes by default. *Cost if wrong:* a missing **Commit statuses: write** permission is not caught until the first real `meld review`.
16. **`meld setup` is idempotent and writes repo files on a local branch**; `--pr` pushes with the human's own git credentials, and a public repo is refused without `--allow-public`. *Not taken:* have setup push as a group's bot, or create the files directly on the default branch. *Cost if wrong:* bootstrapping needs the human's git credentials at hand.
17. **Section 21 item 22 (housekeeping posts wait for the alphabetically first group) stays documented, not changed.** *Not taken:* let every PM post, or elect a live poster. *Cost if wrong:* while that one group is down, stray comments and off-protocol changes are recorded silently by the others but flagged to nobody, and an event on an issue that closes meanwhile is never revisited.

## Decisions for the owner (plan 6a; each is reversible)

- **One App per group, not one shared App.** An App has exactly one identity (`<slug>[bot]`); a shared App could not tell the groups' actions apart, breaking every rule that assumes one login per group (`party_of_login`, `approving_parties`, author/committer checks). Alternative not taken: install a single App once and have every group act through it.
- **Signing the App JWT via the `openssl` CLI, not a Python crypto library.** RS256 is exactly `openssl dgst -sha256 -sign`; the key passes through a 0600 temp file (never argv), removed in a `finally`. Alternative not taken: add `PyJWT`/`cryptography` as a runtime dependency — ruled out by the plan's global constraint of stdlib plus `click` only.
- **Minting the installation token over HTTPS with `urllib.request`, not `gh api`.** `gh` injects its own `Authorization` header from `GH_TOKEN`, and the mint call must send the JWT as `Bearer`; every other call still goes through `gh api` with the installation token in `GH_TOKEN`. Alternative not taken: shell out to `gh api` for the mint too and fight its header injection.
- **The installation token is cached on disk, 0600, per group, and reused while more than 5 minutes remain.** PM loops call `meld` dozens of times a minute; minting a fresh token every process would burn the App's rate-limit budget for no benefit — `$MELD_HOME` is already disposable, secrets-adjacent scratch. Alternative not taken: mint a new token on every `meld` invocation.
- **Config shape:** `auth = "app"`, `app_id`, `installation_id`, and *exactly one* of `private_key_env` (PEM text, literal `\n` allowed) or `private_key_file`; `token_env` is ignored for App groups. `bot` must still end in `[bot]`. Alternative not taken: let both key-source settings coexist (or allow neither), or fold the key into the existing PAT `token_env` slot instead of adding dedicated fields.
- **A 401 forces one token refresh and retry**, rather than trusting the cache's own expiry math alone. Alternative not taken: refresh proactively before every single call regardless of remaining lifetime (correct but wasteful of the App's rate budget), or never react to a 401 and let clock skew or an out-of-band revoke fail the call outright.
- **`meld doctor` replaces the PAT identity/permission probes with App-specific ones** (`app:<g>`: the JWT signs and `GET /app`'s slug matches `bot`; `app-installation:<g>`: the installation token mints, its `permissions` map grants contents/issues/pull_requests/statuses = write, its repositories cover the product repo — evidence the fix wave made real by scoping the mint to that repo, so an absent list warns instead of passing). Alternative not taken: run the old PAT probes unmodified against an installation token — they assume a `GET /user` viewer login, which an App token does not have.
- **App groups get a real neutral check run in addition to the `meld/review/<group>` commit status** — the quorum keeps reading only the status (unchanged for PAT groups), and the check run is purely a visible, non-blocking echo on the PR's Checks tab. Alternative not taken: drop the commit status now that a real check run is possible, or make the check run a required/blocking check — either would break the PAT-group quorum path or contradict "neutral."
- **App creation stays a manual browser flow; `meld setup --app` only prints the steps and writes the config shape.** Alternative not taken: automate App creation through GitHub's manifest flow now — still deferred (spec section 21, "Carried into plan 6", item 1; plan 6b did not take it up).
- **`GitHub.token` becomes a property instead of every call site taking a token parameter.** The existing `push_branch(wt, branch, ctx.gh.token)` call sites in `dispatch`, `review`, and `memory` keep working unchanged and still get a fresh installation token on every access. Alternative not taken: thread a `token_provider` argument through every one of those call sites individually — a much larger, more error-prone diff for the same result.

## Decisions for the owner (plan 6b; each is reversible)

Numbered as in the plan header (`docs/superpowers/plans/2026-09-10-plan-6b-label-claim-lock.md`). Each names what was not done and what it costs if the call was wrong.

1. **A label, for every group.** `meld:claimed-by:<group>` replaces the assignee for PAT and App groups alike: one mechanism, and labels already arrive with the issue payload the board fetches, so the lock costs no extra API call to read. *Not taken:* keep the assignee for PAT groups and give App groups a second, different mechanism. *Cost if wrong:* the claim is now just one of the issue's labels, so anyone who can label an issue can claim or unclaim it by hand — the off-protocol sweep reports it, nothing prevents it.
2. **The race rule is the assignee lock's, unchanged in spirit.** `actions.claim` adds its own label, re-reads the issue with the ETag cache bypassed, and loses if the claim-label set is anything but exactly its own: it removes its own label and refuses, with no `PROTOCOL-VIOLATION`, because losing is the designed outcome rather than an illegal call. *Not taken:* a deterministic tie-break (say, the alphabetically first claimant keeps the issue) — GitHub offers no compare-and-swap on labels, and a tie-break needs both racers to see the same set at the same moment, which GitHub does not guarantee. *Cost if wrong:* two racers can both lose and both retry, so a contended issue can take an extra round to be claimed.
3. **A contested issue needs no repair verb.** Two claim labels are only reachable after a crash between add and re-read. Then `claimed_by` is `None`, `claimants` lists them, `claim` and `dispatch` refuse, either claimant (or a human) may release, and each claimant's lease stays valid (`held_leases` keeps a lease whose group is among the claimants), so the ordinary expiry path lets any PM release it — which removes every claim label. *Not taken:* a dedicated repair verb. *Cost if wrong:* a contested issue waits for a lease to expire, or for a human, instead of being fixed on the spot.
4. **A human claims with `meld:claimed-by:human`.** One label for every human (humans build things themselves), no group may dispatch a human-claimed issue, and `human` is therefore a reserved group name. *Not taken:* one claim label per human login. *Cost if wrong:* the board can say a person holds an issue but not which person.
5. **Assignees are neither read nor written any more.** Humans may assign issues to people as a courtesy and meld ignores it; `GitHub.add_assignees`/`remove_assignees` are gone as dead code, and `Issue.assignees` with them. The off-protocol sweep still flags assignee changes by strangers (`housekeeping._EVENTS` keeps `assigned`/`unassigned`), since they remain off-protocol actors. *Not taken:* keep writing the assignee alongside the label as a human-visible echo. *Cost if wrong:* GitHub's own "assigned to" UI no longer shows who is working on an issue; the label is the only signal.
6. **Claim labels are created lazily** by `claim` through `GitHub.ensure_label` (colour `c5def5`, description `Claimed by <group>`), because `meld setup` cannot know a product's group names and its static `LABELS` list stays as it is. *Not taken:* have `meld setup` create one claim label per configured group. *Cost if wrong:* one extra API call per claim, and a group's claim label first appears in the repo's label list only when that group claims something.
7. **Group names are validated** — `[a-z0-9][a-z0-9_-]{0,31}`, never `human` or `joint` — because a name becomes a label (GitHub's 50-character limit, prefix included) and a worktree path component. *Not taken:* sanitise the name into a label rather than refusing it. *Cost if wrong:* a config with a capitalised, over-long, or reserved group name now fails to load and has to be renamed.
8. **`Board` learns bot logins.** `Board.bots` (group → login, filled by `assemble` from the config) lets `holder_login` and so `pr_for_issue` still prefer the current holder's PR. *Not taken:* keep `Board` free of anything config-shaped and drop the holder preference from `pr_for_issue`. *Cost if wrong:* a small, explicit exception to "Board stays free of Config", limited to logins.
9. **`assignable:<g>` leaves `meld doctor`.** The lock no longer depends on assignability. A PAT group still needs push access for PR branches, but that is a different requirement and is not checked here. *Not taken:* keep the check, repurposed as a collaborator probe for PAT groups. *Cost if wrong:* nothing in doctor now speaks specifically to a PAT machine account's repository access; `token-permissions:<g>`'s read probes are the nearest signal.
10. **No migration tooling.** An issue claimed under the assignee lock reads as unclaimed after the upgrade; a product mid-milestone re-claims it once. No product is mid-flight today. *Not taken:* a one-shot converter that turns existing assignees into claim labels. *Cost if wrong:* an in-flight milestone has to be re-claimed, and a worker already running on such an issue collects as `superseded` (`dispatch._collect_build` sees no claim) with its branch left in the worktree for inspection.
11. **An orphan claim is recoverable through `meld`** (added by the whole-branch review, 2026-09-10). `actions.claim` adds its label before the `try`, so a PM killed between the add and the re-read used to leave `meld:ready` plus a claim label that refused everyone — `claim` said "already claimed", `release` said "issue is ready", `tick` skipped it, and no lease existed to expire. `rules._release` now also accepts a `ready` issue carrying a claim label, for a claimant or a human, and names that case in its refusal text; `rules._claim` compares against the caller's own name, so a group re-claims past its own stale label (the add is a no-op, the re-read shows exactly its own label, the swap proceeds) while another party's label still refuses and a contested `ready` issue refuses everyone. `actions.release` needed no change: it sheds every claim label, re-adds `meld:ready` as a no-op, and finds no `in-progress`/`blocked` label to remove. *Not taken:* a `meld repair` verb, or letting any PM release a stale claim it does not hold. *Cost if wrong:* a live claim released mid-flight by its own group is impossible in practice — only a claimant or a human — or, once the holder's lease has expired, any PM through the ordinary lease rule — may release it, and a claimant releasing its own in-flight claim is exactly what it could already do. *Residual:* a stale label whose holder never comes back, and an `in_progress` issue with no claimant, still need a human `meld release` (spec section 21 item 21).

## Decisions for the owner (plan 7; each is reversible)

Numbered as in the plan header (`docs/superpowers/plans/2026-09-10-plan-7-guardrails.md`) for 1–10; 11–14 are rulings made while executing it. Each names what was not done and what it costs if the call was wrong.

1. **Declarations live in the issue body and labels, not in a new file or a comment.** The body is orchestrator- and human-written and workers cannot touch it; labels arrive with the issue payload the board already fetches, so neither costs an extra API call. `## Scope` holds globs (`fnmatch`, `*` crosses `/`, exactly `PullRequest.touches`' semantics) and `## May delete` holds exact paths, both as `- ` bullets, with backticks around an item stripped. *Not taken:* a `.meld/scope.toml`-style tracked file, or a `SCOPE` coordination comment. *Cost if wrong:* a declaration changes with no reviewable diff — a body edit leaves only GitHub's own edit history, and anyone who can edit the issue can widen a scope; `tick`'s off-protocol sweep watches `labeled`/`unlabeled`/`assigned`/`unassigned` events, so it reports a held label added by a stranger but says nothing about a body edit.
2. **Scope is opt-in per issue; the deletion gate is always on.** No `## Scope` means no scope check, so a product adopts scopes gradually (the orchestrator prompt tells it to declare one for every issue it tags). A deleted file is refused unless listed under `## May delete`, whether or not a scope is declared — deletions are rare and consequential. Renames are not deletions (GitHub reports them as `renamed`). Memory PRs are exempt because they close no issue. *Not taken:* requiring a `## Scope` on every issue and refusing a merge without one. *Cost if wrong:* an issue nobody scoped is unbounded at merge, so the guardrail helps only where the orchestrator remembered to declare one.
3. **Enforcement is at merge; the warning is everywhere earlier.** `rules._merge` refuses; `meld status` shows `scope_violations` and `blocked_deletions` per PR; the build brief tells the worker its scope and deletion allowlist; the review brief tells the reviewer what merge will refuse. Humans widen a scope by editing the body (or by `meld tag`), never by a merge override. *Not taken:* refusing at `collect`, before the PR ever opens, or a `--force` override on `meld merge`. *Cost if wrong:* out-of-scope work is done, committed and pushed before anything refuses it, and the PR then sits unmergeable until a human widens the declaration or the changes are pared back.
4. **Held categories are a fixed vocabulary**: `cleanup`, `credential-change`, `delete`, `live-outreach`, `paid-media`, `production-mutation`, `public-release` (`board.HELD_CATEGORIES`); labels `meld:held:<category>`, created by `meld setup` as a static list, unlike the claim labels `claim` creates lazily. The offensive-security categories in the source note are out of Meld's domain. *Not taken:* product-defined categories in `.meld.toml`. *Cost if wrong:* a product whose consequential action falls outside the seven has no label for it and must fall back to the plain needs-human flow, which asks after the fact rather than withholding authority up front.
5. **Authorization reuses the needs-human flow.** `meld tag N --held CATEGORY` adds the held labels and `meld:needs-human` and posts `NEEDS-HUMAN #N`; the human answers `RESOLVED #N` (or `PROVIDED #N`) exactly as for any needs-human item; `_dispatch` refuses until `Board.needs_human_answered(N)` — a listed human's answer newer than the newest `NEEDS-HUMAN #N`, or any answer when no such comment exists. The held labels stay as the record, and the brief lists them as human-authorized. No new verb. *Not taken:* a `meld authorize` verb with its own grammar verb and its own audit trail. *Cost if wrong:* the answer is not scoped to a category, so a `RESOLVED #N` posted for an unrelated reason also lifts the held gate on that issue.
6. **`tick` closes the pre-existing needs-human gap, and a lease that lapsed before the answer is suspended rather than expired.** Nothing removed `meld:needs-human` after a human answered (the spec promised it; a hand edit did it). Any PM's `tick` now swaps `meld:needs-human` → `meld:in-progress` (claimed) or `meld:ready` (unclaimed) once `needs_human_answered`, posting nothing, because the human's answer is already the record; idempotent across PMs, and the issues it just resumed are held back from that same tick's Slack nudge, which is computed from the board as it stood before the swap. The whole-branch review found the other half: a build that stops on a needs-human posts no lease closer, so the resumed issue carries its dead worker's long-lapsed `until` and the next foreign PM's `tick` read that as an expiry — `EXPIRED`, claim label stripped, issue back to `ready` — for a group that was only ever waiting for a person. `tick` now skips a lease whose issue has a listed human's `PROVIDED`/`RESOLVED` created after the lease's `until`; the holder's next `meld dispatch` posts a fresh `LEASE` that governs from then on, and no `RESUMED` is posted (that verb is the liveness notice for a restarted orchestrator or PM). *Not taken:* leaving the label to a person, having `dispatch` simply ignore the label once an answer exists, or making the blocked-collect path post a `RELEASED` closer (which would drop the claim as well as the lease). *Cost if wrong:* an issue is un-gated by a label swap no comment announces, so the trace is GitHub's label history plus the human's own answer rather than a coordination comment; and a holder that never re-dispatches keeps the claim indefinitely, since the one lease that could have freed it is now suspended — only a human `meld release` clears it (spec section 21 item 21's seam, a lease-like age rule for claim labels, would close that too).
7. **Workers learn their limits in the brief and the contract.** `_worker_contract.md`'s item 4 names the held categories as forbidden unless the brief's `## Authorized by a human` section lists them; the build brief carries `## Scope` (the globs, the deletion allowlist, "merge will refuse anything else") and `## Authorized by a human` (the issue's held categories, present only because dispatch was legal — i.e. because a human answered). *Not taken:* enforcing the categories inside the worker, or withholding tools from it. *Cost if wrong:* the contract is a prompt, not a sandbox: a worker that ignores it is caught at merge for a deletion or an out-of-scope change, and not at all for an outbound action — which is exactly why the brief lists only what a human already authorized.
8. **Supersession is a two-file memory PR for decisions, a first-line reference for lessons.** `meld decide <ref> --supersedes NNNN-<slug>.md` renders the new file with a `- Supersedes:` line and appends `\n---\nStatus: superseded by MMMM-<slug>.md on YYYY-MM-DD\n` to the old one; `verify_memory_pr` accepts exactly that pair (new file byte-identical to the rendering, old file byte-identical to origin's content plus that one trailer). `meld remember ... --supersedes "<heading>"` puts `Supersedes: <heading>` on the entry's first body line; lessons stay append-only and their existing verification is unchanged. *Not taken:* editing a status field in place on the old file, or keeping a separate index of retirements. *Cost if wrong:* the two files must land together, so a supersession fails wholesale if either write fails; and `lessons.md` records the link only on the newer entry, so reading an old lesson on its own never shows that it was retired.
9. **Recall shows status; briefs drop superseded notes.** `memory.recall` hits carry `status` and `superseded_by`; `brief.recall_snippets` and `brief.decision_titles` skip superseded entries, so `## Relevant memory` and `## Decisions in force` quote only current memory. *Not taken:* dropping superseded hits from `recall` as well, or leaving them in briefs with a marker and trusting the worker to weigh them. *Cost if wrong:* a worker cannot tell a retired decision from one that never existed — only the orchestrator sees the supersession, so a wrong one is theirs to catch.
10. **The prompts carry the discipline, the code carries the marks.** `orchestrator.md`'s Memory section gained "Memory primes hypotheses; it does not prove current state — read the file, grep the symbol, run the command before acting on a recalled note", plus the `--supersedes` usage; its planning guidance gained "declare a `--scope` for every issue you tag; flag held categories with `--held`". *Not taken:* refusing a dispatch whose recalled memory is older than some age, or making `recall` demand a verification step before it answers. *Cost if wrong:* nothing enforces "verify before acting" — a model that skips the line acts on a stale note exactly as it did before, and only a reviewer catches it.
11. **`meld tag --held` posts the `NEEDS-HUMAN #N` ask before the labels, for every actor, and only for categories the issue does not carry yet.** A re-tag of an already-held category is a no-op (no duplicate ask, so an answered issue is not re-gated); the ask names the full held set. The whole-branch review reversed the first version of this ruling, under which a human's `--held` posted no ask: the ask is the gating stamp `Board.needs_human_answered` measures an answer against, so an unstamped hold was one nothing could lift on purpose and any earlier answer on that issue lifted by accident — and the remedy this decision named ("a human posts a new `NEEDS-HUMAN #N` by hand") was impossible, `grammar.HUMAN_VERBS` not having the verb. It has it now, `tag` posts `[human] NEEDS-HUMAN #N` for a human like any other actor, the comment goes out before any label write (a `GitHubError` on it therefore leaves no labels for the caller to retry past), and `needs_human_answered` requires an ask to exist at all. *Not taken:* always re-posting the ask; leaving a human's hold unstamped on the grounds that the human is the authority. *Cost if wrong:* a human who holds an issue is also the recipient of their own ask — it appears in `meld inbox` under the issue it holds, which is where that issue already was; and the coordination issue carries one more comment per hold.
12. **Declarations are rewritten in place and validated for shape only.** `board.replace_section` rewrites an existing `## Scope`/`## May delete` section where it stands (keeping the body's own heading spelling; blank lines after the section collapse to one), appends a missing one, removes one given an empty list; `meld tag` refuses blank paths but does not validate globs or check that paths exist; there is no CLI way to clear a scope (an omitted repeatable option means "not given") — edit the body to remove a section. *Not taken:* `--scope ''` as a clearing form; glob validation. *Cost if wrong:* a typo in a glob refuses every merge on that issue until the body is edited; scopes can only be replaced, not cleared, from the CLI.
13. **`Supersedes:` lines in worker-authored lesson text are escaped like headings.** Only `meld remember --supersedes` (the flag, run by the PM) can write the unescaped first line that `recall`/briefs read; a worker cannot make another group's lesson disappear from `## Relevant memory`. *Not taken:* trusting the text. *Cost if wrong:* none observed; a lesson that legitimately begins "Supersedes: …" as prose is shown with a leading backslash.
14. **A decision supersession is authorized by the `--supersedes` flag on `meld decide`, not by the agreed text.** Any group holding one verified `[joint] DECISION` can retire any decision file; the other PMs auto-approve from provenance plus hash; the record is the PR body's `supersedes:` line, the `- Supersedes:` header, and git history. The verifier pins everything else: flat paths under `.meld/decisions/`, a new path that does not already exist on the default branch (added by the fix wave — otherwise a valid rendering of decision B could be landed at decision A's path and destroy A), the old file byte-identical to origin plus exactly one trailer naming the new file and its date, no second supersession of an already-superseded file. *Not taken:* requiring the joint DECISION text to name the file it supersedes (a grammar change). *Cost if wrong:* a group can retire an unrelated decision without a human seeing it before merge — visible afterwards, reversible by a counter-supersession. Recorded as a residual in spec section 21, plan-6-carried item 28.

## Live-run hotfixes (2026-09-11, first run on `smidley/meld-playground`)

The first paid run (product `tally`; milestone 1 = engine, CLI, QA, docs; two groups, claude and codex, authenticating as GitHub Apps) exposed defects that were fixed the same day as single-purpose PRs to `main`, each with tests:

- **PR #12 — adapters.** The claude adapter pins its identity settings for the orchestrator and PM and blanks them for workers (`settings_for(role, env)`); codex `exec` drops `-a never` and takes a per-role sandbox; `meld doctor` checks `cli-flags:<group>` against each CLI's `--help` (`help_argv`/`required_flags`); `milestone_complete` needs at least one issue.
- **PR #13 — runner.** A quick zero exit is throttled but reported as `exit`, not a crash; the PM prompt waits `polling.wait_timeout_seconds`.
- **PR #14 — adapters.** `TRUSTED_ROLES` fails closed; `-p` is a verified required flag (spec sections 16 and 18).
- **PR #15 — codex workers** get `--add-dir` for the worktree gitdir, the common `.git`, and the uv cache, so a sandboxed worker can commit.
- **PR #16 — review feedback reaches the retry.** `Review.body`, `brief.review_feedback(pr)`, and `collect`'s `no_change` outcome, which keeps the issue in progress instead of looping.
- **PR #17 — audits** refuse PRs not authored by a group (`cfg.group_for_bot(author) is None`), and such PRs leave `audit_summary.pending`.
- **PR #18 — one review slot per group per head.** `rules._review` refuses a head the group's bot already reviewed, the author group's marked COMMENT verdicts included (two slots when the PR touches `review.security_paths`; a dismissed review frees the slot), and the ping-pong cap counts distinct (reviewer, head) pairs (spec section 13 steps 2 and 5, section 21 item 31, which also records the collect-to-review window this leaves open).

Residuals observed in the run and deliberately not fixed live (plan 8 candidates, roughly by cost of leaving them):

1. **Build/review mutual exclusion on an issue's branch.** A reviewer's push-fix and a retry build ran on one branch at once, and a PM merged a PR while a retry was still building on its branch (the retry's commit had to be recovered from a dangling object).
2. **An audit FAIL reopens the issue even when `main` already carries the fix.** The auditor judges the merge commit; the reopen should check later remediation, or the auditor should judge against current `main`. It happened twice (issues #6 and #7 were closed again by hand).
3. **Rate-limit and spend-limit handling.** The runner treats a 429 or "hit your … limit" result as an ordinary crash (silent backoff relaunches, no board signal); the adapter should recognise it and the runner should pause the role until the stated reset.
4. **Disk full.** A supervisor that cannot create a log file exits; it should back off and retry, and `meld doctor` should warn on low free space. Workers' multi-megabyte benchmark files in `/private/tmp` are what tipped the host.
5. **The retry tier is prompt-only.** A PM can dispatch a retry at the unchanged tag before the orchestrator retags; `_dispatch` could enforce the rubric, or `collect` could suggest the retag.
6. **PM over-eagerness.** PMs try verbs `meld status` already lists as illegal (cross-group collects, claims with another adapter's model, a second audit past the concurrency cap), each posting a `PROTOCOL-VIOLATION`; the prompt should say "act only on `legal`", or refusals of that class should stay local.
7. **Audits requested by a CHALLENGE or a DECISION are never `due`** (the batching heuristic is the only trigger).
8. **Silent omissions in `meld status`.** `audit`/`review` vanish from `legal` when no run slot is free without saying why, and nothing says "a review was requested from you and is unanswered on this head" once an older verdict goes stale.
9. **Agreement refs.** A `plan-add-*` ref closed with a `[joint] DECISION` cannot take `[joint] PLAN-ADD` afterwards (the ref is spent), and `meld post --joint DECISION` records the agreed text, not the comment body, so an addendum in the comment is lost.
10. **Human interventions and the PM loop.** A human push to a PR branch does not move the issue to in-review, and a human relabel is undone by the PM's next cycle.
11. **Plan items have no dependency ordering**; QA was parked behind the CLI by a `DIRECTIVE`.
12. **App setup** through GitHub's manifest flow (spec section 21 item 1) and a `doctor` login probe for each CLI.
13. **Console ergonomics.** `meld chat`'s `/resolved` needs an issue or PR ref (free-form refs go through `meld post RESOLVED <ref>`), and a coordination thread passes 100 comments in hours, so every ad-hoc reader needs pagination.
