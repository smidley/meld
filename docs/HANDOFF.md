**The claim lock is a label.** Since plan 6b a party holds an issue with a `meld:claimed-by:<group>` label (`board.claim_label`; a human's is `meld:claimed-by:human`), so an App group claims and builds exactly like a PAT group — nothing depends any more on a bot user being an issue assignee, which GitHub never allows for an App (probe, 2026-09-09, read-only, `gh api -i repos/smidley/meld/assignees/<login>`: `smidley` → 204; `github-actions[bot]`, `dependabot[bot]`, `copilot-swe-agent[bot]` → 404 each). Meld neither reads nor writes issue assignees now: humans may assign issues to people as a courtesy, and `meld tick`'s off-protocol sweep still reports assignee changes made by strangers.

**An issue now declares what a worker may do.** Since plan 7 the issue *body* carries the declarations Python enforces (`board.body_section`; workers hold no credentials and cannot edit an issue, so a declaration is always the orchestrator's or a human's word): `## Scope` globs bound what a PR may change and `## May delete` lists the only paths it may delete, both written by `meld tag N --scope GLOB --may-delete PATH`. `rules._merge` refuses a PR that leaves the scope or deletes an unlisted file (`Board.scope_violations`/`blocked_deletions`; a memory PR closes no issue, so neither reaches it), and `meld status` shows both per PR long before anyone tries. Seven `meld:held:<category>` labels (`board.HELD_CATEGORIES`, created by `meld setup`) withhold authority up front: `rules._dispatch` refuses a held issue until a listed human's `RESOLVED #N`/`PROVIDED #N` is newer than the newest `NEEDS-HUMAN #N`, and the worker brief's `## Authorized by a human` section is the only place a worker learns it has that authority. And memory is superseded, never edited — `meld decide --supersedes` writes a two-file PR, `meld remember --supersedes` a first-line reference, and briefs quote only what is still in force.

## What Meld is

Meld lets N independent AI coding systems ("groups", each with a long-lived orchestrator, a long-lived PM, and short-lived headless workers in git worktrees) build one GitHub-hosted product together. Each group authenticates to GitHub as its own bot identity — either a machine-user account with a personal token (`auth = "pat"`, the default), or a GitHub App installation (`auth = "app"`, bot login `<slug>[bot]`) that needs no extra GitHub account or mailbox. GitHub is the only shared state: issues are the work queue, a `meld:claimed-by:<group>` label is the claim lock, an issue body's `## Scope`/`## May delete` sections and `meld:held:<category>` labels are the declarations that bound what its worker may do, a per-milestone coordination issue is the conversation, and every comment there starts with a `[<party>] <VERB> [<ref>]` header. "LLM decides, Python enforces": the `meld` CLI computes the legal actions for the calling party and refuses anything else, posting `PROTOCOL-VIOLATION` where every group and the human can see it — including a merge that would leave a task's declared scope and a dispatch that would hand a worker held authority no human granted. Agreed decisions and lessons persist as versioned files that auto-approved memory PRs carry into the repo (`meld decide`/`meld remember`/`meld recall`), superseded rather than edited when they go stale, a product's own skills reach every worker through the CLI's project skill directory, a human runs the plan gate and talks to every group from one console (`meld plan`, `meld inbox`, `meld chat`), and each PM's `meld tick` handles red CI, off-protocol GitHub changes, stray comments, and Slack nudges without being asked. `meld setup` bootstraps a fresh product repo and `meld doctor` says why it is not working.

## The SDD process used for this plan (repeat this)

1. **Spec first.** Behaviour changes start in the spec; the spec wins over any plan. Plan 5's checklist *was* spec section 21's "Carried into plan 5" list, and the last task of every plan is this one: put a marker on every item, make the body sections describe what now exists, and write down what the plan chose not to do as "Carried into plan 6".
2. **Plan, then execute task by task.** Each task got its own brief, its own failing tests first, a focused-then-whole-suite run, a plain conventional commit, and an independent review whose every finding produced a recorded ruling. The ledger for this plan is `.superpowers/sdd/2026-09-05-plan-5-setup-doctor-skills-sweep/`: a brief and a report per task, a `review-<sha>..<sha>.diff` per reviewed task, `progress.md`, `pr-5a-body.md` and `pr-5b-body.md`. Plan 6a's equivalent is `.superpowers/sdd/2026-09-05-plan-6a-github-app-identity/`, including its whole-branch `final-review.md` and `final-fix-report.md`. Plan 6b's is `.superpowers/sdd/2026-09-10-plan-6b-label-claim-lock/`, and plan 7's is `.superpowers/sdd/2026-09-10-plan-7-guardrails/` (a brief, a report and a `review-<sha>..<sha>.diff` per task, two `task-N-fix-round-1.md` files where a review's findings needed a second pass, `progress.md`, and `pr-7-body.md`).
3. **Hermeticity is a hard rule.** No network, no real CLI, no dependence on the host's `~/.claude`, gitconfig, or wall clock; inject `now`; every `load_context` in tests passes `adapter_for=`. Anything that would reach out — a Slack webhook, an App token mint — takes an injected callable in tests.

An App's private key never appears in argv, logs, state, result dicts, error messages, worker environments, or the repo.
5. **Reconcile docs at the end of each plan** (the spec sections touched, the README, this file). Verify it with a grep on the *stem* of whatever the plan renamed, not on the exact words the old code used: plan 6b's check was `grep -rn -i "assignee\|assignable" README.md docs/HANDOFF.md docs/superpowers/specs/2026-09-03-meld-design.md src/meld/prompts`, which read clean while six sentences still said *assigned* or *assignment* — so it is `grep -rn -i "assign" ...` now, and the survivors to expect are the off-protocol rows, the history clauses ("was the issue assignee"), the negative statements ("assignees are not read"), and the unrelated sense of the word (a ref number or a review concern is *assigned*). ## Decisions for the owner (plan 5; each is reversible)

Numbered as in the plan header. Each names what was not done and what it costs if the call was wrong.

1. **A verified `[joint]` sticks.** Once the proposer's own bot has closed a round, later `[joint]` comments on that ref are ignored and `meld post --joint` refuses. *Not taken:* keep "the latest `[joint]` wins", which let a hand-written one flip a closed ref back to unverified and freeze `decide`/`plan`. *Cost if wrong:* a round that genuinely needs a corrected joint comment must open a new ref.
2. **A release ends a lease by posting, not by a run-record field.** `meld release` posts a framework-only `RELEASED #<n>`; `derive_leases` drops the lease on it. *Not taken:* make the lease a property of the run record. *Cost if wrong:* one more coordination comment per release, and a lease that lives in the thread rather than in typed state.
3. **The squash commit message is the PR body.** *Not taken:* scrub closing keywords from every worker commit message instead. *Cost if wrong:* the merge commit no longer summarises the individual commits, so `git log` on the default branch is coarser.
4. **A detached worker is never waited on.** `DetachedPopen.__del__` is a no-op; `state.pid_alive`'s `waitpid` reaps. *Not taken:* keep a reference and wait, which is wrong for a child that outlives the `meld` process. *Cost if wrong:* a zombie survives until some `pid_alive` call reaps it.
5. **The author group's request-changes counts toward the ping-pong cap**, carried by a `meld-verdict:` marker line on its COMMENT review. *Not taken:* leave it uncounted, as GitHub does. *Cost if wrong:* a PR reaches `blocked` a round earlier than a reader of GitHub's own review list would expect.
6. **`legal` reports the path `meld review` takes.** `legal_pr_verbs` goes through `review_verdict_rule`; `pr_refusal` stays strict for the memory-PR path. *Not taken:* leave `legal` conservative and let callers discover the truth from a refusal. *Cost if wrong:* `legal` promises an `approve` that a later GitHub-side change could still refuse.
7. **Among several open PRs for one issue, the current claim holder's PR wins**, then the highest number. *Not taken:* keep "highest number wins". *Cost if wrong:* a deliberately-opened alternative PR from another group is not the one the board points at.
8. **A complete milestone makes the audit batch due**, even below `batch_merges` and `batch_hours`. *Not taken:* leave the last few merges of a milestone unaudited until a timer fires. *Cost if wrong:* one small audit batch per milestone that a longer wait might have merged into a bigger one.
9. **One shared nudge throttle, held by the `meld:nudged` label** and read from GitHub's own label events; the per-party `notify.json` is gone. A label event counts as a nudge when its actor is a configured bot *or a listed human* — a human's own `meld notify` labels under their login, so the window has to see it (and a human hand-adding the label snoozes one window, deliberately). Parties are staggered one minute apart by sort order. *Not taken:* keep the per-party file, where N groups meant up to N copies of every nudge. *Cost if wrong:* a group that has gone quiet can no longer independently re-nudge, and two residuals stay open (an item that clears and returns inside the window is not re-nudged; a very slow label event can still produce a duplicate) — both recorded in spec section 21.
10. **A `BUDGET` comment may carry a `budget-<n>` ref**, and then only a human comment on that ref clears it; a ref-less `BUDGET` keeps the old behaviour. *Not taken:* require a ref. *Cost if wrong:* two behaviours to remember, and an old ref-less `BUDGET` still clears on any human comment.
11. **The recall scan's cost is closed by measurement, not an index.** `meld doctor` warns past 2 MB of decisions plus lessons. *Not taken:* build an index or cache now. *Cost if wrong:* brief-rendering latency grows with the memory store until someone reads the warning.
12. **`get_contents` falls back to the blob endpoint** above 1 MB. *Not taken:* switch every read to the `raw` media type. *Cost if wrong:* one extra API call per oversized file.
13. **`remember` escapes lines starting with `#`.** *Not taken:* reject such a lesson, or take the entry boundary from the marker instead of the last heading. *Cost if wrong:* a lesson's Markdown renders with visible `\#`.
14. **Skills: `.meld/skills/<name>/SKILL.md`, matched per brief, materialised into the worktree.** *Not taken:* sync the product's skills into the host's own skill directory (`~/.claude/skills`), or list the whole roster in every brief. *Cost if wrong:* a CLI that only reads skills from the home directory sees none of the product's, and a task whose wording shares no term with a relevant skill's description does not get it offered (the orchestrator's `--skill` pin is the escape hatch).
15. **`meld doctor` is read-only except `--sweep`**, and the commit-status write probe is opt-in behind `--probe-status`. *Not taken:* probe writes by default. *Cost if wrong:* a missing **Commit statuses: write** permission is not caught until the first real `meld review`.
16. **`meld setup` is idempotent and writes repo files on a local branch**; `--pr` pushes with the human's own git credentials, and a public repo is refused without `--allow-public`. *Not taken:* have setup push as a group's bot, or create the files directly on the default branch. *Cost if wrong:* bootstrapping needs the human's git credentials at hand.
17. **Section 21 item 22 (housekeeping posts wait for the alphabetically first group) stays documented, not changed.** *Not taken:* let every PM post, or elect a live poster. *Cost if wrong:* while that one group is down, stray comments and off-protocol changes are recorded silently by the others but flagged to nobody, and an event on an issue that closes meanwhile is never revisited.

## Decisions for the owner (plan 6a; each is reversible)

- **One App per group, not one shared App.** An App has exactly one identity (`<slug>[bot]`); a shared App could not tell the groups' actions apart, breaking every rule that assumes one login per group (`party_of_login`, `approving_parties`, author/committer checks). Alternative not taken: install a single App once and have every group act through it.
- **Signing the App JWT via the `openssl` CLI, not a Python crypto library.** RS256 is exactly `openssl dgst -sha256 -sign`; the key passes through a 0600 temp file (never argv), removed in a `finally`. Alternative not taken: add `PyJWT`/`cryptography` as a runtime dependency — ruled out by the plan's global constraint of stdlib plus `click` only.
- **Minting the installation token over HTTPS with `urllib.request`, not `gh api`.** `gh` injects its own `Authorization` header from `GH_TOKEN`, and the mint call must send the JWT as `Bearer`; every other call still goes through `gh api` with the installation token in `GH_TOKEN`. Alternative not taken: shell out to `gh api` for the mint too and fight its header injection.
- **The installation token is cached on disk, 0600, per group, and reused while more than 5 minutes remain.** PM loops call `meld` dozens of times a minute; minting a fresh token every process would burn the App's rate-limit budget for no benefit — `$MELD_HOME` is already disposable, secrets-adjacent scratch. Alternative not taken: mint a new token on every `meld` invocation.
- **Config shape:** `auth = "app"`, `app_id`, `installation_id`, and *exactly one* of `private_key_env` (PEM text, literal `\n` allowed) or `private_key_file`; `token_env` is ignored for App groups. `bot` must still end in `[bot]`. Alternative not taken: let both key-source settings coexist (or allow neither), or fold the key into the existing PAT `token_env` slot instead of adding dedicated fields.
- **A 401 forces one token refresh and retry**, rather than trusting the cache's own expiry math alone. Alternative not taken: refresh proactively before every single call regardless of remaining lifetime (correct but wasteful of the App's rate budget), or never react to a 401 and let clock skew or an out-of-band revoke fail the call outright.
- **`meld doctor` replaces the PAT identity/permission probes with App-specific ones** (`app:<g>`: the JWT signs and `GET /app`'s slug matches `bot`; `app-installation:<g>`: the installation token mints, its `permissions` map grants contents/issues/pull_requests/statuses = write, its repositories cover the product repo — evidence the fix wave made real by scoping the mint to that repo, so an absent list warns instead of passing). Alternative not taken: run the old PAT probes unmodified against an installation token — they assume a `GET /user` viewer login, which an App token does not have.
- **App groups get a real neutral check run in addition to the `meld/review/<group>` commit status** — the quorum keeps reading only the status (unchanged for PAT groups), and the check run is purely a visible, non-blocking echo on the PR's Checks tab. Alternative not taken: drop the commit status now that a real check run is possible, or make the check run a required/blocking check — either would break the PAT-group quorum path or contradict "neutral."
- **App creation stays a manual browser flow; `meld setup --app` only prints the steps and writes the config shape.** Alternative not taken: automate App creation through GitHub's manifest flow now — still deferred (spec section 21, "Carried into plan 6", item 1; plan 6b did not take it up).
- **`GitHub.token` becomes a property instead of every call site taking a token parameter.** The existing `push_branch(wt, branch, ctx.gh.token)` call sites in `dispatch`, `review`, and `memory` keep working unchanged and still get a fresh installation token on every access. Alternative not taken: thread a `token_provider` argument through every one of those call sites individually — a much larger, more error-prone diff for the same result.

## Decisions for the owner (plan 6b; each is reversible)

Numbered as in the plan header (`docs/superpowers/plans/2026-09-10-plan-6b-label-claim-lock.md`). Each names what was not done and what it costs if the call was wrong.

1. **A label, for every group.** `meld:claimed-by:<group>` replaces the assignee for PAT and App groups alike: one mechanism, and labels already arrive with the issue payload the board fetches, so the lock costs no extra API call to read. *Not taken:* keep the assignee for PAT groups and give App groups a second, different mechanism. *Cost if wrong:* the claim is now just one of the issue's labels, so anyone who can label an issue can claim or unclaim it by hand — the off-protocol sweep reports it, nothing prevents it.
2. **The race rule is the assignee lock's, unchanged in spirit.** `actions.claim` adds its own label, re-reads the issue with the ETag cache bypassed, and loses if the claim-label set is anything but exactly its own: it removes its own label and refuses, with no `PROTOCOL-VIOLATION`, because losing is the designed outcome rather than an illegal call. *Not taken:* a deterministic tie-break (say, the alphabetically first claimant keeps the issue) — GitHub offers no compare-and-swap on labels, and a tie-break needs both racers to see the same set at the same moment, which GitHub does not guarantee. *Cost if wrong:* two racers can both lose and both retry, so a contended issue can take an extra round to be claimed.
3. **A contested issue needs no repair verb.** Two claim labels are only reachable after a crash between add and re-read. Then `claimed_by` is `None`, `claimants` lists them, `claim` and `dispatch` refuse, either claimant (or a human) may release, and each claimant's lease stays valid (`held_leases` keeps a lease whose group is among the claimants), so the ordinary expiry path lets any PM release it — which removes every claim label. *Not taken:* a dedicated repair verb. *Cost if wrong:* a contested issue waits for a lease to expire, or for a human, instead of being fixed on the spot.
4. **A human claims with `meld:claimed-by:human`.** One label for every human (humans build things themselves), no group may dispatch a human-claimed issue, and `human` is therefore a reserved group name. *Not taken:* one claim label per human login. *Cost if wrong:* the board can say a person holds an issue but not which person.
5. **Assignees are neither read nor written any more.** Humans may assign issues to people as a courtesy and meld ignores it; `GitHub.add_assignees`/`remove_assignees` are gone as dead code, and `Issue.assignees` with them. The off-protocol sweep still flags assignee changes by strangers (`housekeeping._EVENTS` keeps `assigned`/`unassigned`), since they remain off-protocol actors. *Not taken:* keep writing the assignee alongside the label as a human-visible echo. *Cost if wrong:* GitHub's own "assigned to" UI no longer shows who is working on an issue; the label is the only signal.
6. **Claim labels are created lazily** by `claim` through `GitHub.ensure_label` (colour `c5def5`, description `Claimed by <group>`), because `meld setup` cannot know a product's group names and its static `LABELS` list stays as it is. *Not taken:* have `meld setup` create one claim label per configured group. *Cost if wrong:* one extra API call per claim, and a group's claim label first appears in the repo's label list only when that group claims something.
7. **Group names are validated** — `[a-z0-9][a-z0-9_-]{0,31}`, never `human` or `joint` — because a name becomes a label (GitHub's 50-character limit, prefix included) and a worktree path component. *Not taken:* sanitise the name into a label rather than refusing it. *Cost if wrong:* a config with a capitalised, over-long, or reserved group name now fails to load and has to be renamed.
8. **`Board` learns bot logins.** `Board.bots` (group → login, filled by `assemble` from the config) lets `holder_login` and so `pr_for_issue` still prefer the current holder's PR. *Not taken:* keep `Board` free of anything config-shaped and drop the holder preference from `pr_for_issue`. *Cost if wrong:* a small, explicit exception to "Board stays free of Config", limited to logins.
9. **`assignable:<g>` leaves `meld doctor`.** The lock no longer depends on assignability. A PAT group still needs push access for PR branches, but that is a different requirement and is not checked here. *Not taken:* keep the check, repurposed as a collaborator probe for PAT groups. *Cost if wrong:* nothing in doctor now speaks specifically to a PAT machine account's repository access; `token-permissions:<g>`'s read probes are the nearest signal.
10. **No migration tooling.** An issue claimed under the assignee lock reads as unclaimed after the upgrade; a product mid-milestone re-claims it once. No product is mid-flight today. *Not taken:* a one-shot converter that turns existing assignees into claim labels. *Cost if wrong:* an in-flight milestone has to be re-claimed, and a worker already running on such an issue collects as `superseded` (`dispatch._collect_build` sees no claim) with its branch left in the worktree for inspection.
11. **An orphan claim is recoverable through `meld`** (added by the whole-branch review, 2026-09-10). `actions.claim` adds its label before the `try`, so a PM killed between the add and the re-read used to leave `meld:ready` plus a claim label that refused everyone — `claim` said "already claimed", `release` said "issue is ready", `tick` skipped it, and no lease existed to expire. `rules._release` now also accepts a `ready` issue carrying a claim label, for a claimant or a human, and names that case in its refusal text; `rules._claim` compares against the caller's own name, so a group re-claims past its own stale label (the add is a no-op, the re-read shows exactly its own label, the swap proceeds) while another party's label still refuses and a contested `ready` issue refuses everyone. `actions.release` needed no change: it sheds every claim label, re-adds `meld:ready` as a no-op, and finds no `in-progress`/`blocked` label to remove. *Not taken:* a `meld repair` verb, or letting any PM release a stale claim it does not hold. *Cost if wrong:* a live claim released mid-flight by its own group is impossible in practice — only a claimant or a human — or, once the holder's lease has expired, any PM through the ordinary lease rule — may release it, and a claimant releasing its own in-flight claim is exactly what it could already do. *Residual:* a stale label whose holder never comes back, and an `in_progress` issue with no claimant, still need a human `meld release` (spec section 21 item 21).

## Decisions for the owner (plan 7; each is reversible)

Numbered as in the plan header (`docs/superpowers/plans/2026-09-10-plan-7-guardrails.md`) for 1–10; 11–14 are rulings made while executing it. Each names what was not done and what it costs if the call was wrong.

1. **Declarations live in the issue body and labels, not in a new file or a comment.** The body is orchestrator- and human-written and workers cannot touch it; labels arrive with the issue payload the board already fetches, so neither costs an extra API call. `## Scope` holds globs (`fnmatch`, `*` crosses `/`, exactly `PullRequest.touches`' semantics) and `## May delete` holds exact paths, both as `- ` bullets, with backticks around an item stripped. *Not taken:* a `.meld/scope.toml`-style tracked file, or a `SCOPE` coordination comment. *Cost if wrong:* a declaration changes with no reviewable diff — a body edit leaves only GitHub's own edit history, and anyone who can edit the issue can widen a scope; `tick`'s off-protocol sweep watches `labeled`/`unlabeled`/`assigned`/`unassigned` events, so it reports a held label added by a stranger but says nothing about a body edit.
2. **Scope is opt-in per issue; the deletion gate is always on.** No `## Scope` means no scope check, so a product adopts scopes gradually (the orchestrator prompt tells it to declare one for every issue it tags). A deleted file is refused unless listed under `## May delete`, whether or not a scope is declared — deletions are rare and consequential. Renames are not deletions (GitHub reports them as `renamed`). Memory PRs are exempt because they close no issue. *Not taken:* requiring a `## Scope` on every issue and refusing a merge without one. *Cost if wrong:* an issue nobody scoped is unbounded at merge, so the guardrail helps only where the orchestrator remembered to declare one.
3. **Enforcement is at merge; the warning is everywhere earlier.** `rules._merge` refuses; `meld status` shows `scope_violations` and `blocked_deletions` per PR; the build brief tells the worker its scope and deletion allowlist; the review brief tells the reviewer what merge will refuse. Humans widen a scope by editing the body (or by `meld tag`), never by a merge override. *Not taken:* refusing at `collect`, before the PR ever opens, or a `--force` override on `meld merge`. *Cost if wrong:* out-of-scope work is done, committed and pushed before anything refuses it, and the PR then sits unmergeable until a human widens the declaration or the changes are pared back.
4. **Held categories are a fixed vocabulary**: `cleanup`, `credential-change`, `delete`, `live-outreach`, `paid-media`, `production-mutation`, `public-release` (`board.HELD_CATEGORIES`); labels `meld:held:<category>`, created by `meld setup` as a static list, unlike the claim labels `claim` creates lazily. The offensive-security categories in the source note are out of Meld's domain. *Not taken:* product-defined categories in `.meld.toml`. *Cost if wrong:* a product whose consequential action falls outside the seven has no label for it and must fall back to the plain needs-human flow, which asks after the fact rather than withholding authority up front.
5. **Authorization reuses the needs-human flow.** `meld tag N --held CATEGORY` adds the held labels and `meld:needs-human` and posts `NEEDS-HUMAN #N`; the human answers `RESOLVED #N` (or `PROVIDED #N`) exactly as for any needs-human item; `_dispatch` refuses until `Board.needs_human_answered(N)` — a listed human's answer newer than the newest `NEEDS-HUMAN #N`, or any answer when no such comment exists. The held labels stay as the record, and the brief lists them as human-authorized. No new verb. *Not taken:* a `meld authorize` verb with its own grammar verb and its own audit trail. *Cost if wrong:* the answer is not scoped to a category, so a `RESOLVED #N` posted for an unrelated reason also lifts the held gate on that issue.
6. **`tick` closes the pre-existing needs-human gap, and a lease that lapsed before the answer is suspended rather than expired.** Nothing removed `meld:needs-human` after a human answered (the spec promised it; a hand edit did it). Any PM's `tick` now swaps `meld:needs-human` → `meld:in-progress` (claimed) or `meld:ready` (unclaimed) once `needs_human_answered`, posting nothing, because the human's answer is already the record; idempotent across PMs, and the issues it just resumed are held back from that same tick's Slack nudge, which is computed from the board as it stood before the swap. The whole-branch review found the other half: a build that stops on a needs-human posts no lease closer, so the resumed issue carries its dead worker's long-lapsed `until` and the next foreign PM's `tick` read that as an expiry — `EXPIRED`, claim label stripped, issue back to `ready` — for a group that was only ever waiting for a person. `tick` now skips a lease whose issue has a listed human's `PROVIDED`/`RESOLVED` created after the lease's `until`; the holder's next `meld dispatch` posts a fresh `LEASE` that governs from then on, and no `RESUMED` is posted (that verb is the liveness notice for a restarted orchestrator or PM). *Not taken:* leaving the label to a person, having `dispatch` simply ignore the label once an answer exists, or making the blocked-collect path post a `RELEASED` closer (which would drop the claim as well as the lease). *Cost if wrong:* an issue is un-gated by a label swap no comment announces, so the trace is GitHub's label history plus the human's own answer rather than a coordination comment; and a holder that never re-dispatches keeps the claim indefinitely, since the one lease that could have freed it is now suspended — only a human `meld release` clears it (spec section 21 item 21's seam, a lease-like age rule for claim labels, would close that too).
7. **Workers learn their limits in the brief and the contract.** `_worker_contract.md`'s item 4 names the held categories as forbidden unless the brief's `## Authorized by a human` section lists them; the build brief carries `## Scope` (the globs, the deletion allowlist, "merge will refuse anything else") and `## Authorized by a human` (the issue's held categories, present only because dispatch was legal — i.e. because a human answered). *Not taken:* enforcing the categories inside the worker, or withholding tools from it. *Cost if wrong:* the contract is a prompt, not a sandbox: a worker that ignores it is caught at merge for a deletion or an out-of-scope change, and not at all for an outbound action — which is exactly why the brief lists only what a human already authorized.
8. **Supersession is a two-file memory PR for decisions, a first-line reference for lessons.** `meld decide <ref> --supersedes NNNN-<slug>.md` renders the new file with a `- Supersedes:` line and appends `\n---\nStatus: superseded by MMMM-<slug>.md on YYYY-MM-DD\n` to the old one; `verify_memory_pr` accepts exactly that pair (new file byte-identical to the rendering, old file byte-identical to origin's content plus that one trailer). `meld remember ... --supersedes "<heading>"` puts `Supersedes: <heading>` on the entry's first body line; lessons stay append-only and their existing verification is unchanged. *Not taken:* editing a status field in place on the old file, or keeping a separate index of retirements. *Cost if wrong:* the two files must land together, so a supersession fails wholesale if either write fails; and `lessons.md` records the link only on the newer entry, so reading an old lesson on its own never shows that it was retired.
9. **Recall shows status; briefs drop superseded notes.** `memory.recall` hits carry `status` and `superseded_by`; `brief.recall_snippets` and `brief.decision_titles` skip superseded entries, so `## Relevant memory` and `## Decisions in force` quote only current memory. *Not taken:* dropping superseded hits from `recall` as well, or leaving them in briefs with a marker and trusting the worker to weigh them. *Cost if wrong:* a worker cannot tell a retired decision from one that never existed — only the orchestrator sees the supersession, so a wrong one is theirs to catch.
10. **The prompts carry the discipline, the code carries the marks.** `orchestrator.md`'s Memory section gained "Memory primes hypotheses; it does not prove current state — read the file, grep the symbol, run the command before acting on a recalled note", plus the `--supersedes` usage; its planning guidance gained "declare a `--scope` for every issue you tag; flag held categories with `--held`". *Not taken:* refusing a dispatch whose recalled memory is older than some age, or making `recall` demand a verification step before it answers. *Cost if wrong:* nothing enforces "verify before acting" — a model that skips the line acts on a stale note exactly as it did before, and only a reviewer catches it.
11. **`meld tag --held` posts the `NEEDS-HUMAN #N` ask before the labels, for every actor, and only for categories the issue does not carry yet.** A re-tag of an already-held category is a no-op (no duplicate ask, so an answered issue is not re-gated); the ask names the full held set. The whole-branch review reversed the first version of this ruling, under which a human's `--held` posted no ask: the ask is the gating stamp `Board.needs_human_answered` measures an answer against, so an unstamped hold was one nothing could lift on purpose and any earlier answer on that issue lifted by accident — and the remedy this decision named ("a human posts a new `NEEDS-HUMAN #N` by hand") was impossible, `grammar.HUMAN_VERBS` not having the verb. It has it now, `tag` posts `[human] NEEDS-HUMAN #N` for a human like any other actor, the comment goes out before any label write (a `GitHubError` on it therefore leaves no labels for the caller to retry past), and `needs_human_answered` requires an ask to exist at all. *Not taken:* always re-posting the ask; leaving a human's hold unstamped on the grounds that the human is the authority. *Cost if wrong:* a human who holds an issue is also the recipient of their own ask — it appears in `meld inbox` under the issue it holds, which is where that issue already was; and the coordination issue carries one more comment per hold.
12. **Declarations are rewritten in place and validated for shape only.** `board.replace_section` rewrites an existing `## Scope`/`## May delete` section where it stands (keeping the body's own heading spelling; blank lines after the section collapse to one), appends a missing one, removes one given an empty list; `meld tag` refuses blank paths but does not validate globs or check that paths exist; there is no CLI way to clear a scope (an omitted repeatable option means "not given") — edit the body to remove a section. *Not taken:* `--scope ''` as a clearing form; glob validation. *Cost if wrong:* a typo in a glob refuses every merge on that issue until the body is edited; scopes can only be replaced, not cleared, from the CLI.
13. **`Supersedes:` lines in worker-authored lesson text are escaped like headings.** Only `meld remember --supersedes` (the flag, run by the PM) can write the unescaped first line that `recall`/briefs read; a worker cannot make another group's lesson disappear from `## Relevant memory`. *Not taken:* trusting the text. *Cost if wrong:* none observed; a lesson that legitimately begins "Supersedes: …" as prose is shown with a leading backslash.
14. **A decision supersession is authorized by the `--supersedes` flag on `meld decide`, not by the agreed text.** Any group holding one verified `[joint] DECISION` can retire any decision file; the other PMs auto-approve from provenance plus hash; the record is the PR body's `supersedes:` line, the `- Supersedes:` header, and git history. The verifier pins everything else: flat paths under `.meld/decisions/`, a new path that does not already exist on the default branch (added by the fix wave — otherwise a valid rendering of decision B could be landed at decision A's path and destroy A), the old file byte-identical to origin plus exactly one trailer naming the new file and its date, no second supersession of an already-superseded file. *Not taken:* requiring the joint DECISION text to name the file it supersedes (a grammar change). *Cost if wrong:* a group can retire an unrelated decision without a human seeing it before merge — visible afterwards, reversible by a counter-supersession. Recorded as a residual in spec section 21, plan-6-carried item 28.

Residuals observed in the run and deliberately not fixed live (plan 8 candidates, roughly by cost of leaving them):

1. **Build/review mutual exclusion on an issue's branch.** A reviewer's push-fix and a retry build ran on one branch at once, and a PM merged a PR while a retry was still building on its branch (the retry's commit had to be recovered from a dangling object).
2. **An audit FAIL reopens the issue even when `main` already carries the fix.** The auditor judges the merge commit; the reopen should check later remediation, or the auditor should judge against current `main`. 3. **Rate-limit and spend-limit handling.** The runner treats a 429 or "hit your … limit" result as an ordinary crash (silent backoff relaunches, no board signal); the adapter should recognise it and the runner should pause the role until the stated reset. **Landed in plan 9:** `is_limit`/`reset_at`/`limit_event` (`src/meld/adapters/base.py`) give each adapter its own recognition of a `usage_limit` event, and `run_group` freezes the role on it instead of relaunching — recognise-and-pause is exactly what this item asked for. The review forced two tightenings worth recording plainly: the first patterns matched any noun before "limit" (so "you've hit your context limit" over-matched) and a bare `429` (so "Closes #429" would have too) — the free-noun form was dropped for a fixed list (usage/rate/spend/session/weekly/daily/monthly) and `429` now needs "Too Many Requests" or an explicit http/status/code qualifier; and the claude adapter consults `is_limit` only when the CLI's own `result` reports `is_error`, so a healthy role's own narration about rate limits (its own or someone else's) can never freeze it. A `reset_at` match is believed only when it names an instant strictly after `now`, because a codex stderr line's own timestamp prefix was briefly misread as the reset time. **No transcript of either CLI actually hitting a limit has been captured** — the patterns come from the first live run's prose plus the MIT-licensed `Maurdekye/orgtree`'s tested set; a miss reverts to the old crash-and-relaunch behaviour, an over-match freezes a healthy role for `[runners] limit_retry_minutes` — or, when the over-matched text also named an instant, until that instant, and at most `runners.MAX_FREEZE_MINUTES` (six hours; the fix wave's cap, because a timestamp in prose is not a promise) — and the next live run that hits a limit should capture the real text into `tests/fixtures/transcripts/` and tighten the patterns against it.
4. **Disk full.** A supervisor that cannot create a log file exits; it should back off and retry, and `meld doctor` should warn on low free space. Workers' multi-megabyte benchmark files in `/private/tmp` are what tipped the host. **Landed in plan 9:** both halves shipped. `runners._try_launch` catches a launch failure, backs off on the same exponential schedule as a crash, and leaves the other role running — `run_group` now iterates `ROLES` rather than live processes, so a role with no process launches from inside that same guarded loop, which also means a supervisor that starts while a role is already frozen now launches that role zero times (the old unguarded startup launched it once before the freeze check could apply). `meld doctor`'s new `disk-free` check warns once free space on the volume holding `$MELD_HOME` drops under `[logs] warn_free_mb`. One case the item did not anticipate: `meld run --once` is a one-shot diagnostic (launch, wait, return), not a supervisor, so a launch failure there still propagates as a clean exit-1 error instead of backing off — spec section 17's table now says so explicitly.
5. **The retry tier is prompt-only.** A PM can dispatch a retry at the unchanged tag before the orchestrator retags; `_dispatch` could enforce the rubric, or `collect` could suggest the retag. **Landed in plan 16, the first way:** `RunRecord.outcome` (stamped by `collect`, read back from disk) lets `rules._dispatch` refuse a retry at the unchanged `model` and `effort` after a build run collected as `failed` — `legal`/`refused` and `meld dispatch` read the one rule — and the orchestrator's rubric says so. A retry after `request-changes` is not refused.

A DECISION names no PR, so it stays without a mechanical trigger — a decision that wants an audit opens a challenge.

## Plan 8a — normalized transcripts (landed)

Section 22's "Normalized transcripts" is built. `transcript.py` owns one closed event vocabulary (`Event`, `KINDS`: `run_started`, `message`, `thinking`, `tool_call`, `tool_result`, `usage`, `run_finished`, `log_truncated`, `cli_error`, `raw`) and everything above it: `render`/`render_line` for the terminal, and `Tail` — a byte-offset reader that yields only complete lines and turns an underlying truncation into one `log_truncated` event rather than garbage. Each adapter translates only its own CLI's vocabulary, through `parse_events(line, now) -> list[Event]` (`adapters/claude.py`, `adapters/codex.py`); nothing outside `adapters/` names either CLI's event types, and an unrecognized line renders as `raw` rather than raising — as does a line an adapter *did* recognize whose every content block or item was unknown, which is how a new Claude content block type (`thinking`, `server_tool_use`, `mcp_tool_use` all arrived that way) degrades instead of disappearing. `meld tail <group>/<role>` and `meld tail --run <issue>` render a log from the terminal, live or finished, reading local files only — no board, no party, nothing posted; it needs no board and so never calls `load_context`, and calls `context.refuse_worker` itself so it is not the one verb a worker can run (section 18). And the failure tail a PM posts when a worker dies without writing `.meld-result.json` is now rendered instead of raw (`dispatch.render_tail`, called from `dispatch._collect_build` with `ctx.adapter()`; a `None` adapter — a human party holds no group — and a missing or empty log both render as empty rather than raising). `Tail.read` withholds an unterminated trailing line, because in a growing log that is a line which has not happened yet; `Tail.flush` claims it for a reader that will not read again, which is what keeps a crash message written without a newline — and a pre-plan-8 one-blob log — from vanishing out of the failure tail and out of `meld tail --no-follow`. Following never flushes. The held bytes are bounded by `PARTIAL_CAP`.

**The Claude adapter now launches with `--output-format stream-json --verbose`**, not `--output-format json`. `--verbose` is not optional — `claude -p` refuses `stream-json` without it — and both flags are in `REQUIRED_FLAGS`, so `meld doctor`'s `cli-flags:<group>` check fails loudly the day a future CLI drops either one, instead of every worker's log silently going back to being one unreadable blob. The bound of that check: `doctor.missing_flags` only looks for each flag's *name* as a whole token in `claude --help`, so it cannot catch `stream-json` ceasing to be an accepted *value* of `--output-format` while the flag itself is still listed — doctor would pass while every launch died, and only a real run (or a smoke run) would show it. A Claude role's log is JSONL now, one event per line; under the old `--output-format json` the entire log — and so the entire failure tail — was a single ~5 KB line.

**The log cap truncates in place; it never renames.** `popen_detached` hands the log's open file descriptor to the CLI as its stdout and the run outlives the `meld` process that started it (section 11), so nothing meld-side can rename the file out from under the writer without invalidating that fd. `open_log` opens with `O_APPEND`, which recomputes the write offset from the file's end every time; `transcript.trim_log` — run on every `meld tick`, ahead of everything else `tick` does but *after* the PM refusal, because an exhausted disk killed both supervisors on 2026-09-12 and yet a refused verb must change nothing — reads the log's tail into memory, truncates the original to zero, and only then writes that tail to `<name>.1`, replacing any previous `.1`, so the writer's next line lands at the new end with no fd invalidated. The sidecar comes last because on a full disk it is the write that fails, and it transiently adds up to a keep-window before it does; a `.1` that could not be written is still reported as a trim. `Tail` closes the loop from the reading side: a file shorter than the offset it already holds means it was truncated underneath the reader, so `Tail` emits one `log_truncated` event and resumes from zero instead of misreading the shrink as corruption. `meld doctor` also reports total bytes under `logs/` and warns past `[logs] warn_total_mb`.

**Fixture caveat.** `tests/fixtures/transcripts/claude-run.jsonl`'s final `result` line is the redacted shape captured from the first live run's own log — `--output-format json` (the format plan 8a replaces) writes exactly that one event and nothing else, so it was real to capture. The `system`/`assistant`/`user` lines above it are written by hand from Claude Code's documented `stream-json` shape, not captured from a real multi-turn run. The gap is covered for now by the `raw` fallback (an event type neither adapter recognizes renders as `raw` rather than raising) and by `meld doctor`'s `cli-flags:<group>` check, but it means the Claude adapter's per-event-type parsing is unverified against a real streamed run. The first live run after this plan should capture a full one into `tests/fixtures/transcripts/` and tighten those expectations against it.

**Complete.** Plans 8a, 8b, 8c and 8d have all landed — 8a, 8b and 8c on `main`, 8d on this branch, `plan-8d-config-form`; see their sections below. Spec section 22 is the binding design for all four. Section 21 lists what none of them build: a curses transcript view for a headless box (`meld tail` is plan 8's non-graphical surface; the full-screen version waits until the page has proved which panes matter), token-level streaming (plan 8 renders whole events, never partial messages), starting or stopping a supervisor from the viewer, and guided App setup in the viewer beyond the config form — plus item 31's `submitted` flag on `RunRecord`, named there as plan-8 work.

## Plan 8b — the loopback viewer (landed)

`meld watch` serves one page on `127.0.0.1` and prints its URL, token included; it is a tool a person runs, not a service the framework depends on: no role may start it, nothing reads from it, and it holds no legality logic (section 22). This plan is the read-only half of the viewer: the board, each supervisor’s liveness, each role’s standing freeze, budget, free disk and log bytes above up to four transcripts at a time (`MAX_SOURCES`), alive roles first, each in its own column. `/api/action` (plan 8c, the human verbs from the page) and `/api/config` (plan 8d, the `.meld.toml` form) have both since landed — see their sections below.

**Liveness is a tri-state with evidence.** The first live run announced a dead audit worker as running because `kill(pid, 0)` succeeded on a reused pid. Now `state.liveness` answers `alive` only for a live pid whose process start time matches the recorded one, `dead` for a pid that is gone or one whose start time differs (reused), and `unknown` for anything it cannot settle — no record, no pid, no recorded start time, or a start time `ps` could not read — each with its reason. The evidence is written by the processes themselves: `run_group` records `state/<group>/supervisor.json` (`pid`, `started_at`, `proc_start`) at startup and `state/<group>/<role>/current.json` (plus `log_path`, `reason`, `launch_no`) on every successful launch, and every worker `RunRecord` carries `proc_start`. `proc_start` is `ps -o lstart=`'s own string, compared for equality and never parsed. **Records are never deleted** (a dead pid in one is "confirmed gone", which is more than "no record" can say), and a record that cannot be written is swallowed (`runners._note`): a launch that succeeded must reach `procs` whatever happened to its record, or the next cycle would launch the role twice.

**The stream is plan 8a's `Tail`, framed.** A stream is a log under `$MELD_HOME/logs`, named `<group>/<file>.log`; `stream_path` accepts nothing else, so a request cannot reach outside that directory. Resume is by count (`Last-Event-ID`, which the browser sends on its own reconnects, else `after=`); a client that has seen more events than the file now holds was reading a log that has since been trimmed, and gets one `log_truncated` frame then the whole file. A trim that lands *under* an open connection is handled the same way — the batch `Tail` numbered straight through the truncation is discarded, the reader is rebuilt at offset 0, and the file is replayed from event 1 behind one `log_truncated` frame — so `seq` is a position in the current file throughout and a later reconnect's count means the same thing. When the writer is confirmed dead and the transcript, flushed, does not end in `run_finished`/`usage_limit`/`cli_error`, the stream synthesizes one `run_finished` marked `synthesized` (a Codex transcript ends at `usage`; section 22's table leaves the terminal event to the reader) and closes with `end`. While the writer is alive or unknown the stream stays open on a comment heartbeat and checks the writer every six idle polls, because the check may run `ps`.

**Tried it by hand.** Task 7's implementer ran `meld watch` against a real product clone and opened the printed URL in a real browser: the page, its assets and every per-stream column rendered end to end. The one snag was environmental, not the viewer's — on this Mac the active `gh` account flips between two logins, and `build_status` (so `/api/state`) answers 502 with a GitHub 404 when it is not the smidley one. Run it as `GH_TOKEN=$(gh auth token --user smidley) meld watch` from the product clone.

3. `[viewer] port` defaults to 0 (the OS chooses) and `open_browser` to false; `--port`/`--open` override per launch.
4. The page is tested only for what Python can see (served behind the gate, no external reference, `textContent` not `innerHTML`, only real routes named). Rendering is not unit-tested: no JavaScript runtime is in the toolchain.
5. A stream whose writer is `unknown` never ends on its own; the person closes the tab.

**Known follow-ups:** `discover` and `record_for` read every role record and run record per call (fine at two groups); `liveness` runs `ps` once per check for a live pid, so a page with many live columns runs a few `ps` a second — cache per pid if it ever shows; the `[::1]` host is accepted but the server binds IPv4 only; worker records written before this plan carry no `proc_start` and read `unknown` while alive; `appendEvent` never trims a column's list, so a tab left open on a long run grows the DOM without bound; an `EventSource` the browser abandons (non-200) stays `reconnecting`; `#error` is one slot shared by the two polls; no test covers `Connection: close` on the SSE response or the 502 on `UnknownAdapter`; the `now` seam round-trips through `strptime`, so a differently spelled ISO instant would raise out of `handle`; the cached `/api/state` `Response` is returned by identity and `Response` is mutable; `discover`'s `stat()` races a deleted log (an unhandled exception that drops that one connection); `streams._worker_records` builds a throwaway `StateStore` and drops its `errors`, so a corrupt run record silently vanishes from `/api/streams`. ## Plan 8c — the human verbs from the page (landed)

`meld watch` can now act, not only show. `POST /api/action` runs one of ten verbs — `claim`, `release`, `post`, `tag`, `challenge`, `decide`, `remember`, `plan-approve`, `plan-ack`, `merge` (`viewer/actions.py`'s `VERBS`) — as the human party, by calling exactly the function the matching `meld` command calls; `rules.py` decides every one, precisely as it does for the CLI, and a refusal comes back whole — the verb, the target, and the rule that named it — rendered verbatim, never summarised, because a summary would make the page a second legality authority. Two of the ten, `decide` and `remember`, are refused for a human today by `rules.py` itself (`decide_rule`/`remember_rule` both open `if actor.party.kind not in ("group", "pm")`), so no button for either ever renders — the page draws buttons only from the `legal` lists `render_status` computes, never from the verb table itself — but the two dispatch entries stay: the honest answer to a human's `decide` is that same refusal, rendered verbatim, not the page's silence (spec 22, amended to say so). As on the CLI, a human's refusal posts no `PROTOCOL-VIOLATION`.

The board panel (issues, pull requests, agreements, each row carrying its own legal-verb controls) never acts on a click by itself: a row's button only fills the action bar with that verb and its ref, and nothing runs until the person presses Run — one execution path, so a merge is never one stray click away. `tag` is the one API verb with no bar control at all — its eight fields (scope, may-delete, held, skill, worker, model, effort, size) belong to a form that does not exist yet — so it renders as text rather than a button.

Every transcript now streams over one `/api/events` connection instead of one `EventSource` each; the four-transcript cap (`MAX_SOURCES`) and its alive/dead/unknown priority queue are both gone, and so is the `waiting` badge state they needed. `streams.events` keeps one `_Reader` per `Source` (a stream's name, log path, its group's adapter's `parse`, and a `writer` liveness check), each counting its own idle polls so one talkative transcript can never stall another's flush, synthesis, or `end`. The resume cursor — the SSE `id:` line — is `encode_cursor`'s `<stream>=<count>` for every stream the connection has ever carried, zero counts included, joined by `|`; `decode_cursor` reads it back per stream, and the browser's own `EventSource` reconnect (`Last-Event-ID`) needs no client-side resume logic to use it. A stream that ends is marked, and once `discover` no longer lists it, dropped — bounding both the reader set and the cursor over a long session. **One operational consequence for the owner:** the feed's cost scales with the number of **un-reaped** worker runs, not the number of live ones — `discover` lists every run still on record under `runs/<group>/`, and `meld reap` is what archives a record once its work is merged or closed, so a milestone that reaps promptly keeps both the resume cursor and a page load's replay small. Plan 8b's four-source cap hid this.

**Decisions for the owner (each reversible):**
1. About 45 bytes per stream per frame on a loopback connection, which is the price of leaving all reconnect logic to the browser.
2. `api_action` turns an unhandled exception into a rendered 500 rather than letting it drop the connection and print a traceback in the person's terminal — a long-lived local tool has to answer even when something unforeseen breaks.
3. A row's button only prefills the action bar; nothing runs until the person presses Run.
4. `tag` is reachable only through the raw API for now, until a form exists for its eight independent fields.
5. The page acts as the human party or refuses to start: `meld watch` itself refuses to run unless `ctx.actor().is_human`, and `api_action` separately refuses when the context it actually holds is not human, whatever the request body claims — so a `MELD_GROUP`-launched `meld watch` cannot start, rather than silently posting (and being refused) as that group.

## Plan 8d — the configuration form (landed)

`meld watch`'s page now edits `.meld.toml`, not only shows it — the last of the five routes spec section 22 promises. `GET /api/config` answers with the configuration canonicalised: every field the schema defines, at its effective value, plus any key `unknown_keys` names carried over from the file verbatim, falling back to the raw parse when `Config.from_dict` cannot read the file at all — alongside the path it came from, the model catalogue `models.toml` holds (so the generated form offers model and effort choices that cannot be wrong rather than rejecting them after the fact), a `version` digest of the file it read, and the diagnosis the form itself cannot show: `unknown`, every key the schema does not define, and — on the fallback path only — `error`, the parser's own complaint. Those last two are why the page can say on open that no save will pass, instead of letting the first Save be where a person discovers the file has to be hand-edited first. `PUT /api/config` takes that same object back, ignoring `path`, `models`, `note`, `unknown` and `error`, and requiring `version`. What the form edits is what a running product may change day to day: the budgets, the concurrencies, the models and efforts, the timeouts, the polling and runner intervals, the log caps, the viewer's own port, and — within a group — its `git_name`/`git_email`. What it shows but will not let you touch is identity: a group's `cli`, `bot`, its authentication and token or App settings, and `[repo]`/`[humans]`. Changing any of those mid-milestone orphans a group's claims and its open pull requests, and the remedy for that stays `meld setup`, not a text box on a page.

A write passes four gates before it ever touches disk, in that order: the `version` it names must still be the file's, or a form held open while the file changed underneath it would save the copy it is still holding and quietly revert whatever the file gained meanwhile (409); the candidate must parse into a `Config` (`Config.from_dict`, after an unknown key is refused by name — `from_dict` would otherwise just ignore it), which since this branch's last wave means every numeric setting clears its own floor rather than whatever a bare `int()` would swallow; the rendering of that `Config` must parse back into an equal one (`dumps` round-tripped through `tomllib`, which catches a serializer bug rather than a bad edit); and `doctor.config_checks` — the two checks, `models:<g>` and `timeout-ceiling:<g>`, that are a function of the configuration and the model catalogue alone — must pass. Only then does `atomic.write_atomic` replace the file, so a refusal at any gate leaves it exactly as it was.

The floors are per field, not a blanket rule, and **the rule is whether `0` is a lie**. A `0` is refused where it cannot mean what it says — where the code coerces it into something else, or acts on it in a way the word does not describe. `review.quorum = 0` is clamped to 1 by `effective_quorum` and always was; `audit.batch_merges = 0` cannot mean a batch of nothing, because `audit.due` already requires a pending merge; `polling.interval_seconds = 0` does not poll quickly but deletes the backoff, since `waiting.py` doubles it from zero forever; `runners.restart_hours = 0` recycles a paid session every cycle *and* launches each one on a zero-second timeout; `worker.log_tail_lines = 0` posts the whole transcript, because `lines[-0:]` is every line. A `0` is kept where it means something, and there only a negative is refused: the three budgets and `budget.wallclock_hours`, `lease.grace_minutes` (the lease expires at the deadline), `agreement.amend_cap` (propose, then AGREE or DISSENT), and `audit.batch_hours` (do not wait on age; audit as soon as anything is pending) — whose refused sibling `batch_merges` in the same table is the contrast that makes the rule concrete. That first clause is about lying rather than about harm, deliberately: an honest `0` survives even when it is drastic, and a dishonest one goes even where the clamp meant nothing was misbehaving. A second and narrower clause floors a `0` that is a **runaway** even where it is honest — a zero poll interval never stops, and `notify.repeat_after_minutes = 0` honestly means "repeat every pass" while what it repeats is a nudge posted to a Slack workspace the person may not own; the test there is not cost but the absence of a stopping condition, pointed at something outside meld. Three of the floored settings — `runners.roster_refresh_minutes`, `silence_grace_minutes` and `summary_cadence_minutes` — are read by no loop at all and reach the product only as the cadence a role's prompt states it should keep, so a `0` there states a rule that cannot be followed as written. `_at_least` refuses a float and a bool as well, so `review_concurrency = 2.5` is named rather than truncated to 2, and its message names the setting where `int()`'s named only the value; a group's inert App settings (`_loose_int`) are the one numeric read still deliberately lenient. A worker timeout is the same rule as a duration: `timeouts.S = "0m"` launches a worker already past its deadline, so the floor sits at `from_dict`'s read of `[timeouts]` rather than inside `parse_duration`, whose contract belongs to its other callers.

A save reconfigures nothing already running. The file is what the next `meld` process reads; the supervisors already running, and `meld watch` itself, keep the configuration they started with — which is why `GET` reads the file fresh on every call rather than the `Config` this process loaded at launch. And plainly: the first save rewrites the whole file canonically — every field the schema defines, defaults included, in a fixed order under a template header — and it does not preserve whatever comments were in the file before. A hand-written minimal `.meld.toml` becomes the full explicit one the moment anyone saves the form once.

**Decisions for the owner (plan 8d; each is reversible).** Decisions 1–8 are numbered as in the plan header (`docs/superpowers/plans/2026-09-20-plan-8d-config-form.md`), with decision 2 given below in its final, amended form; decision 9 has no counterpart there — it was taken during the final fix wave, after the plan was written.

1. **`dumps` emits every field the schema defines, defaults included.** A round trip is only exact if nothing is omitted, and a form that shows a field and then does not write it is lying. *Not taken:* write only what differs from a default, which needs a second table of defaults that can drift from `from_dict`'s own and makes the round-trip comparison depend on which fields were omitted. *Cost if wrong, said plainly:* the first save turns a hand-written minimal `.meld.toml` into the full explicit file, and any comment in it is gone — the header template is re-rendered, nothing else survives.
2. **`GET` answers the configuration canonicalised, not the bare parse — amended by a ruling made during Task 5's review (R20).** The plan's original call had `GET` return `tomllib.loads(text)` verbatim, plus the catalogue and the path. A real `meld setup` starter file exposed the gap: the bare parse rendered 27 fields and none of the tables §22 promises the form offers, because a starter file simply has no `[budget]`/`[polling]`/`[runners]`/`[timeouts]`/`[logs]`/`[viewer]` table to parse in the first place. `GET` now answers with every field the schema defines at its effective value, plus any key `unknown_keys` names carried over from the file verbatim, falling back to the raw parse when `Config.from_dict` cannot read the file at all. *Not taken:* leave `GET` as the bare parse and fill defaults in the browser instead. *Cost if wrong:* the form shows defaults nobody typed — but the first save was always going to write them anyway, so nothing it shows is a value that would not exist the moment somebody saves once.
3. **An unknown key is refused by name, and `from_dict` is not what refuses it.** `Config.from_dict` reads with `.get` and silently ignores what it does not recognise, which is correct for a parser tolerating a newer file and wrong for a form that must not drop a field somebody typed; `unknown_keys(data)` walks the schema separately and the route refuses with the dotted paths it returns. *Not taken:* teach `from_dict` itself to raise on an unknown key, breaking its other job of reading an older or newer file leniently. *Cost if wrong:* none observed — the split is what let the route report an unknown key without also breaking lenient parsing elsewhere.
4. **The doctor subset is exactly `models:<group>` and `timeout-ceiling:<group>`.** Those two alone are a function of the configuration and the model catalogue; everything else `meld doctor` checks needs the network, a binary, a token, or the machine, and a form must not refuse a budget change because the network happens to be down. *Not taken:* run every doctor check against the candidate. *Cost if wrong:* a save can pass the form's gate and still leave `meld doctor` unhappy about something the form was never positioned to check.
5. **The form offers what a running product may change; identity stays `meld setup`'s.** `[repo]`, `[humans]`, and a group's `bot`, `auth`, `token_env`, `app_id`, `installation_id` and key settings render read-only; only a group's `git_name`/`git_email` are editable, because they label a commit rather than claim who anyone is. *Not taken:* let the form change identity too, with a warning. *Cost if wrong:* changing a bot or a CLI mid-milestone from a text box could orphan open claims and pull requests with no `meld setup`-level ceremony to catch it — the API still accepts these fields on the round trip, so opening them later needs no route change, only a decision to open them.
6. **A write reconfigures nothing already running.** The file is what the next `meld` process reads; the supervisors already running, and `meld watch` itself, keep the configuration they started with. *Not taken:* push a changed value into the running supervisors, or have the page hold and serve its own in-memory copy. *Cost if wrong:* `/api/state`'s derived numbers (the budget cap, the warn thresholds) come from `ctx.cfg` and stay stale until the page restarts, and nothing today reloads a running supervisor either — a changed concurrency or model takes effect only on that group's next restart.
7. **A render that cannot reproduce its own input is a 500, not a 400.** If `from_dict(loads(dumps(cfg))) != cfg`, the person did nothing wrong — `dumps` has a bug — so it is reported as one, with the fields that differ named, and nothing is written. *Not taken:* fold it into the same 400 a bad candidate gets. *Cost if wrong:* a genuine serializer bug and a bad edit would look identical on the wire, though the message text still tells them apart.
8. **The form is generated from the payload, not hand-written.** One renderer walking the scalar tables means a field added to `Config` appears in the form with no JavaScript change, and the page cannot quietly fall behind the schema. *Not taken:* hand-write a field per setting. *Cost if wrong:* none observed; if anything the cost runs the other way — a nested sub-table the renderer does not recognise as scalar is skipped (`isTable`) rather than mis-rendered.
9. **`review.quorum = 0`, `audit.batch_merges = 0` and `notify.repeat_after_minutes = 0` are now refused, and they are the floors that can turn a file which has worked until now into one that will not load.** Added in the final fix wave, when every setting the form can write gained a floor. These two are the cases where the coercion was *already* silently doing the right thing, so refusing them buys no change in behaviour: `effective_quorum` is `max(1, min(quorum, len(groups) - 1))`, so a `0` quorum already ran at 1; and `audit.due` guards both its comparisons with `bool(pending)`, so `batch_merges = 0` behaved exactly as `1` does. They are refused anyway because a `0` in either never meant what it says — it meant 1, silently, forever — and the rule behind every floor on this branch is that a field which quietly means something other than what it says is the lie worth fixing; a pair that coerced while every neighbour refused would be its own trap. (Their sibling `audit.batch_hours = 0` is *kept*, because "do not wait on age" is a real and distinct policy — that contrast is the rule in one table.) **The third is the marginal one, and it is floored under a different clause of the rule.** `notify.repeat_after_minutes = 0` is, by the letter, *honest*: it reads as "repeat every pass", and `notifier.py`'s `(repeat + offset) * 60` does exactly that — so the lie test alone points the other way, and it was flagged rather than changed for that reason. It is refused under the rule's second clause instead: what it repeats is a nudge posted to a Slack workspace the person running meld may not even own, so an honest `0` here is a loop with no stopping condition aimed at an external service and at other people's attention. The test is not cost — an honest `0` that is merely expensive stays — but the absence of a stop, pointed outward. **Reasonable people could rule the other way on this one**, and it is recorded as a judgement call rather than a table entry. *Not taken:* leave all three reading `int()` and let the clamps keep absorbing them; or, for `repeat_after_minutes` alone, let an honest zero stand. **If you disagree, each reversal is one character** — the `1` in `_at_least(review.get("quorum", 2), 1, ...)`, `_at_least(audit.get("batch_merges", 5), 1, ...)` or `_at_least(notify.get("repeat_after_minutes", 120), 1, ...)` in `config.py`, plus that field's entry in `tests/test_config.py`'s `FLOORS` table, which is what drives the per-field test. *Cost if wrong:* somebody's working `.meld.toml` stops loading at the next `meld` command until they change a `0` to a `1` — and the error names the setting, which is more than the old silence did.

**Known follow-ups:** a malformed table (`review = 5` in place of a table) reaches `Config.from_dict` as a bare `AttributeError`/`TypeError` rather than a clean `ConfigError`, so the viewer's 400 is correct but names no field, and `dumps` itself raises a bare `KeyError` given a hand-built `Config` carrying a partial `timeouts`/`budget` (unreachable through `from_dict`, which always fills every field, but a trap for code that builds one directly); on a PAT group, `_loose_int` quietly coerces or drops inert leftover App settings (`app_id = "abc"` or `nan` vanish, `12.9` becomes `12`, `true` becomes `1`), which partly defeats the point of keeping them at all, and separately `load_config` does not wrap the `AttributeError`/`TypeError` a badly-shaped hand-edited file (`groups = 5`) raises out of `from_dict`, so the CLI still tracebacks on it even though the viewer's own route already catches the same exception; the three-line adapter-resolution `try`/`except` is duplicated between `run_checks` and `config_checks` rather than shared, and no doctor-layer test pins the timeout-ceiling boundary at exactly equal or one second below, or an effort invalid for an otherwise-known model; the route's `read_text`/`write_text` use the platform's locale encoding where TOML is UTF-8 by definition (consistent with how `load_config` already reads, so not a new gap, but still one worth closing); a render-mismatch 500's `differs` list names `Config`'s own dataclass fields rather than their TOML paths; two saves genuinely racing each other can still lose an update — R34's `version` closed the common case (a panel left open while the file changed, which is now a 409), but the check itself is a read-then-write with no lock around it, so two `PUT`s interleaving between `config_version(read_text())` and `write_atomic` will both see a current version and the second will overwrite the first; `_lock` guards only `_state_cache`, and the write stays atomic either way, so the result is a lost update and never a half-written file; **`budget.wallclock_hours` is read by nothing at all** — `from_dict` parses it, the final fix wave gave it a floor (`>= 0`, as a budget), `dumps` writes it into every saved file and the form renders it as an editable field, but no module anywhere consumes the value, so a person can set it, save it, see it persisted, and change nothing; whether it is an unkept promise to implement or a leftover to delete is a spec decision rather than a fix-wave one, and until it is made the form is offering a knob that is not wired to anything; a quoted TOML key that itself contains a literal `.` is walked but its control is silently skipped, so editing it through the form is a no-op (the save still 400s afterward, naming it as unknown, so nothing already there is lost; `GET` no longer 500s on one, which is a separate fix), and a same-branch test assertion (`assert '"repo"' in js`) is vacuous, since `el("repo")` already contains that substring regardless, leaving only its neighboring `'"humans"'` clause doing real work; `/api/state`'s derived numbers — the budget cap, the warn thresholds — come from `ctx.cfg` and go stale the moment a save changes the file underneath a page that stays open, since dropping the cached response only affects the next call this process serves; ## Plan 9 — run reliability (landed)

The first live run's three worst failures — residuals 3, 4 and 14 above — are fixed, each behind its own tests, plus the `meld doctor` warning residual 4 also asked for. **A usage limit freezes the role instead of relaunching it (residual 3).** Each adapter recognises its own CLI's limit answer — `is_limit`, `reset_at`, `limit_event` in `src/meld/adapters/base.py` — and emits a `usage_limit` event instead of `run_finished`/`cli_error`/`raw`. `run_group` checks a role's freeze first on every turn, before anything else, and never relaunches a frozen role. The freeze is persisted at `$MELD_HOME/state/<group>/<role>/limit.json` (`freeze_path`/`read_freeze`/`write_freeze`), so it survives a supervisor restart. The **supervisor**, not the role, posts `LIMITED`, because by the time anyone can read the transcript the role's process is already gone; a notice that could not be posted (the supervisor itself rate-limited at the wrong moment) is retried on the `limit_retry_minutes` cadence — the fix wave's change, from every cycle, because each attempt is two paginated reads plus a POST at a board that is already failing and a cycle is five seconds — with `announce_attempted_at` in the freeze file so the cadence holds across a restart. `LIMITED` is a new liveness verb (`grammar.py`) and is **framework-only** (`posting.FRAMEWORK_ONLY_VERBS`) — a role's own `meld post LIMITED` is refused, and both the orchestrator and PM prompts say so and tell the role to close the pair with its own `RESUMED` on the next `limit`-reason launch. `run_group` gained a `wall=` seam (an injected ISO-8601 clock, distinct from the monotonic `clock=` that already drove backoff and restart timing) so no test depends on the wall clock. New config: **`[runners] limit_retry_minutes`** (default 30) is the re-probe cadence when the CLI named no reset time. When the CLI *did* name one, it is honoured only up to **`runners.MAX_FREEZE_MINUTES` (360, a module constant and deliberately not a config knob)** after the freeze began: the instant is parsed out of the CLI's own prose, and the fix wave's reviewer showed one stray timestamp in a limit message freezing a role until December. Six hours covers a Claude five-hour session window; a genuinely weekly limit re-probes four times a day, each re-probe costing one fast-failing launch and one true `LIMITED`. **If a role looks stuck, the freeze file is the place to look:** `$MELD_HOME/state/<group>/<role>/limit.json` says when the freeze began and what reset it believes, a stale one clears itself at the six-hour cap, and deleting it **and restarting the supervisor** forces a re-probe. Deleting it under a running supervisor does not: the next cycle re-reads the role's transcript from the start, finds the same limit, freezes again for a fresh window and posts a second `LIMITED`. `meld run`'s own report also carries `frozen_until` per role (the deadline it is actually waiting on, cap included), so a frozen role is not read as one that failed to launch.

*Honest caveat, the same shape as plan 8a's streaming-fixture one above:* no transcript of either CLI actually hitting a limit has been captured. The recognition patterns come from prose observed in the first live run plus the MIT-licensed `Maurdekye/orgtree`'s tested set. A miss looks like the old bug — silent crash-and-relaunch; an over-match freezes a healthy role for `limit_retry_minutes`, or until the instant it thought it read, and never for longer than the six-hour `MAX_FREEZE_MINUTES` cap. The next live run that hits a real limit should capture it into `tests/fixtures/transcripts/` and tighten the patterns against it.

**A launch that cannot start backs off instead of ending the run (residual 4, first half).** `runners._try_launch` catches the failure, records it, and backs off on the crash schedule while the other role keeps going. `run_group` now iterates `ROLES` rather than live processes, so a role with no process — never started, or its last attempt failed — is launched from inside that same guarded loop; one side effect is that a supervisor started while a role is already frozen now launches that role zero times, where the old unguarded startup launched it once before the freeze check could apply. **`meld run --once` is the deliberate exception:** it is a one-shot diagnostic whose contract is launch/wait/return, not a supervisor, so a launch failure there is re-raised and reaches the CLI as a clean exit-1 error (`cli._guard` turns the `DispatchError` into a `click.ClickException`) instead of backing off. Spec section 17's table says so now.

**`meld doctor` warns on low free space (residual 4, second half).** The new `disk-free` check (`run_checks`'s `disk_usage=shutil.disk_usage` seam, `src/meld/doctor.py`) reports free space on the volume holding `$MELD_HOME` and warns — `ok=None`, never `False` — once it drops under **`[logs] warn_free_mb`** (default 2048 MB); the fix text tells the operator that a supervisor now backs off rather than exiting on a full disk, but that every launch keeps failing until there is room. Low disk is a machine condition a person fixes, not a misconfiguration, so this check can never fail `meld doctor` outright, only warn.

**An identical refusal is announced once, not re-issued more narrowly than that (residual 14).** `actions.refuse` skips the `PROTOCOL-VIOLATION` comment when the newest such comment from the same party about the same target already carries the exact posted body this refusal would post (`_refusal_text`, built once and used for both the post and the comparison); only an authorized, parsed board comment counts as "already said." **This is narrower than the residual asked for: the refusal itself is unchanged and happens on every call — only the repeated GitHub announcement is throttled** — `Refused.violation_posted` is `None` on a skip, `True` on a fresh post, `False` on a failed one, so a caller can tell the three apart. The board is the throttle's memory, not a local file, so it holds across a restart and across the group's two supervisors the same way `meld:nudged` already does (spec section 14).

**The `OSError` boundary is closed (the whole-branch review's fix wave).** A launch failure was the only `OSError` this plan first caught, which left four more of the same shape able to end the supervisor: `_announce`'s underlying `subprocess.run` (a missing or upgraded `gh` raises `FileNotFoundError`, which `_announce`'s `except (GitHubError, BoardError)` does not catch), `write_freeze` from `_freeze` and again from `_frozen`, and the freeze file's own `unlink`. One `except OSError` now wraps **the whole body of `run_group`'s `for role in ROLES` iteration** — the freeze check, the launch, the poll, the freeze write, the notice — and treats what it catches as that role's cycle failing: recorded in `launch_errors`/`last_launch_error`, backed off on the crash schedule, with the other role still taking its turn. `_StopRequested` and `KeyboardInterrupt` are not `OSError`, so a stop still propagates and a `RuntimeError` still reaches the caller; do not widen that `except`. `launch_role`'s own `try` grew to cover `refresh_roster` and `role_prompt` too, which read the preamble, the role prompt and the product's standards file, so a filesystem error while assembling a prompt is a `DispatchError` like every other launch failure. One consequence worth knowing: `_freeze` announces before it writes, so if `gh` itself is gone the freeze file is not written and the role retries on the backoff schedule rather than the freeze cadence — the supervisor lives, which is the point, and the role's next limit writes the file once `gh` is back.

One thing this plan found during review and deliberately left for the next one, because it is only worth fixing if a live run proves it a real problem:

- **`LIMITED` reposts on every re-probe when the CLI names no reset time** — about two comments an hour per frozen role across a multi-hour outage. Accurate, but noisy over a long freeze. If a live run makes that a real problem, the fix is Task 4's own mechanism — `_already_said`'s exact-body comparison — applied to `LIMITED` instead of `PROTOCOL-VIOLATION`.

## Plan 40 — a conflicted pull request has a way back (PR #58)
