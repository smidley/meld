## What Meld is

Meld lets N independent AI coding systems ("groups", each with a long-lived orchestrator, a long-lived PM, and short-lived headless workers in git worktrees) build one GitHub-hosted product together. Each group authenticates to GitHub as its own bot identity — either a machine-user account with a personal token (`auth = "pat"`, the default), or, as of plan 6a, a GitHub App installation (`auth = "app"`, bot login `<slug>[bot]`) that needs no extra GitHub account or mailbox. GitHub is the only shared state: issues are the work queue, assignment is the claim lock, a per-milestone coordination issue is the conversation, and every comment there starts with a `[<party>] <VERB> [<ref>]` header. "LLM decides, Python enforces": the `meld` CLI computes the legal actions for the calling party and refuses anything else, posting `PROTOCOL-VIOLATION` where every group and the human can see it. Agreed decisions and lessons persist as versioned files that auto-approved memory PRs carry into the repo (`meld decide`/`meld remember`/`meld recall`), a human runs the plan gate and talks to every group from one console (`meld plan`, `meld inbox`, `meld chat`), and each PM's `meld tick` handles red CI, off-protocol GitHub changes, stray comments, and Slack nudges without being asked.

## The SDD process used for this plan (repeat this)

1. **Spec first.** Changes to behaviour start in the spec; the spec wins over any plan. The spec's own section 21 item 4 already recorded that "a personal token cannot create a check run" as the reason PAT groups get a commit status instead of the check run that section 21 originally asked for; plan 6a's Task 6 ships that originally-intended behaviour for App groups specifically, without changing it for PAT groups (see "Decisions for the owner").
2. **Plan, then execute task by task.** `docs/superpowers/plans/2026-09-05-plan-6a-github-app-identity.md` has 6 tasks; each got its own failing tests, implementation, a focused-then-whole-suite test run, and a plain conventional commit. Every task got an independent review; every finding produced a recorded ruling. The ledger lives in `.superpowers/sdd/2026-09-05-plan-6a-github-app-identity/` for this plan: a brief and a report per task (1–6), a `review-<sha>..<sha>.diff` per reviewed task, `pr-body.md`, `progress.md`. A whole-branch review runs before the milestone PR is opened; its findings become one fix wave of small commits, each with its own failing test first.
3. **Hermeticity is a hard rule.** No network — plan 6a's installation-token mint takes an injected `post` callable in tests, exactly like plan 4's Slack webhook did — no dependence on the host's `~/.claude`, gitconfig, or wall clock; inject `now`; every `load_context` in tests passes `adapter_for=`. `openssl` itself runs for real (key generation, signing, and verification are all local; nothing reaches the network).
4. **Security invariants.** Workers never hold GitHub credentials; only PM-side code pushes/merges/reviews/commits with the group's token and bot identity (memory PRs included). Anything worker- or stranger-authored that reaches GitHub goes through `neutralise_closers`; `[joint]`, `LEASE`, `EXPIRED`, `IGNORED-COMMENT` are framework-posted only; challenge verbs go through `meld challenge`. Plan 6a adds: an App's private key never appears in argv, logs, state, result dicts, error messages, worker environments, or the repo — it reaches `openssl` only through a 0600 temp file deleted immediately after signing; installation tokens are cached only under `$MELD_HOME/cache/<group>/` with mode 0600 and never printed; `MELD_APP_KEY_*` is scrubbed from worker environments exactly like `MELD_TOKEN_*`.
5. **Reconcile docs at the end of each plan** (spec sections touched, README table, this file) — this commit is that step for plan 6a.

## Decisions for the owner (plan 6a; each is reversible)

- **One App per group, not one shared App.** An App has exactly one identity (`<slug>[bot]`); a shared App could not tell the groups' actions apart, breaking every rule that assumes one login per group (`party_of_login`, `approving_parties`, author/committer checks). Alternative not taken: install a single App once and have every group act through it.
- **Signing the App JWT via the `openssl` CLI, not a Python crypto library.** RS256 is exactly `openssl dgst -sha256 -sign`; the key passes through a 0600 temp file (never argv), removed in a `finally`. Alternative not taken: add `PyJWT`/`cryptography` as a runtime dependency — ruled out by the plan's global constraint of stdlib plus `click` only.
- **Minting the installation token over HTTPS with `urllib.request`, not `gh api`.** `gh` injects its own `Authorization` header from `GH_TOKEN`, and the mint call must send the JWT as `Bearer`; every other call still goes through `gh api` with the installation token in `GH_TOKEN`. Alternative not taken: shell out to `gh api` for the mint too and fight its header injection.
- **The installation token is cached on disk, 0600, per group, and reused while more than 5 minutes remain.** PM loops call `meld` dozens of times a minute; minting a fresh token every process would burn the App's rate-limit budget for no benefit — `$MELD_HOME` is already disposable, secrets-adjacent scratch. Alternative not taken: mint a new token on every `meld` invocation.
- **Config shape:** `auth = "app"`, `app_id`, `installation_id`, and *exactly one* of `private_key_env` (PEM text, literal `\n` allowed) or `private_key_file`; `token_env` is ignored for App groups. `bot` must still end in `[bot]`. Alternative not taken: let both key-source settings coexist (or allow neither), or fold the key into the existing PAT `token_env` slot instead of adding dedicated fields.
- **A 401 forces one token refresh and retry**, rather than trusting the cache's own expiry math alone. Alternative not taken: refresh proactively before every single call regardless of remaining lifetime (correct but wasteful of the App's rate budget), or never react to a 401 and let clock skew or an out-of-band revoke fail the call outright.
- **`meld doctor` replaces the PAT identity/permission probes with App-specific ones** (`app:<g>`: the JWT signs and `GET /app`'s slug matches `bot`; `app-installation:<g>`: the installation token mints, its `permissions` map grants contents/issues/pull_requests/statuses = write, its repositories cover the product repo). Alternative not taken: run the old PAT probes unmodified against an installation token — they assume a `GET /user` viewer login, which an App token does not have.
- **App groups get a real neutral check run in addition to the `meld/review/<group>` commit status** — the quorum keeps reading only the status (unchanged for PAT groups), and the check run is purely a visible, non-blocking echo on the PR's Checks tab. Alternative not taken: drop the commit status now that a real check run is possible, or make the check run a required/blocking check — either would break the PAT-group quorum path or contradict "neutral."
- **App creation stays a manual browser flow; `meld setup --app` only prints the steps and writes the config shape.** Alternative not taken: automate App creation through GitHub's manifest flow now — deferred to a plan 6b candidate (see "What is next").
- **`GitHub.token` becomes a property instead of every call site taking a token parameter.** The existing `push_branch(wt, branch, ctx.gh.token)` call sites in `dispatch`, `review`, and `memory` keep working unchanged and still get a fresh installation token on every access. Alternative not taken: thread a `token_provider` argument through every one of those call sites individually — a much larger, more error-prone diff for the same result.
