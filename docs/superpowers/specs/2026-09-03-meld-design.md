# Meld: multi-AI coordination framework — design

Date: 2026-09-03
Status: draft for review
Name: **Meld** (to merge distinct parts into one whole; the working name until 2026-09-03 was "moot"). Package and command are both `meld`.

## 1. Purpose

Meld lets N independent AI coding systems (day one: Claude Code and OpenAI Codex CLI) work on one GitHub-hosted product together, with a human able to steer, contribute, and intervene. Each AI system is a **group** with an orchestrator, a project manager (PM), and many short-lived worker agents. Groups negotiate plans, split work by free claim, review and modify each other's code, and challenge each other's claims. The bet is that independent models checking each other produce a better product than either alone.

Everything durable lives in GitHub (issues, PRs, milestones, files in the product repo). Everything the models are not allowed to get wrong is enforced by Python, not prompts.

## 2. Goals and non-goals

Goals

- Mostly autonomous execution inside a human-approved plan.
- N groups, each a different AI CLI, added by writing one adapter.
- Massive parallelism: many workers of the same speciality at once.
- Cross-group review with the power to modify, and a merge quorum that no group can satisfy alone.
- Hallucination protection: evidence requirements, challenges, independent audit, drift detection.
- Shared, versioned memory of decisions and lessons that orchestrators consult.
- One human console to chat with all orchestrators and receive one agreed answer.
- One local page that shows what every agent is doing while it does it, and from which a person can answer what needs a person.
- Every rule that matters is code with tests.

Non-goals for v1

- Webhooks, or any service reachable from off this machine. Polling only. `meld watch`'s viewer (section 22) is not an exception: a person starts it, it binds loopback, and it dies with the terminal that started it.
- Running groups on separate machines. Designed for portability; tested on one machine.
- Fine-grained token scoping per branch or per label. Mitigated by giving workers no GitHub credentials at all (section 12).
- Judging model quality automatically. That is done by humans watching the first milestones and turning bad decisions into prompt edits or new invariants.

## 3. Decisions made during design

| Topic | Decision |
|---|---|
| Autonomy | Human approves the plan per milestone; agents run autonomously through merge within it |
| Framework location | Its own repo (`~/Documents/meld`), reusable across products |
| Orchestrator channel | GitHub coordination issue, one per milestone |
| Identity | One GitHub identity per group (a machine account or, since plan 6a, a GitHub App); the claim lock is the `meld:claimed-by:<group>` label (plan 6b — it was the issue assignee before, which an App's bot user can never be) |
| Topology | Orchestrator and PM are long-lived headless processes per group; each worker is a fresh headless run in its own worktree |
| Cross-modify | Reviewers may push to the PR branch; last committer's group cannot approve |
| Work split | Free claim, first claim label wins |
| Hosting | This Mac first, portable by design (single entry point, env-var secrets) |
| Language | Python 3.12, `uv`-managed, `gh` under the hood |
| Framework shape | LLM decides, Python enforces: `meld status` returns legal actions, verbs refuse anything else |
| Groups | N, configured in `.meld.toml`; two shipped adapters |
| Name | Meld |

## 4. Architecture

Three layers in one Python package.

1. **`meld` CLI.** The only way any agent touches GitHub. Verbs today: `status`, `wait`, `claim`, `release`, `post`, `models`, `dispatch`, `tick`, `collect`, `review`, `merge`, `audit`, `reopen`, `reap`, `tag`, `challenge`, `roster`, `run`, `decide`, `remember`, `recall`, `plan`, `inbox`, `chat`, `notify`, `setup`, `doctor`, `tail` (plan 8a); `watch` is plan 8b (section 22). Every mutating verb recomputes the legal-action set for the calling party and refuses anything outside it, naming the violated rule. The calling party is `MELD_GROUP` (a group name) plus `MELD_ROLE` (`orchestrator` or `pm`), or `human` when neither is set and `gh` is on a listed human account. State lives under `MELD_HOME`, default `~/.meld`.
2. **Role prompts.** Markdown, one per role, rendered identically for every adapter: `orchestrator.md`, `pm.md`, `workers/<speciality>.md`. Shared preamble carries the cardinal rules, the `meld status` first habit, the header grammar, and a pointer to the product repo's own agent instructions, which win over framework defaults.
3. **Runners and adapters.** `meld run <group>` starts a group's orchestrator and PM processes with the right prompts and environment (`--detach` runs that supervision in its own session and `meld ps`/`meld stop` read and end it through the supervisor's own record, plan 15; restart after a reboot or a kill stays outside v1), restarting them on a schedule. `meld chat` (the human console, section 14) landed in plan 4; `meld setup` (prepares a product repo) and `meld doctor` (checks the machine) are still plan-5 work (section 21). Each supported CLI is an adapter module that knows how to render prompts, launch a headless run with a model and effort, and which models and efforts are valid.

Values written as `<populated ...>` are filled by `meld setup` from the packaged `models.toml`, not hand-typed — `setup._group_block` takes a `large`-tier model for the orchestrator and a `medium`-tier one for the PM, falling back to the first model the registry lists for that adapter — and `meld doctor` re-verifies every configured model against `models.toml`. ### `models.toml` (framework)

Per adapter, per model: `context_class` (`small` | `medium` | `large`), `efforts` (ordered list), `tier` (`small` | `medium` | `large`, used for budgets), and `default_for` (`orchestrator` | `pm` | `worker`, optional). Model identifiers are populated at implementation time from each CLI's live model list and re-verified by `meld doctor`; this spec does not pin them because they change faster than the framework.

`size` to `context_class` compatibility: `S` runs on any class, `M` requires `medium` or `large`, `L` requires `large`.

**A group's own environment and CLI settings (plan 28).** Two free tables per group make "Codex pointed at my server" a configuration rather than a new adapter. `[groups.<g>.env]` is added to every launch of the group, roles and workers alike, under the launch's own identity: `config.extra_env` drops any `MELD_*`, `GIT_*`, `GH_*` or `GITHUB_*` name, so a group can point its CLI at a model server (`ANTHROPIC_BASE_URL`, `OPENAI_API_KEY=ollama` as the placeholder a keyless server ignores) but never hand a worker a token or re-point its git identity. `[groups.<g>.cli_config]` reaches the adapter as `LaunchSpec.cli_config`: the Codex adapter renders each entry as a `-c key=value` override (a dotted key such as `model_providers.ollama.base_url` is quoted as one key in the file), which is how an ephemeral `codex exec` -- it reads no config file -- learns a custom `model_providers.<id>` and `model_provider`; the Claude adapter merges the entries under its own `--settings`, where hooks stay disabled, memory off and credentials blanked. Both tables are the product's to fill (any key), written only when they hold something, and committed with `.meld.toml`: no secret belongs in either; a keyed provider's key is exported in the shell that runs `meld run`. The models such a group names come from the product's own catalogue, `.meld/models.toml` beside `.meld.toml`, laid over the packaged `models.toml` (`ModelRegistry.load(extra=...)`) and written by `meld add-model <adapter> <id> --tier --context --efforts`, because a local model's tier and context class are the product's call.

## 6. GitHub data model

- **Milestone.** One per approved unit of work. Description holds the approved plan. Exactly one coordination issue.
- **Coordination issue.** Label `meld:coordination`, title `Coordination: <milestone>`. All cross-group and human-to-group conversation happens here. Every comment begins with a header line (section 7).
- **Work issue.** One per task, in the milestone. Labels:

| Label | Meaning |
|---|---|
| `meld:planned` | Created by the plan, not yet approved |
| `meld:ready` | Approved, unclaimed |
| `meld:in-progress` | Claimed, worker running or pending |
| `meld:in-review` | PR open, awaiting review quorum |
| `meld:blocked` | Needs orchestrator resolution |
| `meld:needs-human` | Needs a human before retry |
| `meld:challenged` | A CHALLENGE is open against it |
| `worker:<speciality>` | Role that owns it |
| `model:<id>` `effort:<level>` `size:S|M|L` | Set by the orchestrator, read by dispatch |
| `area:<x>` | Optional, product-defined |

- **The `meld:claimed-by:<group>` label is the claim lock** (plan 6b; before it the lock was the issue assignee, which an App's bot user can never be — probe 2026-09-09). One mechanism for every group, PAT and App alike. `meld claim` refuses if a `meld:claimed-by:*` label naming another party is present, ensures its own label exists (created on first use; `meld setup` cannot know group names), adds it, re-reads the issue, and treats any claim label set other than exactly its own as a lost race: it removes its own label and refuses without a `PROTOCOL-VIOLATION`. Two claimants can both lose and both retry; none can both win, so no tie-break is needed. A group's own stale claim label on a `ready` issue does not block its own re-claim (plan-6b decision 11): a PM killed between the label add and the status swap leaves `meld:ready` plus its own claim label, and on the next loop the add is a no-op, the re-read shows exactly its own label, and the swap proceeds — the crashed PM self-heals. Any other party's label still refuses. `meld release` reaches such an issue too (section 8), so an orphan claim is recoverable through `meld` rather than by hand-editing labels. Two claim labels on one issue (only possible after a crash between add and re-read) make it *contested*: nobody may dispatch it, either claimant may release, and its leases still expire, so `meld tick` clears it. A human claims with `meld:claimed-by:human` (one label for all humans; no group may dispatch a human-claimed issue). Issue assignees are neither read nor written by meld any more — humans may assign issues to people freely; the off-protocol sweep still reports assignee changes by strangers. Group names are therefore label- and path-safe by construction (`[a-z0-9][a-z0-9_-]{0,31}`, never `human`).
- **Issue bodies carry the declarations Python enforces** (plan 7). Under a `## Scope` heading the orchestrator (or a human) lists the globs a task may change, one `- ` bullet per glob (`fnmatch` semantics, as `PullRequest.touches`: `*` crosses `/`, so `src/*.py` is not shallow — it matches `src/a/b.py` too — and `**` has no special meaning of its own, `tests/**` being exactly `tests/*`); under `## May delete` the exact paths it may delete. `board.body_section` reads either list — bullets only, up to the next `## ` heading, backticks around an item stripped, and fenced code skipped, since a body that quotes a sample `## Scope` in a ``` fence is quoting it, not declaring it — and `Issue.scope`/`Issue.may_delete` are the typed result. Workers hold no credentials and cannot edit issues, so a declaration is the orchestrator's and the human's word, never the worker's. `meld tag N --scope GLOB --may-delete PATH` (both repeatable) writes those sections through `board.replace_section`, which rewrites an existing section where it stands, appends a missing one, and removes one given an empty list; blank and multi-line items are refused (`--scope and --may-delete require non-empty, single-line paths` — one declaration is one bullet), globs are otherwise unvalidated, and no CLI form *clears* a section — an omitted repeatable option means "not given", so a scope is removed by editing the body. `merge` refuses a PR that changes a file outside its issue's declared scope (`Board.scope_violations`) or deletes a file that issue does not list (`Board.blocked_deletions`): scope is opt-in per issue, the deletion gate is always on, a rename is not a deletion (GitHub reports it as `renamed`), and a memory PR closes no issue so neither applies to it. `meld status` shows both lists per PR before anyone tries to merge, and both worker briefs print the declaration — a build brief with no declaration at all still states the deletion gate in one line. Consequential actions are *held*: `meld:held:<category>` labels over a fixed vocabulary of seven (`board.HELD_CATEGORIES` — `cleanup`, `credential-change`, `delete`, `live-outreach`, `paid-media`, `production-mutation`, `public-release`), created by `meld setup` (a static list, unlike the claim labels) and matched case-insensitively like them. `meld tag N --held CATEGORY` posts a `NEEDS-HUMAN #N` naming the issue's full held set and then adds the held label together with `meld:needs-human` — the ask first, and for every actor, a human included: the labels are the gate and the ask is the stamp `Board.needs_human_answered` measures an answer against, so a hold with no ask behind it is one nothing can lift on purpose and any earlier answer lifts by accident, and a failed comment must leave no labels behind. Only a category the issue does not carry yet is posted and labelled, so re-tagging one it already has neither re-labels nor re-gates it. `dispatch` refuses the issue until a listed human answers `RESOLVED #N` (or `PROVIDED #N`) *after* that ask, the held labels stay as the record of that authority, and the worker brief names the authorized categories — a worker is never given held authority the human did not grant. Holding an `in_progress` issue whose build is already running makes that run collect as `superseded` (`meld:needs-human` outranks `meld:in-progress`, so `_collect_build` no longer sees its own claim): nothing of it reaches GitHub and the worktree is kept for inspection, which is the intended outcome — the authority question was raised after the work began. Fenced code (matched pairs of ``` lines) is skipped by both the reader and `meld tag`'s writer; an unterminated fence is inert, so a truncated paste can never make a scope vanish and fail open.
- **Pull request.** Branch `meld/<issue>-<slug>`. Body contains `Closes #<issue>` and a `verified-by:` line. Branch protection, as `meld setup` applies it (`setup.protect_branch`, the plan-5a decision accepted in PR #7): one approving review required (a GitHub backstop; the real quorum is enforced by `meld merge`), no required status checks — the `meld/review/<group>` commit statuses stay informational, and a human may add product CI checks as required ones — no push restrictions, so any reviewer can push to a PR branch, and admins not enforced. `meld merge` always merges by squash.
- **Decision and memory files.** `.meld/decisions/NNNN-<slug>.md`, `.meld/memory/lessons.md` in the product repo (section 15).
- **Worker comments.** The framework posts exactly two comments per worker run on its issue: start (worktree, model, effort, size) and finish (commit range, outcome, `verified-by:`). Workers themselves post nothing.

## 7. Coordination grammar

Every coordination comment starts with one header line:

```
[<party>] <VERB> [<ref>] [<qualifier>]
```

- `<party>` is a group name, `<group>:pm`, `human`, or `joint`. `joint` may only be written by `meld` after quorum is verified.
- Comments from accounts that are not a configured bot or an allow-listed human are ignored by the parser and flagged once, in their own `IGNORED-COMMENT` comment posted by `meld tick`. This is the prompt-injection defense for the channel.
- Malformed headers are ignored and logged, never fatal.

Verbs:

| Verb | Written by | Purpose |
|---|---|---|
| `ROSTER`, `ROSTER-CHANGE` | group | Inventory of worker types available to that group |
| `CONFIG` | group | Running models and efforts for orchestrator and PM |
| `PROPOSE`, `AMEND`, `AGREE`, `DISSENT` | group | Agreement protocol rounds on a referenced item |
| `PLAN`, `PLAN-ADD` | joint | Agreed decomposition; additions mid-milestone |
| `ASK`, `DIRECTIVE`, `AMEND`, `APPROVE`, `ACK`, `PROVIDED`, `RESOLVED`, `HALT`, `RESUME`, `REVERT`, `RELEASE`, `NEEDS-HUMAN` | human | Human inputs |
| `DRAFT`, `AGREE`, `AMEND` | group | Chat deliberation on an `ASK <id>` |
| `ANSWER` | joint | Agreed reply to an `ASK`; qualifier `DISAGREE` when no majority |
| `REVIEW-REQUEST #<pr>` | group:pm | Ask other groups to review |
| `STATUS` | group:pm | Periodic summary; leads with needs-human and budget |
| `NEEDS-HUMAN #<issue>` | group, group:pm, or human | A blocking ask to the human. A human writes it too — `meld tag --held` run by a human posts its own, and it is how a person re-gates an issue they have already answered (section 14) |
| `BUDGET [budget-<n>]` | group or group:pm | A blocking ask to the human; a `BUDGET` that carries a `budget-<n>` ref is cleared by the human's own non-`ASK` comment on that ref (section 14) |
| `CHALLENGE <ref>`, `EVIDENCE <ref>`, `RETRACT <ref>`, `UPHELD <ref>`, `DISMISSED <ref>` | group or human | Hallucination protection (section 14); posted only through `meld challenge`, which applies or clears `meld:challenged`; `meld post` refuses them |
| `AUDIT <ref>` | group or group:pm | Independent audit findings |
| `DRIFT` | group | Plan drift |
| `DECISION <id>` | joint | Agreed decision, mirrored to a file |
| `PROPOSE-WORKER <name>` | group or group:pm | New worker type proposal with draft prompt |
| `WORKER <name>` | joint | Agreed new worker type, closing a `PROPOSE-WORKER` round |
| `PING`, `SOLO`, `RESUMED`, `LIMITED`, `PROTOCOL-VIOLATION` | group or group:pm | Liveness notices, and enforcement: `LIMITED` is posted by the **supervisor**, not by a role -- a role that hit its subscription's usage limit is already gone, so nothing it could post survives (section 17); it carries the reset instant when the CLI named one, and the role's own `RESUMED` on relaunch closes the pair. Otherwise: `PROTOCOL-VIOLATION` is posted either by the party whose illegal `meld` call was refused (naming the broken rule, section 8), or by a PM's `meld tick` naming a label or assignee change on a milestone issue made by an actor that is neither a configured bot nor a listed human (section 17) |
| `LEASE #<issue>`, `EXPIRED #<issue>`, `RELEASED #<issue>` | group:pm or group, framework-posted | A build's claim lease, its expiry, and the release that voids it (section 11), written only by `meld dispatch`, `meld claim`, `meld tick`, and `meld release`; `meld post` refuses all three for every caller |
| `IGNORED-COMMENT` | group:pm, framework-posted | Flags comments from accounts outside the configured bots and humans, counted as `coordination.ignored_comments` in `meld status`; posted by `meld tick` — only the alphabetically first configured group's PM, so a stranger's comment is flagged once rather than once per group; framework-posted, `meld post` refuses it |

`RETRACT` may come from the challenger (withdrawing the doubt) or the challenged party (conceding the claim); `UPHELD` and `DISMISSED` are for a party that is neither.

Required fields by verb are enforced by the parser: `PLAN`, `DECISION`, `ANSWER`, `EVIDENCE`, and every worker finish comment must carry a `verified-by:` line naming a command run, test executed, or URL read. Missing it makes the comment invalid.

**Ref conventions.** `ask-<n>` and `dir-<n>` are assigned by `meld chat` itself — the next unused number for that prefix among comments already on the board — for `[human] ASK` and `DIRECTIVE`. `plan-<milestone>`, `plan-add-<n>`, and a decision id (conventionally `dec-<n>`) are not generated by any code: the proposing orchestrator picks the string when it opens the `PROPOSE`/`DRAFT` round, and that same ref is carried through `AGREE`/`AMEND`/`DISSENT` to the `[joint]` comment and on to `meld plan issues`/`meld decide`. `budget-<n>` is picked the same way: the PM prompt tells a PM refused for an exhausted budget tier to post `BUDGET budget-<n>` with the next free number, so the human can answer that one ref.

### Agreement protocol

Used for `PLAN`, `PLAN-ADD`, `DECISION`, `ANSWER`, and `PROPOSE-WORKER`. Each round closes with the
matching joint verb; a `PROPOSE-WORKER <name>` round closes with `WORKER <name>`, not with a joint
`PROPOSE-WORKER` (there is no such joint verb).

1. One group posts `PROPOSE <id>` (or `DRAFT <id>` for chat) with full text.
2. Every other group posts `AGREE <id>` or `AMEND <id>` with edited full text. An amend restarts the round with the amended text as the proposal.
3. When every group has agreed to the same text, the proposing group runs `meld post --joint <VERB> <id>`, which verifies the agreement on GitHub and writes the `[joint]` comment. Nothing else may write `[joint]`.
4. A `DISSENT` counts as a cast vote rather than leaving the round open, so the outcome is decided as soon as every group has either agreed or dissented — not when a round cap expires. With a strict majority, the majority text is posted as `[joint]` with a `DISSENT` section listing minority positions; with no majority (including any 2-group tie) the item is posted as `[joint] <VERB> <id> DISAGREE` containing all positions, and the human decides.
5. `agreement.amend_cap` bounds only the number of `AMEND` and re-proposal rounds. Once it is reached, a group must post `AGREE` or `DISSENT` instead of amending again; it does not by itself decide the outcome. A group that dissented is not locked in: a later `AGREE` from that group supersedes its dissent, as an `AMEND` by any group restarts the round.
6. The `[joint]` comment carries the agreed text verbatim. A caller may add its own note, which is appended under an `## Addendum` heading; it never replaces the agreed text. A ref that already has a *verified* `[joint]` comment cannot get a second one, and a later `[joint]` posted anyway is ignored by the agreement computation, so nothing hand-written can flip a closed ref back to unverified (`grammar.agreement_for`; plan-5 decision 1). An unverified one (written by anyone but the proposer's bot, or before the round closed) does not block the proposer's, which then supersedes it — until a verified `[joint]` exists, the latest one on the ref is the one that counts.
7. **Any `[joint]` comment freezes the round.** Once a `[joint]` comment exists on a ref — verified or not — later `PROPOSE`, `DRAFT`, `AMEND`, `AGREE`, and `DISSENT` comments on that ref are ignored by the agreement computation and refused by `meld post` ("`<ref>` is closed by a `[joint]` comment; open a new ref"). Without this, an `AMEND` posted after a verified `[joint] DECISION` rewrote the round's text and made the amender its proposer under a joint comment that still read as verified — and `meld decide` recorded it. A round that genuinely needs reopening gets a new ref.
8. **A `DISAGREE` round is never recorded.** `[joint] <VERB> <id> DISAGREE` lists the positions for the human; `meld decide` refuses it and the memory-PR verifier requests changes on a decision PR for it ("`<ref>` ended in DISAGREE; the human decides").

## 8. Issue lifecycle and legal actions

```
planned ──human APPROVE──▶ ready ──claim──▶ in-progress ──PR opened──▶ in-review ──quorum + CI──▶ merged
                             ▲                 │                          │
                             └────release──────┘                          └─changes requested─▶ in-progress
                                               │
                                               └─worker fail / timeout / pingpong cap─▶ blocked ─▶ ready | needs-human | closed
merged ──AUDIT reopen──▶ ready
```

Two milestone-level states sit above this: `planning` until `meld:plan-approved` is on the coordination issue, then `executing`. `HALT` overlays either and freezes `claim` and `dispatch` for every group until `RESUME`.

`rules.py` computes, for a board snapshot and a calling party, the set of legal verbs per issue and per PR. Every rule below is a test.

- **claim**: caller is a PM or a human; milestone is `executing`; issue is `ready`; no `meld:claimed-by:*` label naming any party but the caller — the caller's own stale label (left by a crash between `claim`'s label add and its status swap) does not block its re-claim, while another party's label refuses naming every claimant, so a contested `ready` issue refuses everyone; caller's roster contains the issue's `worker:` label; caller's count of `in-progress` issues below `concurrency`; caller's budget tier for the issue's model not exhausted; no `HALT`.
- **dispatch**: caller is a PM; the issue's single `meld:claimed-by:` label names the caller's group (a contested issue, two labels, is dispatchable by nobody); no live run record for the issue; `model`, `effort`, `size` labels present and valid for the caller's adapter; `size` compatible with the model's context class; issue not `needs-human` or `challenged`; not a retry at the unchanged `model` and `effort` after a build run the group collected as `failed` (plan 16: the section 9 rubric's "raise effort a level or move up a tier", enforced; a retry after `request-changes` or a human's answer is not refused); a `meld:held:<category>` label refuses dispatch (naming every held category on the issue) until a listed human has posted `RESOLVED #<issue>` or `PROVIDED #<issue>` *newer than* the newest `NEEDS-HUMAN #<issue>` — an ask must exist, so a `meld:needs-human` label with nothing behind it never auto-unlocks and an issue answered once in the past is not thereby authorized for a hold added later (`Board.needs_human_answered`, comparing comment ids; plan 7: held categories); no `HALT`.
- **release**: caller's group holds a claim label on the issue (or is a PM and the holder's lease expired), or the caller is human; issue in `in-progress` or `blocked`, or `ready` while it carries a claim label — a claim that never reached `in-progress`, which is what a crash between `claim`'s label add and its status swap leaves behind. The refusal names that case: `issue is <status>; release is only legal from in-progress or blocked, or from ready with a stale claim label`. Release removes every claim label present, so releasing a stale `ready` claim returns the issue to a claimable state (it is already `meld:ready`; nothing else changes). `--force` is human-only and posts a note.
- **review approve**: caller's group did not author the last commit on the PR head; the caller is not the PR's author party; PR not `challenged`; the head committer is known. The author-party clause is GitHub's rule, not ours: GitHub returns 422 when the account that opened a PR submits an `APPROVE` or `REQUEST_CHANGES` review on it, and Meld's PR author is the author group's bot. So after another group push-fixes the head (section 13 step 3) the author group's approve or request-changes is refused as a GitHub verb, and `meld review` posts it as a `COMMENT` review whose first line names the verdict, with the `meld/review/<group>` commit status on that head as the record (`rules.review_verdict_rule` is the legality `meld review` applies: PR open, the author is not the head committer, the head committer is known, and no open challenge for an approve). Since plan 5 that is also the rule `meld status` reports: `legal_pr_verbs` computes `approve` and `request-changes` through `review_verdict_rule` — through `memory_review_rule` for a memory PR — while `pr_refusal` stays strict, so a PR's `legal` array no longer calls `approve` illegal at the moment `meld review` would accept one. The author group's request-changes carries a `meld-verdict:` marker as the COMMENT review's first line (`board.AUTHOR_VERDICT_MARKER`), which `assemble` reads back as a `CHANGES_REQUESTED` review flagged `as_author`, so it counts toward `review.pingpong_cap` like any other. Request-changes is legal for any party that is neither the head committer's nor the author's; push-fix is legal for any non-author-of-head group, including when the head committer is unknown, because it approves nothing. Push-fix by group X makes X the last committer. A last commit that maps to no GitHub account leaves the head committer unknown and refuses approve, rather than falling back to the PR author.
- **merge**: approvals on the current head from at least `min(review.quorum, N-1)` distinct groups -- `N` the groups that have spoken on this milestone's coordination thread (`rules.participating_groups`; every configured group until one has), since plan 29, because a group configured but never started is not a reviewer anyone can wait for -- none of which authored the head, with human approvals counting as a group; the author group counts when it is not the head committer and its `meld/review/<group>` status on the current head is `success`, since its approval can never be a GitHub review (see review approve); required checks green; no open `CHALLENGE` on the PR; the head committer is known, since the non-committer rule cannot be evaluated without it; when the PR closes an issue whose body declares a `## Scope`, every changed file matches one of its globs, and whenever the PR closes an issue, every file it deletes is listed under that issue's `## May delete` (plan 7: write scope and the deletion gate — both checks run last, after the quorum and the checks, and each refusal names up to the first five offending files; a memory PR closes no issue, so neither reaches it); no `HALT`. Either group's PM may call it.
- **reopen**: an `AUDIT` comment with a `fail` finding naming the issue exists and was posted by the caller's group; the issue is closed; that `FAIL` is newer than the issue's last close (`closed_at`), because a `FAIL` speaks about the close it followed and a later close is work it never judged (plan 12 — the first live run reopened two issues whose fixes had already landed); the caller's group did not author the PR that closed it. Returns the issue to `ready` with the findings attached.
- **collect**: caller is a PM and the run record is that group's own — a build it dispatched, or the review or audit it requested — whose process has exited and has not been collected. The claim itself is not part of the legality (`rules._collect`); a build whose issue has left `in-progress`, or whose claim has moved to somebody else, is instead collected as `superseded` (`dispatch._collect_build`): the worktree is detached for inspection and nothing of the run reaches GitHub.
- **post**: always legal for any party, except `--joint`, which requires verified agreement. A `PROPOSE` or `DRAFT` on a ref that already has proposal text is refused; a re-proposal after that point is an `AMEND` and counts a round. Refusals here come in two kinds. A **rule-level** refusal — no agreement yet, caller is not the proposer, wrong milestone phase, a ref that already has a verified `[joint]` comment, an agreement verb on a ref that a `[joint]` comment has closed (section 7), a re-proposal on an active ref, the amend cap reached — posts `PROTOCOL-VIOLATION` like any other illegal call. A **usage error** — a verb the party may not post, a human writing `[joint]`, `--joint` without a ref, a missing ref or `verified-by:` line, `DISAGREE` without the qualifier — is the caller's own mistake, reaches no other party, and posts nothing.
- **plan**: `plan issues` is legal for the proposer group's orchestrator given a verified `[joint] PLAN` (refused once the milestone has left `planning`, since that plan's issues already exist) or `[joint] PLAN-ADD` (legal in any phase). It parses the referenced text as the item format (plan-4 decision 4: `- id: <slug> | title: <text> | worker: <w> | model: <m> | effort: <e> | size: <S|M|L>` plus indented `  - <criterion>` lines), skipping and reporting a malformed line and skipping (not recreating) an id that already backs a `meld:planned` issue; `--dry-run` parses and reports `would_create` without creating anything. `plan approve` is legal for a human only, while the milestone is still `planning`, given a verified `[joint] PLAN` on `plan-<milestone>`; it adds `meld:plan-approved` to the coordination issue and flips every `meld:planned` issue to `meld:ready`. `plan ack` is legal for a human only, given a verified `[joint] PLAN-ADD` on the ref; it posts `[human] ACK <ref>` — skipped, idempotently, if already posted — and flips that addition's own planned issues to `meld:ready`.
- **decide**: legal for the agreement's proposer (that group's orchestrator or PM) given a verified `[joint] DECISION` on the ref whose round ended `agreed` or `majority` (a `DISAGREE` round is refused: the human decides), unless the ref is already recorded — an open or merged memory PR for it on the board (plan 12; a merged one is how `meld status` knows without reading origin), or its file already present on origin's default branch. Writes `.meld/decisions/NNNN-<slug>.md` from the agreed text, linking the verified `[joint]` comment itself as `- Source:` (never an earlier hand-written one), opens a memory PR carrying a `meld-memory: decision <ref> <sha256>` body marker, and posts `REVIEW-REQUEST` naming it a memory PR.
- **remember**: legal for any group's orchestrator or PM once `ref` (an issue or PR number already on the board) is neither `blocked` nor `needs_human`, carries no open challenge, and has no lesson yet — a ref whose lesson is recorded or in flight (an open or merged memory PR whose marker names `lesson <ref>`, `rules.recorded_lesson`) takes a second `remember` only with `--supersedes`, so `lessons.md` carries one current entry per item instead of several takes on it, each a PR, a review and a merge (plan 44: the scratch product's PM recorded five lessons from one issue in a day); the refusal names the earlier PR and says to supersede — there is no agreement round to verify, since a lesson records what already happened rather than proposing anything. Appends an entry to `.meld/memory/lessons.md` through the same memory-PR machinery, marker `meld-memory: lesson <ref> <sha256>`.

`meld status` lists, per agreement ref, what the caller may post on it now (`rules.agreement_post_verbs`, plan 47: `propose` while there is no text, `amend` under the cap, `agree` and `dissent` on text the caller has not agreed to, `joint` for the proposer once the round has agreed and no verified `[joint]` closes it) ahead of the `decide`/`plan-*` actions, under the same conditions `meld post` enforces, so a role never reads an empty `legal` on an open round as "I may not answer" (the first real run's codex orchestrator did, and asked the owner why). A `[joint]` comment is *verified* only when it was written by the proposer's own bot after the round reached `agreed`, `majority`, or `disagree` (`Agreement.joint_verified`, alongside `joint_verb`, `joint_author`, and `joint_comment_id`; `grammar.verified_joint` returns that comment, and it is the one `decide` links and the verifier re-renders from); `meld status` shows both that flag and the round `status` per ref under `coordination.agreements`. `plan`, `decide`, and `remember` refuse through the same `Refusal`/`PROTOCOL-VIOLATION` path as every verb above, and since plan 5 their legality lives in `rules.py` with everything else: `remember_rule` puts `remember` in `ISSUE_VERBS` and `PR_VERBS`, so it appears in each issue's and PR's `legal` array, and `decide_rule`/`plan_rule` feed `legal_agreement_verbs`, which fills a per-ref `legal` array under `meld status`'s `coordination.agreements` with `decide`, `plan-issues`, `plan-approve`, and `plan-ack`.
- **review** (dispatch a review run): caller is a PM; PR open; caller's group is not the head committer's; PR not challenged; no `HALT`; within `review_concurrency`; no live or uncollected run on the PR.
- **audit** (dispatch an audit run): caller is a PM; PR merged and not a memory PR (its content was verified against the board at review, and `audit.pending` omits it too); caller's group did not author it; caller's group has not audited it; no `HALT`; within `review_concurrency`.
- **reap**: caller is the PM whose collected, dead run it is; a build once its issue is closed or its PR merged or closed; a review or audit run once collected.
- **tag**: caller is the orchestrator or a human; issue open.
- **challenge**: acted on by an orchestrator or a human only (PMs may not open, answer, or decide challenges). Open by any orchestrator or human but the claim's own party; `EVIDENCE` by the challenged party's orchestrator (or a human); `RETRACT` by the challenger or the challenged party's orchestrator (or a human); `UPHELD`/`DISMISSED` by an orchestrator of a group that is neither (with two groups, the human).

`meld status` lists `review`, `audit`, `reap`, `tag`, and `remember` under each issue's or PR's `legal` array — and, since plan 12, every other issue or PR verb under a `refused` map beside it, each with the rule that keeps it out, computed from the same table (`rules.issue_verb_rules`/`pr_verb_rules`) so a verb is never missing from `legal` without saying why — and `decide`/`plan-issues`/`plan-approve`/`plan-ack` per agreement ref; `challenge` legality is not surfaced there — call `meld challenge` and read its refusal (or the lack of one), or watch `coordination.challenges` for what is currently open.

Illegal calls return a refusal naming the rule and post `PROTOCOL-VIOLATION` on the coordination issue so other groups and the human see it. Two cases are refusals without a violation: a **lost claim race**, which is first-label-wins working as designed rather than an illegal call, and any refusal of a human, who answers to nobody on the board. The refusal JSON therefore reports `violation_posted` as `true`, `false` (posting it was attempted and failed), or `null` (none was attempted).

## 9. Roles

All roles are headless runs. Per group, two are long-lived and one is short-lived.

**Orchestrator** (long-lived, restarted every `runners.restart_hours`). Loop: `meld wait` filtered to coordination comments, chat, blocked and needs-human issues, roster changes, and drift; act; repeat. Responsibilities: decompose the goal into issues; tag each with `worker`, `model`, `effort`, `size` via `meld tag` using the rubric; negotiate with other orchestrators; answer human chat via the agreement protocol; resolve blocked issues; re-tag on retries; propose worker types when the roster has a gap; post `ROSTER`, `CONFIG`, `DRIFT`. It never writes product code and never dispatches.

**PM** (long-lived, same restart schedule, sibling process). Loop: `meld tick` first each cycle (timeouts, leases); `meld wait`; act; repeat. Responsibilities in `executing` only: claim `ready` issues up to the cap; dispatch with the tagged model and effort; `collect` finished workers; reap merged ones; move labels; post `REVIEW-REQUEST`; dispatch reviewers for other groups' requests; dispatch auditors after merged batches; call `merge` when legal; post `STATUS` on cadence, leading with needs-human and budget; auto-approve decision PRs whose file is byte-identical to `meld decide`'s rendering of the verified `[joint] DECISION`, and lesson PRs that append exactly one entry about a resolved item (a lesson has no agreed comment; section 15). It never chooses models. If it disagrees with a tag it posts to the coordination issue and the orchestrator re-tags.

**Workers** (fresh run per task). Day-one roster: `backend`, `frontend`, `security`, `qa`, `reviewer`, `auditor`, `docs`. A worker prompt is a role brief plus the fixed contract: read `.meld-brief.md` first; work only in this worktree; commit small; run the product's tests; write `.meld-result.json` (outcome, summary, `verified-by`, for reviewers a verdict) and exit. Workers have no GitHub credentials and never push, open PRs, comment, label, or merge. The framework does all of that from the result file.

Orchestrator and PM keep no state that is not also on GitHub. Restarting them is always safe, and it never touches running workers, which are independent processes tracked by run records.

### Model and effort selection rubric

The orchestrator prompt carries the rubric as a table with three worked examples. Inputs: task type, blast radius (files and systems touched), ambiguity, first attempt or retry. Outputs: `model`, `effort`, `size`. Rules the rubric states plainly: read `meld models` before tagging; there is no `XL`, split instead; on a retry after failure or changes-requested, step effort up one level or move to a stronger model before trying the same approach again; prefer the cheapest tier whose context class fits the size. The rubric is a prompt and tunable without code. Validity and budget are code.

## 10. Roster

`meld roster` returns worker types available to the calling group, with a one-line description each, from four sources: framework built-ins; the product repo's `.meld/workers/` (a same-named file overrides a built-in); the product repo's own skills under `.meld/skills/<name>/SKILL.md`, shared by every group (source `product-skill`, `name` and `description` from the file's frontmatter); and the skills and plugins installed for the group's CLI on the machine (adapter-provided). A product skill wins over a same-named host-installed one, but never over a worker: a `SKILL.md` whose frontmatter `name:` collides with a built-in or product worker is dropped entirely, so a role prompt can never be silently replaced by a skill.

- At start, each orchestrator posts `ROSTER` and `CONFIG` in its opening comment.
- On every restart and every `roster_refresh_minutes`, it re-runs `meld roster`, diffs against its last posted inventory, and posts `ROSTER-CHANGE` on any difference.
- `claim` checks the issue's `worker:` label against the caller's roster.
- The PM reads `meld roster` before each dispatch, never from cache. When a new type better matches a `blocked` or `ready` issue, it suggests re-tagging.
- **Skills in a brief.** A brief does not carry the whole roster: `brief.select_skills` lists the skills the orchestrator pinned with `skill:<name>` labels (`meld tag --skill <name>`, repeatable, refused for a name that is neither an installed nor a product skill) first, then every skill whose name or description shares a term with the issue's or PR's own title and body, best score first and capped. Unmatched skills stay out.
- **Skills in the worktree.** At dispatch, every rostered product skill is copied into the worktree under the launching adapter's project skill directory — `.claude/skills/` for Claude, `.agents/skills/` for Codex (`Adapter.project_skills_dir`) — and each copied skill directory (plus the manifest below) is added to the clone's shared `info/exclude` by its own exact path — never the skills directory itself, which is shared with every other worktree and with the PM's checkout, where a worker's or a human's own new project skill must stay visible to git. Those are the directories each CLI reads a *project's* own skills from (plan-5 decision 14), so nothing has to be written under the host's home directory and a worker cannot commit the copies. The copy is idempotent across a reused worktree through a `.meld-materialised.json` manifest of the names written last time (only a name that manifest holds is ever pruned as stale); a destination the product itself tracks in git is left alone and reported as skipped; and no filesystem failure there can fail a dispatch. A worker whose CLI cannot invoke a skill by name is told by the worker contract to open the `SKILL.md` at the path the brief prints — for a product skill that is the copy in its own worktree, not the file in the PM's clone. A `SKILL.md` that is a symlink is not scanned at all, and symlinks inside a skill directory are dropped from the copy, so nothing outside the skills tree is read into a brief or written into a worktree.
- Gap detection during decomposition triggers `PROPOSE-WORKER`, which follows the agreement protocol, then a `docs` worker is dispatched to write `.meld/workers/<name>.md` and `collect` opens the PR. That PR requires a human approval via CODEOWNERS on `.meld/workers/` in addition to the review quorum. Proposals made during `planning` ride with plan approval instead.

## 11. Dispatch and worker runtime

`meld dispatch <n> [--kind review|audit]` (`<n>` is a PR number for reviewer and auditor runs):

1. Re-check legality (section 8).
2. Create a worktree from the default branch at `$MELD_HOME/worktrees/<group>/<issue>-<slug>` on branch `meld/<issue>-<slug>`; a retry whose worktree is still on disk reuses it as-is, otherwise a pushed remote branch is checked out instead of branching fresh from the default branch — **unless a PR from that branch has already merged** (plan 40): then the worktree and local branch are discarded and the branch starts over from the default branch, because its old commits are on the default branch as one squash commit and a PR that continued them conflicted with the squash of itself (the scratch product's PR #9); `collect`'s push then rewrites the stale remote branch with `--force-with-lease`. On every retry that is not such a fresh start, `dispatch` runs a local `git merge-tree` against the freshly fetched default branch and the brief gets a `## Merge conflicts to resolve first` section naming the files, since a worker holds no credentials and cannot read the PR's conflict on GitHub. A retry after a `NEEDS-HUMAN` carries `## The person answered` (plan 53): the last ask the issue raised and the answer to it, from a listed human or from the asking group withdrawing it (`dispatch.person_answer`), so the worker acts on what was said instead of asking again. And every build brief carries `## Where you run` when the CLI's adapter has something to say about its sandbox (`Adapter.worker_notes`): a Codex worker is told its `workspace-write` sandbox cannot launch a browser or any GUI process, to verify what it can, finish `done` with the browser-only checks listed as unverified, and never report `blocked` for a browser, since the reviewing group's worker runs without that sandbox; the orchestrator's rubric routes work whose acceptance needs a browser to a group whose workers can launch one, or leaves those checks to the reviewer. The first real run's codex worker blocked twice asking a person to run browser checks, and the retry read nothing of the answer. And `## What you cannot push` (plan 62) when the group's GitHub App lacks a permission a push can need: without Workflows: write, a branch that creates or edits a file under `.github/workflows/` is refused on push, so the worker is told not to touch workflow files and, if the task needs one, to finish `blocked` naming the change (`dispatch.push_limits` over `AppAuth.permissions`); the maze's #4 worker edited a workflow file, GitHub refused the push, `collect` failed twice and a person was asked. A worktree registration whose directory was deleted ($MELD_HOME is disposable) is pruned and recreated. Reviewer and auditor runs check out the PR head instead.
3. Materialise the product's skills into the worktree and render `.meld-brief.md`: role prompt, the fixed contract, issue body, the plan excerpt for this issue, file hints from the orchestrator, relevant decisions from `meld recall` (section 15), the skills matched to this task with their paths (section 10), and the product's agent-instruction file path. Not the whole plan, not the coordination thread.
4. Spawn the headless run via the adapter — a build uses the issue's tagged model and effort, a reviewer or auditor run uses the group's orchestrator model and effort — non-interactive, cwd set to the worktree, wall-clock timeout from `size`. The environment is scrubbed of tokens and party identity and carries the group's bot as git author and committer (`GIT_AUTHOR_*`/`GIT_COMMITTER_*`; never `git config` in the worktree, which would write the clone's shared `.git/config`), `GH_CONFIG_DIR` pointed at an empty per-run directory, git credential helpers reset, and `GIT_TERMINAL_PROMPT=0`. Filesystem scope is whatever the adapter provides: the Claude adapter runs `--permission-mode bypassPermissions`, so its isolation is exactly this environment; the Codex adapter runs `-s workspace-write` (section 18).
5. Write the run record `$MELD_HOME/runs/<group>/<issue>.json` (PID, start, worktree, log path, model, effort) and post the start comment.
6. Return immediately.

**Leases**: dispatching a build also posts a `[<group>:pm] LEASE #<issue>` comment on the coordination issue, whose `until` is the worker's deadline plus `lease.grace_minutes`. No per-cycle renewal is needed: `meld tick` fills in a lease that is missing for one of the calling group's own live runs, and releases any other group's lease whose `until` has passed, posting `[<group>:pm] EXPIRED #<issue>` and returning that issue to `ready`. A release ends the lease structurally rather than by convention (plan-5 decision 2): `meld release` posts a framework-only `[<party>] RELEASED #<issue>` comment when the caller is a group or a PM, and `derive_leases` drops the lease on `RELEASED` exactly as it does on `EXPIRED` or a human's `RELEASE` — so a same-group re-claim can never revive the old lease, and a stale `LEASE` never reaches across a release into the next claim. (`dispatch.tick` suppresses that comment with `announce=False` when it is about to post its own `EXPIRED` naming the lease that expired: one event, one framework comment.) A lease also counts only while the leasing group holds a claim label on the issue (`board.held_leases` drops any other lease when the board is assembled), which covers the release paths that post nothing; on a contested issue each claimant's lease survives, so the ordinary expiry path can still clear it. `LEASE`, `EXPIRED`, and `RELEASED` are written only by `meld dispatch`, `meld claim`, `meld tick`, and `meld release`; `meld post` refuses all three for every caller, so a lease cannot be forged.

**An attempt budget per issue** (plan 55): a build run carries `attempt`, carried over from the previous build record on the issue for that group (a capacity stop is a pause, not an attempt), and `dispatch` is refused once a failed or blocked build has reached `budget.attempts_per_issue` (default 3), naming the cap and telling the PM a person decides; the maze run ran seven builds on one issue, the last three at max effort on the largest model. A listed human's `RESOLVED` or `PROVIDED` on the issue after that build is the decision (plan 60): `dispatch` is legal again and the next build's `attempt` starts at 1 (`Board.answered_since`); the maze's #4 hit the cap on three builds that all ran before its dependency merged, and nothing let a person clear it. The role prompt lists each roster entry on one line (`roster.brief`: the first sentence, at most 120 characters) and `meld roster` prints the same unless `--full`, so the prompt and the ROSTER post stop carrying 24k characters of skill descriptions. **Post-run**: `meld status` reports a run as `finished` once its process has exited. The PM then calls `meld collect <issue>`, which does all side effects: read `.meld-result.json`; if commits exist, push the branch and open (or update) the PR with `Closes #<issue>` and the `verified-by:` line (GitHub closing keywords inside the worker's own text are neutralised, so only that line can close an issue); post the finish comment; move the issue to `in-review`. If the issue is no longer `in-progress`, or its `meld:claimed-by:` label no longer names the group alone, when `collect` runs (its lease expired and another group re-claimed it, a human released it, or the issue is contested — `dispatch._collect_build` reads `Issue.claimed_by`, which is `None` while two claim labels are present), the run is recorded as `superseded`: nothing is pushed or posted, and the worktree is kept for inspection. A retry on the same issue archives the previous run record, so every run counts against the budget. For reviewer and auditor runs, `collect` instead writes the verdict to `$MELD_HOME/results/<group>/<kind>-<n>.json`, tagged with the PR's `head_sha` at dispatch time (head SHA, whether it timed out, the worker's result, and the log tail), and marks the run collected; a second collect that finds an unconsumed verdict there moves it aside to `superseded/` rather than overwriting it. `meld review` and `meld audit` read that file to act on it — submitting the review (approve, request-changes with the worker's comments, or push-fix which pushes the reviewer's commits and requests re-review from the author group) or posting `AUDIT` and, on a `fail` finding, calling `reopen` — then move the consumed file to `submitted/`. A review verdict whose stored `head_sha` no longer matches the PR's current head is stale: `meld review` refuses to submit it and reports so instead of acting on stale intent; re-dispatch a fresh review.

**Failures**: exit without a result file, or a result with outcome `failed`, moves the issue to `blocked` with the last 50 rendered log events posted (`[logs]`/`worker.log_tail_lines`, section 22). A timeout kills the process, keeps the branch, and does the same. `meld reap` removes the worktree and archives the record after merge or close.

## 12. Polling

`meld wait [--timeout S] [--interval S] [--filter <kinds>]` blocks until the board changes or the timeout elapses, then returns the `meld status` JSON plus a `changes` list. `--filter` takes a comma-separated subset of the change kinds — `phase`, `halted`, `issue`, `pr`, `run`, `comments`, `human`, `challenges`, `audits` — and only those kinds count as a change; omitted, every kind does. `human` (plan 63) fires on a new post by a listed human (`board_digest.last_human_comment_id`; a snapshot from before the key never fires it), so a PM whose own `NEEDS-HUMAN` is open waits with `--filter human,issue,pr,run` and is not woken by the other group's `PING` or `STATUS` about the wait. `challenges` fires on any change to a ref's challenger (a `CHALLENGE` opening, closing, or being replaced by a different challenger on the same ref); `audits` fires on any new or changed `AUDIT #<pr> PASS|FAIL` verdict, per group per PR; `pr` fires on a new head, a change in approvals, changes-requested, checks, or state, *or* a change in commit statuses — so the author group's `meld/review/<group>` status flipping to `success` after a push-fix (section 13 step 3) fires `pr` too, not only a fresh GitHub review. An initial snapshot (no prior state to diff against) always counts, filter or not. Inside, every `polling.interval_seconds`:

- Fetch coordination comments newer than the stored cursor (`since`).
- Fetch open issues in the active milestone with labels (the claim lock is a label; assignees are not read), open PRs on `meld/` branches with reviews and check status.
- Read this group's run records and check whether each PID is alive.
- Diff against `$MELD_HOME/state/<group>/<role>/snapshot.json`; return on any change. The snapshot is **per party** — a group's orchestrator, that group's PM, and the human each keep their own — because both roles of a group poll the same board and a shared snapshot would let whichever polls second consume the other's changes. The conditional-request ETag cache is **per group**, at `$MELD_HOME/cache/<group>`, since both roles authenticate with the same token; it is written atomically and a corrupt entry is treated as no cache.

Three or four conditional API calls per cycle, roughly 400 requests an hour idle against a 5,000 per hour per-token limit. Rate-limit responses trigger exponential backoff and are reported in the returned JSON. Handoff latency is bounded by the interval, about 30 seconds; the timeout only bounds idle re-reads. The wait timeout stays below the calling CLI's command timeout by construction (adapter reports its ceiling; `meld doctor` verifies). `meld claim` re-reads the issue with the ETag cache bypassed before deciding the race.

## 13. Cross-review and merge

For a PR opened on behalf of group A's worker:

1. A's PM moves the issue to `in-review` and posts `REVIEW-REQUEST #<pr>`.
2. Every other group's PM dispatches a `reviewer` (under `review_concurrency`, exempt from the build cap); with three or more groups, `review_concern` gives every reviewing group but the head committer's a different primary concern — correctness and security, tests and product conventions, or architecture, performance, and visual design — in rotation by group name (section 21 item 3; with two groups there is one reviewer, so no concern is assigned). When the PR touches `review.security_paths`, the same PM also dispatches a `security` reviewer, sequentially once its first review is submitted: a run record is keyed by PR number, so two live review runs cannot coexist on one PR. A group also gets one review slot per head — two when the PR touches `review.security_paths` — and its submitted verdict is what spends it, counted from the verdicts its bot has posted on that head (the author group's marked `COMMENT` verdicts included): `meld dispatch --kind review` of a head the group already reviewed is refused and `meld status` stops listing `review` for it, until a new head appears or a human dismisses the stale verdict (section 21 item 31; GitHub dismisses only `APPROVED`/`CHANGES_REQUESTED` reviews, so the author group's marked `COMMENT` verdicts wait for a new head).
3. Each reviewer ends in approve, request-changes, or push-fix, submitted by `meld review`. Approve or request-changes posts a GitHub review plus a `meld/review/<group>` commit status (`success` or `failure`) — a personal token cannot create a check run, so this is the neutral signal section 21 item 4 asked for. A group authenticating as a GitHub App additionally publishes a neutral `meld/review/<group>` check run beside that status (a real one, since an installation token can create it); it is a visible echo only — the quorum reads the commit status and nothing else, for App and PAT groups alike, and a check run that fails to post is recorded as `check_run_error` without failing the review. Request-changes also returns the issue to `in-progress` for the author group, or to `blocked` once `review.pingpong_cap` request-changes reviews have accumulated on the PR. Push-fix pushes the reviewer's own commits from its review worktree, posts a `pending` status, makes the pushing group the last committer, and posts a new `REVIEW-REQUEST` for the moved head so A's PM dispatches its own reviewer on it. That reviewer is reviewing A's own PR: GitHub refuses an `APPROVE` or `REQUEST_CHANGES` review from the account that opened a PR (422), so `meld review` posts A's verdict as a `COMMENT` review whose first line names it as a machine-readable `meld-verdict:` marker, and A's `meld/review/<group>` status on the new head is the record the quorum reads (section 8, review approve). The marker is why A's own request-changes still counts as a real verdict: `assemble` reads it back as a `CHANGES_REQUESTED` review flagged `as_author`, so it adds to the ping-pong cap in step 5 (plan-5 decision 5). `meld review` is idempotent through its own verdict file, not through GitHub state: the review id and the pushed sha are written into the file the moment each lands, so a retry after a later failure skips what already happened, while a second verdict on the same head from another worker (the `security` review after the `reviewer`) is a new file and posts its own review. A push-fix verdict with no commits in the worktree (or a reaped worktree) is a no-action outcome like a missing verdict: the PM is told to re-dispatch. Quality rules in the reviewer prompt: correctness, security, performance, visual design and accessibility (for anything a user sees), tests, then repository conventions, in that order; no style-only change requests; verify claims in the PR body by running them.
4. `meld merge` is legal when approvals on the current head come from at least `min(review.quorum, N-1)` distinct groups that did not author the head (human approvals count; the author group counts through its `success` status on the current head, since GitHub's own-PR rule keeps its approval out of the review list — with two groups this is what lets a push-fixed PR land without a human), required checks are green, no `CHALLENGE` is open, and the head committer is known. Since plan 7 it also reads the diff: a PR that changes a file outside its issue's declared `## Scope`, or deletes a file that issue does not list under `## May delete`, is refused naming the offending files (section 6; both checks come after the quorum and the checks, and a memory PR — which closes no issue — is exempt), so a worker that wandered outside its task is stopped by Python rather than only by a reviewer's attention. Whichever PM sees it first merges, squash, PR title as subject and the PR body — already closer-neutralised by `collect` apart from the framework's own `Closes #N` line — as the squash commit's message, so a worker's own commit messages can never be folded into the default branch (plan-5 decision 3); the head sha goes with it as a guard, so a merge attempted after the head moved is refused (409) instead of landing the wrong commit; a 405 means another PM merged first or the PR is no longer mergeable, and a PR the board already shows as merged is a no-op success rather than a refusal. A 405 whose fresh `mergeable_state` is `dirty` — the branch conflicts with the default branch — is handled by `meld merge` itself (plan 40, section 17's row): it is a request for changes nobody posted.
5. Once `review.pingpong_cap` request-changes reviews have accumulated on one PR, the issue moves to `blocked` and orchestrators must post a resolution. The cap counts `CHANGES_REQUESTED` reviews on the PR — from any reviewer, on any head, including the author group's own marked `COMMENT` review (step 3) — not rounds, so two groups each requesting changes on one head spend two of the three. One reviewer's repeated request-changes on one head count once (the count is over distinct reviewer-and-head pairs), so a duplicated or re-posted verdict cannot spend the cap, and a dismissed review does not count; a verdict on a head GitHub no longer knows (its `commit_id` nulled) keys on its timestamp instead, so old rounds on vanished heads still count once each.

With two groups the effective quorum is one non-author approval, which is ordinary cross-review. With three or more, it is two, and the first two responders count so extra groups add speed, not rounds.

## 14. Human participation and hallucination protection

### Plan gate

`meld setup <owner/name> --goal "..."` creates the milestone and the coordination issue (section 20). Orchestrators plan in `planning`: decompose, reconcile via the agreement protocol, and post `[joint] PLAN plan-<milestone>` with the decomposition written as one line per item — `- id: <slug> | title: <text> | worker: <type> | model: <id> | effort: <level> | size: <S|M|L>`, followed by indented `  - <acceptance criterion>` lines (plan 56: an optional ` | after: <id>, <id>` names the items this one waits for; `plan issues` writes it into the issue body as `plan-after:`, and `claim` and `dispatch` are refused while any named item's issue is still open, with the reason `waits for #N to close first`; `meld status` carries the open ones as `waits_for` and the card says so). `meld plan issues plan-<milestone>` parses that text into one `meld:planned` issue per item (a malformed line is reported and skipped, never guessed; `--dry-run` reports what it would create without creating it) and the same text is written into the milestone description. The human reviews in GitHub and runs `meld plan approve`, which adds `meld:plan-approved` and flips every `meld:planned` issue to `ready`, or posts `[human] AMEND` with notes. Mid-milestone additions are proposed and agreed the same way as `plan-add-<n>`, closed with `[joint] PLAN-ADD`, turned into issues by `meld plan issues plan-add-<n>`, and become `ready` only once the human runs `meld plan ack plan-add-<n>` (idempotent: acking twice still posts the `ACK` comment once). Both halves refuse on a `[joint]` comment that is not *verified* (section 7) — written by anyone but the proposer's own bot, or written before the round actually closed.

### Humans as participants

A listed human is a third party in the rules. A human claims an issue with `meld claim`, which labels it `meld:claimed-by:human` (one label for every human; no group may dispatch a human-claimed issue); assigning oneself on GitHub holds nothing: meld never reads assignees as a claim (the off-protocol sweep in section 17 still reports assignment events by strangers). A human PR on a `meld/` branch is reviewed by every group, since none authored it. A human approval counts toward the quorum. Human-only powers: `APPROVE` the plan, `ACK` plan additions, `release --force`, `HALT` and `RESUME`, `REVERT #<pr>` (makes a revert PR the top priority), `PROVIDED` and `RESOLVED` for needs-human items, and the CODEOWNERS approval on worker-type PRs.

### Chat

`meld inbox` (non-interactive) and `meld chat` (a REPL, also scriptable one line at a time via `--once TEXT`) open on the same inbox: open `NEEDS-HUMAN` issues (skipping ones already answered by `PROVIDED`/`RESOLVED`), `BUDGET` comments, `[joint] ... DISAGREE` items still awaiting a `DIRECTIVE`/`AMEND`/`APPROVE`, `PLAN-ADD` rounds still awaiting `ACK`, and open `ASK`s (each flagged answered or not). In `chat`, plain text posts `[human] ASK ask-<n>` (the next unused `ask-` number on the board); slash commands post the human verbs directly — `/halt`, `/resume`, `/directive TEXT`, `/provided`/`/resolved`/`/revert REF [TEXT]` (any ref the grammar accepts — `#13`, `budget-1`, `dir-2`; plan 14, before which only `#N` was taken), `/challenge ACTION REF TEXT`, `/ack REF`, `/approve` — `/inbox` re-prints the inbox, `/recent [N]` prints the newest N coordination comments (default 10) through the same renderer as `meld thread [--last N]`, the one paginated reader of the thread for a person or a restarted role (plan 14), and `/wait` blocks until the board changes and prints the new coordination comments: by default only `[joint]` and `[human]` ones plus `NEEDS-HUMAN`/`BUDGET`/`DRIFT`/`PROTOCOL-VIOLATION`, every comment with `--verbose`. A malformed slash command (a missing ref, an unknown action) is recorded as an error and answered inline; it does not end the session. `DIRECTIVE` requires `ACK` from every group rather than agreed wording, and orchestrators treat it as overriding their plan.

### Needs-human

When a retry depends on a person (credential, external account, product decision, budget, permission), the requesting orchestrator labels the issue `meld:needs-human` and posts `NEEDS-HUMAN #<issue>` with a structured body: what is needed, why the agent cannot do it, what happens once provided. `claim` and `dispatch` are illegal on that issue until a listed human posts `PROVIDED` or `RESOLVED` after the request; once such an answer exists — newer by comment id than the newest `NEEDS-HUMAN #<issue>`, and there must be one (`Board.needs_human_answered`, the same condition that unlocks a held issue in section 8) — any PM's `meld tick` swaps `meld:needs-human` back to `meld:in-progress` (or `meld:ready` for an unclaimed issue) and posts nothing, because the human's own `PROVIDED`/`RESOLVED` is already the record; it is idempotent across PMs, since the next one finds no label to remove, and the resumed issues are held back from that same tick's Slack nudge, which would otherwise be computed from the board as it stood before the swap. So nobody edits labels by hand (plan 7 — until then the label had to be removed manually). The ask is the stamp, so a label with nothing behind it stays locked until someone posts one: a PM, an orchestrator, or a human (`[human] NEEDS-HUMAN #<issue>`, which is also how a person re-gates an issue they have already answered). **An ask the agents answered among themselves is theirs to withdraw** (plan 52): the group that posted a `NEEDS-HUMAN` may post `RESOLVED <ref>` on it, which closes the ask the way a person's answer does (`Board.answers`, read by `needs_human_answered`, `open_ask` and the page's inbox alike); `rules.withdraw_rule` refuses a group's `RESOLVED` on anything else, and a person's own `NEEDS-HUMAN` is cleared only by a person, whatever a bot asked or withdrew after it. On the first real run the codex PM asked the owner to restore a browser service, codex's own orchestrator restored it two minutes later, and the ask sat on the owner's page until they typed an answer. **A lease that lapsed before the human answered is suspended, not expired.** A build that stops on a needs-human posts no lease closer, so the holder still carries the `until` its dead worker was given; once the issue resumes to `in_progress` a foreign PM's `tick` would read that as an expiry and strip the claim of a group that was only ever waiting for a person. `tick` therefore skips a lease whose issue has a listed human's `PROVIDED`/`RESOLVED` created after the lease's `until` — the worker is known to have stopped, and the holder's next `meld dispatch` posts a fresh `LEASE` that then governs. No `RESUMED` note (that verb is the liveness notice for a restarted orchestrator or PM). The cost: a holder that never re-dispatches keeps the claim until a human runs `meld release`. Surfaced in `meld status` (top-level `needs_human`), the PM `STATUS` comment, and the `meld inbox`/`meld chat` inbox. With `[notify] slack_dm_webhook_env` set, every PM's `meld tick` posts one Slack message naming all currently-due needs-human issues (plan-4's header decision 9 said one message per issue; what shipped, and what this describes, is one message listing every due issue) and repeats an issue only after `notify.repeat_after_minutes`. The throttle is shared, and GitHub holds it (plan-5 decision 9): a party that nudges adds the `meld:nudged` label to the issue, and `notifier.last_nudge` reads the newest `labeled meld:nudged` event by a *configured bot or listed human* from that issue's own event history — so it is one nudge per window however many PMs (or listed humans running `meld notify`) are watching. Humans count because a human's own `meld notify` sends and labels under their login; the consequence, accepted deliberately, is that a listed human who adds the label by hand snoozes that item for exactly one window. A `labeled` event from any other login (a passing collaborator, another tool's bot) is not a nudge. GitHub offers no compare-and-swap on a label, so parties are staggered `NUDGE_STAGGER_MINUTES = 1` apart by their alphabetical position among the configured groups (a caller with no group takes offset 0) and only one is normally due for a given item in a given round-trip. An issue that still carries `meld:nudged` but is no longer `needs_human` has the label removed on any non-dry-run call, webhook configured or not, so the marker stays truthful even in a deployment that never sends anything. Nothing here may raise out of `tick`: a failed Slack post (an `OSError`, an `http.client` exception, a bad value), a failed label add or removal, and a failed read of an issue's events all come back as `notify_errors` — and a failed events read leaves that item simply not due on this call rather than guessed at, while a send that did go out counts as notified even when the label fails to attach (the cost is at most one extra nudge later). `meld notify --dry-run` computes what is due and prints the message without sending, labelling, or clearing anything; a missing or unset webhook is reported as `skipped`, not an error, and a failed post is retried on the next `tick` rather than marked sent. Two residuals are recorded in section 21 rather than fixed: an item that clears and returns inside the repeat window is not nudged again immediately, because GitHub's `labeled` event outlives the label itself; and a duplicate is still possible when one party's label event takes longer than the stagger to become visible. Secrets never travel through GitHub: `PROVIDED` names where the value was placed (an env var or 1Password item) and the runner injects it. A just-resumed issue keeps its `meld:nudged` marker for one more tick (the clearing loop reads the pre-resume board); the next tick clears it.

### Hallucination protection

No group grades its own claims; a claim without evidence is not a fact.

- **Evidence.** `verified-by:` is mandatory on `PLAN`, `DECISION`, `ANSWER`, `EVIDENCE`, and worker finish comments. Prompts forbid asserting test results without pasted output.
- **Challenge.** An orchestrator or a human opens one with `meld challenge open <ref> -m "..."` (a comment, plan item, issue, or PR) against a claim that is not its own party's; PMs may not act on challenges at all, and a bare number is read as `#<n>`. The target gains `meld:challenged`; `dispatch` and `merge` are blocked on it. `meld challenge evidence <ref> -m "..."` (with a `verified-by:` line) is the challenged party's orchestrator's to post, or a human's; `meld challenge retract <ref>` may come from the challenger (withdrawing the doubt) or the challenged party's orchestrator (conceding the claim). `meld challenge uphold <ref>` or `dismiss <ref>` is decided by an orchestrator of a group that is neither challenger nor challenged — with two groups, the human. Each of these five verbs applies or clears `meld:challenged` as `meld challenge` posts it (the label moves first, so a failed post leaves a clean retry rather than a stuck label); `meld post` refuses all of them.
- **Independent audit.** Every merged PR except a memory PR (whose content was verified against the board when it was reviewed, section 15, and which has no worker output to audit) is audited by a group that did not author it — within the milestone that closed its issue: a PR whose `Closes` issue is not in the active milestone was audited on that milestone's coordination thread, which the board does not read, so `rules.outside_milestone` keeps it out of `audit.pending` and refuses `audit` on it (plan 24). `meld status`'s `audit` block tells each group which merged PRs it owes (`audit.pending`) and whether the batch is due (`audit.due`, once `[audit] batch_merges` pending audits accumulate, the oldest has waited `batch_hours`, or the milestone is complete — every non-coordination issue closed, reported as `milestone_complete`, since no later and bigger batch can arrive to fold this one into, plan-5 decision 8 — or a pending PR, or the issue it closed, is under an open `CHALLENGE`, reported as `audit.challenged`: an audit a challenge asks for is due at once, plan 16); the PM then dispatches one `auditor` run at a time, checked out at the merge commit rather than the (possibly deleted) head branch. `meld audit` posts `AUDIT #<pr> PASS|FAIL` on the coordination issue with the auditor's findings; a `FAIL` makes `meld reopen <issue>` legal for that group, returning the issue to `ready` with the findings quoted.
- **Drift check.** On every restart, each orchestrator compares the board to the approved plan and the decision log and posts `DRIFT` when scope, approach, or assumptions moved without a `DECISION`.
- **Human overrides.** `HALT`, `RESUME`, `REVERT`, and `CHALLENGE` are all available to the human from `meld chat`.

## 15. Shared memory

Canonical memory is versioned files in the product repo.

- `.meld/decisions/NNNN-<slug>.md`: one per agreed `DECISION`, numbered from one past the highest sequence already present under `.meld/decisions/` on origin's default branch: date, agreeing groups, a link to the *verified* `[joint] DECISION` comment (`grammar.verified_joint`, never an earlier hand-written one), and the agreed text verbatim under `## Decision`; a round that ended `DISAGREE` is refused. `meld decide <ref>` renders it and opens a memory PR on branch `meld/memory-<slug>`, committed and pushed with the calling group's bot identity (forcing `commit.gpgsign=false` for that one commit, so a machine-wide `commit.gpgsign=true` can never hang it); the PR body carries a `meld-memory: decision <ref> <sha256-of-the-file>` marker.
- `.meld/memory/lessons.md`: appended by `meld remember <ref> -m "..."` when a blocked, challenged, or reverted issue or PR resolves — free-form text (what went wrong, what fixed it, what to check next time), dated and attributed to the calling group — through the same memory-PR machinery on its own `meld/memory-lesson-<n>-<timestamp>` branch; the marker is `meld-memory: lesson <ref> <sha256-of-the-appended-entry>` (one regex, `board.MEMORY_MARKER_RE`, which `memory.py` imports rather than redeclaring). Any line of the lesson's own text that starts with `#` is escaped as `\#` first (`memory.escape_headings`), so the rendered `## <date>` heading is always the entry boundary the verifier and the recall splitter find, and a lesson that quotes a Markdown heading can still verify (plan-5 decision 13).
- **Supersession, never edits** (plan 7). A wrong or stale note is not edited or deleted. `meld decide <ref> --supersedes NNNN-<slug>.md` records the new decision with a `- Supersedes: NNNN-<slug>.md` header line and appends one `\n---\nStatus: superseded by MMMM-<slug>.md on <date>\n` trailer to the old file (`memory.superseded_trailer`), so the memory PR changes exactly two files and both land in one commit by the bot; the PR body gains a `supersedes:` line. `decide` refuses a `--supersedes` that is not a bare `.md` filename actually present under `.meld/decisions/` on the default branch (`<name> is not a decision file on <branch>`) or one that already carries a trailer (`<name> is already superseded by <file> on <date>`), so a chain records one step at a time. `meld review` re-verifies the pair rather than trusting it: both paths flat under `.meld/decisions/` (a nested old path is refused), the new file byte-identical to `meld decide`'s rendering of the verified `[joint] DECISION` *including* its `- Supersedes:` line, the old file byte-identical to the default branch's content plus exactly that one trailer naming the new file and its date, the two naming each other, and no second supersession of a file already superseded. **Both markers are read structurally, never by a loose match anywhere in the file**, because the agreed text under `## Decision` is the groups' own prose and may contain any line at all. The `- Supersedes:` link is read from the header region only — everything above the `## Decision` heading, which is where `render_decision` puts it (`review._decision_header`) — so an agreed decision whose prose carries a `- Supersedes: …` bullet is not re-rendered with a header line it does not have and refused "byte for byte", which would have made it permanently unrecordable, `decide` having already opened its PR. The status marker is the whole of `memory.superseded_trailer` anchored at end of file (`brief.STATUS_RE`; trailing whitespace only may follow it, because `gitops.git` strips the output of the `git show` that reads a decision at `origin/<default>`), so a decision that quotes a status line in its prose is not superseded at birth — dropped from every brief and refused as a `--supersedes` target. `meld remember <ref> -m ... --supersedes "<heading>"` names the older lesson's `## <date> — <ref> (<group>)` heading on the new entry's first body line — lessons stay append-only, so only a later entry can retire an earlier one, and an earlier entry can never retire a later one. Only the flag may write that line: `memory.escape_supersedes` prefixes any `Supersedes:` line in the lesson's own text with a backslash exactly as `escape_headings` does for `#` (comparing the stripped line, so an indented one cannot slip through), because otherwise a worker could make another group's lesson vanish from every brief by typing one line. `meld recall` reports each decision and lesson hit's `status` (`active` or `superseded`) and `superseded_by` (a coordination-issue hit carries neither, so consumers read them with `.get`); briefs quote only active memory — `brief.decision_titles` skips a superseded file under `## Decisions in force` and `recall_snippets` skips superseded hits under `## Relevant memory`, while the superseded file itself stays in the repo to be read. Every note already carries its date and source; the prompts add the discipline: memory primes hypotheses, it does not prove current state — read the file, grep the symbol, run the command before acting on it.
- **CI requirement.** Branch protection requires the product's CI check, so that check must report on every PR including docs-only ones; `meld setup` does not make any check required itself (`protect_branch` asks only for one approving review), so that is the human's own call — and `ci_paths_warnings` is the warning that comes with it: it names any workflow whose `on: pull_request` `paths` allow-list never mentions `.meld` (or `**`), or whose `paths-ignore` deny-list does, since such a workflow never runs on a memory PR and would leave decision and lesson PRs unmergeable once its checks were required. A `push`-only filter is ignored, because it does not gate PR runs.
- **Auto-approval path, and no worker.** `meld dispatch --kind review` refuses on a memory PR ("run `meld review N` directly"); `meld review N` itself fetches the changed file at the PR's head and decides: a **decision** PR must change exactly one file under `.meld/decisions/`, at a path that does not already exist on the default branch (a decision file is written once and afterwards only ever gains a supersession trailer, so a PR rendering decision B at decision A's path — content that would otherwise verify perfectly — is refused rather than allowed to destroy A), whose content hash matches the marker *and* which is byte-identical to `meld decide`'s own rendering of the verified `[joint] DECISION <ref>` — the agreement's text and agreeing groups, the verified joint comment's URL as `- Source:`, and the file's own `- Date:` line, which must be a `YYYY-MM-DD` date and is the one value taken from the file itself — so no preamble or note can ride into the repo (and from there into every brief's `## Relevant memory`); a round that ended `DISAGREE` is refused. A **lesson** PR must change only `.meld/memory/lessons.md`, whose head must equal the default branch's copy (or `# Lessons\n` when there is none) plus exactly the one `## `-delimited entry that hashes to the marker — append-only by verification, so a lesson PR can neither rewrite or drop an earlier lesson nor add a second entry under one marker (a PR whose base has moved since needs a rebase) — and whose `ref` is on the board, no longer `blocked`/`needs_human`, and not challenged — a lesson has no agreement round to check against, so it is verified against the board's own state instead (plan-4 decision 1). A `lessons.md` past GitHub's 1 MB contents limit is still readable: `github.get_contents` falls back to the blob endpoint when the contents API answers `encoding: "none"`, and raises rather than letting an unreadable blob pass as an empty file (plan-5 decision 12). Either way `meld review` posts `APPROVE` or `REQUEST_CHANGES` plus the same `meld/review/<group>` commit status an ordinary review uses, so a memory PR still needs the normal quorum — it just never waits on a dispatched reviewer or a human. A cached `APPROVE` is trusted only while the PR's head hasn't moved since; every other case (no cache, a cached `REQUEST_CHANGES`, or a moved head) re-verifies from scratch, so a corrected file is reflected on the next call and a second `meld review N` never posts a duplicate review of an unchanged verdict.
- `meld recall <query>` searches `.meld/decisions/`, `.meld/memory/lessons.md`, and (via the GitHub issue search API, `search/issues`, scoped to the repo and the `meld:coordination` label) past `meld:coordination` issues in the repo, ranked by term hits, returning matches with links. Orchestrators run it at launch and before planning or proposing a decision that might already exist. `meld dispatch` renders up to three locally-matching snippets (decisions and lessons only, not the coordination search) into every worker brief under `## Relevant memory`, matched against the issue's or PR's own title and body. Both halves now read the same state: `decide`/`remember`'s "already recorded" check, `meld recall`'s own local search, and `meld dispatch`'s brief rendering (`dispatch._recall_for_brief`) each fetch `origin` and read `origin/<default branch>`, so a brief no longer lags behind whatever the checkout happens to hold. A fetch that fails — offline, no reachable `origin` — falls back to the working copy instead of failing the call, and says so: `meld recall` appends a `note` entry, and `meld dispatch` returns a `recall_note`. When reading a ref, a file under those directories that is not valid UTF-8 there is skipped rather than raising, so one mis-encoded file cannot hide its well-formed neighbours.
- Workers report which installed skills they used: a worker's `.meld-result.json` may carry `skills_used` (a list of names, silently truncated to 30 entries of 100 characters each rather than failing an otherwise-good result over telemetry), and `meld collect` appends a `skills used: ...` line to the finish comment whenever the list is non-empty.
- The coordination issue is per milestone; cross-milestone continuity comes only from these files.

## 16. Adapters (N groups)

An adapter implements: `launch(spec: LaunchSpec) -> subprocess.Popen`, `installed_skills() -> list[WorkerType]`, `project_skills_dir() -> str | None` (where this CLI looks for a *project's* skills, relative to the worktree — `.claude/skills`, `.agents/skills` and `.gemini/skills` today; `None` for a CLI with no such directory -- Grok Build and Antigravity -- which then gets no materialised copies, section 10), `command_timeout_ceiling_seconds() -> int`, `supports_effort() -> bool`, `version_argv() -> list[str]` (the argv `meld doctor`'s `cli:<group>` check runs to prove the binary is there and answers), and `help_argv() -> list[str]` with `required_flags() -> tuple[str, ...]` (the command whose `--help` lists the flags `launch` passes, and those flags; doctor's `cli-flags:<group>` check names any the installed CLI no longer lists, so a renamed flag fails doctor instead of every launch). An adapter also implements `parse_events(line: str, now: str) -> list[Event]`: the adapter is already the only layer that knows how a CLI is *launched*, and it is now also the only layer that knows how that CLI *talks* (section 22). `LaunchSpec` carries `role`, `model`, `effort`, `cwd`, `prompt`, `log_path`, `timeout_seconds`, `env`, and `max_turns`; model validity and tiers live in `models.toml`, not in the adapter. Claude and Codex ship in v1. Adding a system is one adapter module, one `models.toml` section, one bot account, and one `[groups.<name>]` block. Nothing in `rules.py`, `grammar.py`, or the prompts refers to a specific CLI.

The Claude adapter runs `claude -p <prompt> --model <model> --output-format stream-json --verbose --permission-mode bypassPermissions --strict-mcp-config --mcp-config '{"mcpServers": {}}' --settings '{"disableAllHooks": true, "autoMemoryEnabled": false, "env": {...}}' --setting-sources user,project --max-turns <n>`. The `env` map in `--settings` sets every scrubbed credential name (`GH_TOKEN`, `GITHUB_TOKEN`, the enterprise variants, `MELD_PUSH_TOKEN`) to the empty string for every launch; for a worker it also blanks `MELD_GROUP` and `MELD_ROLE`, and for an orchestrator or PM it PINS them to the values `runners.role_env` set. `--settings` is merged last, so a `settings.json` `env` block loaded through `--setting-sources` can neither hand a worker a token or a party identity that `worker_env` just removed nor re-point a credentialed role session at another group (section 18). (Blanking the identity for every launch, as the first live run did, turned every `meld` call an orchestrator or PM made into a `[human]` one.) Its environment sets `CLAUDE_CODE_EFFORT_LEVEL` to the effort, disables auto-memory and nonessential traffic, and drops the `CLAUDECODE`/`CLAUDE_CODE_ENTRYPOINT` variables a worker would otherwise inherit from meld's own process. `user` was added to `--setting-sources` in plan 3 so a worker can actually load skills installed under `~/.claude/skills` and plugin caches (section 10 already counted them into the roster); hooks stay disabled and the MCP config stays empty, so the change only reaches the user's own `settings.json` permissions and environment, which `--permission-mode bypassPermissions` already makes moot.

The Codex adapter runs `codex exec -m <model> -c 'model_reasoning_effort="<effort>"' -s <sandbox> -C <cwd> --json -o <cwd>/.meld-last-message.txt --ignore-user-config --ephemeral <prompt>`, where the sandbox is `danger-full-access` for an orchestrator or PM (they run `meld`, GitHub, and git) and `workspace-write` with `-c sandbox_workspace_write.network_access=true` for a worker (and for any role the adapter does not know); `exec` never prompts, so it takes no approval flag (the `-a never` of plans 2–7 was removed from `codex exec` upstream and made the first live run crash-loop). The environment is passed through unchanged; the rest is unchanged from plan 2, since `codex exec --help` scopes `--ignore-user-config` to `config.toml` and does not mention skills, so it was never blocking one. Codex has no equivalent way to load a skill at run time from meld's own launch, though. Plan 5 closed the gap as far as it can be closed from outside the CLI: `project_skills_dir()` is `.agents/skills`, so a product's skills are copied there inside the worktree before launch (section 10), its `installed_skills()` scan still feeds the roster and the brief, and the worker contract tells a worker to invoke a skill by name where its tooling loads skills and otherwise to open and follow the `SKILL.md` at the path the brief prints. Both adapters run in the worktree with stdin closed and stdout and stderr appended to the log file, no interactive approval prompts.

## 17. Error handling and budgets

| Failure | Detected by | Response |
|---|---|---|
| Worker exits without result | PM via run record | `blocked`, log tail posted **rendered through `transcript.py`** (section 22: a raw tail of a streamed log is JSONL, and a raw tail of the pre-plan-8 Claude log was one unreadable line), orchestrator re-tags and re-dispatches or splits |
| Worker exceeds deadline | `meld tick` | SIGTERM then SIGKILL; `collect` marks a build issue `blocked` with the log tail, or records the timeout and log tail in the verdict file for review/audit runs |
| Review ping-pong cap | rules | `blocked`; orchestrators must post a resolution |
| Review verdict on a moved head | `meld review` | marked stale; re-dispatch |
| Illegal verb | rules | Refused; `PROTOCOL-VIOLATION` posted |
| A second `NEEDS-HUMAN` on a ref whose newest ask no listed human has answered | `rules.ask_rule`, from `Board.open_ask` | Refused for a group or PM naming the standing ask's comment id and party (plan 41): one open ask per ref, `9` and `#9` the same ref, and a human's own never refused (that is how a person re-gates an issue). The scratch product's three parties posted nine asks on one PR while the first stood, each a new card for the owner. The refusal is quiet (plan 63): no `PROTOCOL-VIOLATION` is posted for it, because on the maze run that post woke the other group, whose `PING` woke the asker, every few minutes for an hour while a person held the answer; and the violation throttle in `actions._already_said` treats `4` and `#4` as one target |
| CI red | author group's `meld tick` via `pulls[].checks` | Comments once naming the PR (the durable evidence), then moves the linked issue back to `in_progress` — once per head; the next build run on the issue is the fix. `merge` stays refused until checks are actually green regardless |
| A listed human pushes to a PR branch | author group's `meld tick` via `pulls[].head_committer` | Posts `REVIEW-REQUEST` naming the head once, then moves the linked issue from `in_progress` to `in_review` — once per head (plan 13); an issue with a live build run is left to that run's `collect`, and a bot's head is `collect`'s or `review`'s business. The next `dispatch` on a reused worktree fast-forwards it to the pushed head, so a retry builds on the person's work rather than over it |
| PR conflicts with the default branch (GitHub 405, `mergeable_state` dirty) | `meld merge` | Handled like CI red (plan 40): a comment on the linked issue naming the PR and head, the issue moves from `in_review` back to `in_progress` (once: a second PM reaching the same 405 finds it already in progress and posts nothing), and the reply says `conflict` and `next`. The next `dispatch` on the issue reuses the branch and the brief names the conflicting files; the PR moves back to review when the merge commit pushes. A memory PR has no issue and no worker: it is closed with a comment, and `meld remember`/`meld decide` rewrites it from the current default branch. Before this, the scratch product's two PMs retried the 405 for hours and posted `NEEDS-HUMAN` nine times |
| Orchestrator or PM dies | runner | Restart, rebuild from `meld status`, post `RESUMED` |
| Orchestrator or PM ends its turn cleanly | runner | Relaunch **as the same session continued** when the CLI can (plan 55: Codex's `exec resume <thread>` and Claude Code's `--resume <session>`, the id read from the transcript's own first event; the prompt is then the launch block alone, fifty tokens instead of ten thousand, and a role's Codex session is kept on disk rather than `--ephemeral` so it can be resumed; a crash or a recycle starts afresh, and after `runners.MAX_RESUMES` continued launches so does the next one, to bound the context), and no sooner than `polling.wait_timeout_seconds` after the launch (plan 39): a single-turn CLI such as `codex exec` ends its session every time the role stops talking, and a role that waited 45 seconds and exited was costing a full prompt every couple of minutes (649 launches overnight on the scratch product). The board cannot move faster than one wait would have blocked for, so the pause loses nothing; a clean exit after a full wait relaunches at once as before. `meld wait` holds the other end: a role's `--timeout` below `cli.ROLE_WAIT_FLOOR_SECONDS` (120, or the configured wait timeout if that is smaller) is raised to it and the reply says so (`timeout_clamped`); a human's and a `--timeout 0` one-shot read are left alone. The role's launch count is on its run record (`launch_no`) and on the overview's role node, so the next loop of this kind is visible |
| The model is at capacity (busy, not out of quota: Codex's "Selected model is at capacity. Please try a different model.", Anthropic's 529 `overloaded_error`) | each adapter (`adapters.base.is_capacity`, the `capacity` event) | **A pause and the same call again, never a failure and never a freeze** (plan 50). A role that died of it is relaunched after `runners.CAPACITY_PAUSE_SECONDS` with the reason `capacity` and its restart count untouched (no doubling backoff); the page's role node says `after capacity`. A worker that died of it before writing its result is collected as outcome `capacity`: the issue stays `in_progress`, nothing is re-tagged, the rubric does not count it, and `dispatch` is legal again with the same tags once `rules.CAPACITY_RETRY_SECONDS` have passed since collect (the refusal names the instant). The first real run's codex worker on #3 died of it, meld called that a failed attempt, the rubric then demanded a re-tag, and the retry's real failure left the issue blocked |
| Role hits a usage or rate limit | runner, from the role's own transcript (`usage_limit`, section 22) | **Freeze that role, do not relaunch it.** Post `LIMITED` once per freeze carrying the reset instant; wait until it passes, or re-probe every `runners.limit_retry_minutes` when the CLI named no time. A named instant is believed up to an eight-day cap (`runners.MAX_FREEZE_MINUTES`; plan 38 raised it from six hours after a week-long Antigravity quota was re-probed 48 times, each probe an over-limit email to the owner) — it is parsed out of the CLI's own prose (ISO instants, clock times, "in 2 hours", "in 7 days", and compact "in 166h54m43s"), so one stray timestamp would otherwise strand a role for months. A limit that named no time is re-probed after `runners.limit_retry_minutes`, and that interval doubles each time a re-probe runs straight into the limit again (`runners.next_retry_minutes`, from the previous freeze's record at `limit-last.json`), up to a day. A notice that could not be posted is retried on the `limit_retry_minutes` cadence, not on every poll. The freeze is persisted, so a supervisor restart honours it; the file is `$MELD_HOME/state/<group>/<role>/limit.json`; deleting it *and restarting the supervisor* forces a re-probe, while deleting it under a running supervisor only re-derives the same limit from the role's transcript and freezes again. Treating a limit as a crash is what made the first live run relaunch a dead role for 45 minutes with nothing on the board to say why |
| Supervisor cannot launch a role (no disk, no binary, no permission) | runner | Back off on the same exponential schedule as a crash and keep the other role alive; in supervisor mode this never propagates out of `meld run`. One `except OSError` around the whole per-role step is the boundary, so the same holds for every filesystem or `gh` failure inside the freeze path — writing or clearing `limit.json`, reading the prompt files a launch assembles, or the `gh` process that posts `LIMITED` (a missing binary is a `FileNotFoundError`) — each of which costs that role a cycle rather than the supervisor. `meld run --once`, a one-shot diagnostic mode whose contract is launch/wait/return, instead reports a launch failure as a clean error and exits 1. An `OSError` opening the log file used to kill the whole supervisor, which is how both groups died mid-milestone on 2026-09-12 when the disk filled |
| The same refusal re-derived on a later launch | `actions.refuse` against the board | Refuse locally and **skip the comment** when the newest `PROTOCOL-VIOLATION` from this party for this target already names the same verb and rule — the whole posted body is compared, because a rule text alone does not identify a refusal (`COLLECT` and `REAP` both refuse with "worker is still running"). GitHub's own record is the throttle, as it is for `meld:nudged` (section 14); one live run published 109 of these, most of them identical |
| Other group silent past `silence_grace_minutes` | orchestrator | `PING`, then continue `SOLO` with a note |
| GitHub rate limit | `meld wait` | Backoff, no action |
| Off-protocol GitHub change (label or assignee changed on a milestone issue by an actor that is neither a configured bot nor a listed human) | `meld tick`'s `off_protocol_sweep`, reading each open issue's own `issue_events` against a persisted per-issue cursor (not a `meld status` snapshot diff) | `PROTOCOL-VIOLATION` naming the actor and the change, posted once per event by the alphabetically first configured group's PM; no automatic revert |

Budgets are per milestone in worker runs by model tier plus a wall-clock cap. `claim` refuses when the issue's model tier is exhausted for the caller; the orchestrator re-tags to a cheaper tier or posts `BUDGET`. Spend to date appears in `meld status` and the PM `STATUS` comment.

## 18. Security

- Bot tokens are fine-grained PATs scoped to the product repo with **Contents**, **Issues**, **Pull requests**, and **Commit statuses** set to read and write — `meld review` publishes every verdict as a `meld/review/<group>` status, and without the last permission the review posts and the status is recorded as `status_error` — injected from 1Password via `op run` into the orchestrator and PM processes only. Workers receive no token.
- Only configured bots and allow-listed humans can speak in the grammar. All other comments are ignored.
- `meld setup` refuses public repos without `--allow-public` and prints the injection risk when overridden.
- Secrets never appear in issues, PRs, briefs, or `.meld/` files. `PROVIDED` comments name a location, not a value.
- A role's own git authenticates as its group (plan 43): `runners.role_env` clears the machine's credential helpers and sets one that runs `meld token`, which prints the calling group's current credential bare (an App group's installation token is re-minted as it expires, so a session that lives for hours is never stale; a human has no group token and is refused; a worker is refused like every verb). So an orchestrator's `git fetch` in the clone works on a private repository, where the scratch product's roles got "repository not found" from every git call they made; the prompt tells it to fast-forward the clone before planning a milestone.
- Workers inherit no credentials. Their environment is scrubbed of `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, every `MELD_TOKEN_*`, and the party variables; `GH_CONFIG_DIR` points at an empty per-run directory, so `gh` has no login; git's credential helpers are reset (`credential.helper=` through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`) and `GIT_TERMINAL_PROMPT=0`, so a push or fetch that needs credentials fails instead of borrowing the human's keychain. `meld` itself refuses to run with `MELD_WORKER=1` set. The Claude adapter additionally blanks every scrubbed variable name through the `env` map of its `--settings` JSON, so a user or project `settings.json` loaded via `--setting-sources user,project` cannot re-inject one; `MELD_TOKEN_*` names are per group and unknown to the adapter, so `meld doctor`'s `settings-env` check warns when the user's `~/.claude/settings.json`, or the product's `.claude/settings.json` or `.claude/settings.local.json`, has an `env` block naming a scrubbed variable or any `MELD_TOKEN_*`. Not blocked: SSH keys or an agent on the host, so the product clone's `origin` should be an HTTPS URL — `meld doctor`'s `origin-https` check warns when it is not.
- Filesystem isolation is only what each adapter provides. The Claude adapter runs `--permission-mode bypassPermissions` (no sandbox: a worker can write wherever the user can) and relies on the environment scrubbing above; the Codex adapter runs `-s workspace-write` (network on) for a worker and `-s danger-full-access` for the orchestrator and PM, whose job is to reach GitHub and git as their group. The Gemini adapter (plan 25) runs `--approval-mode yolo` with no sandbox, the Grok Build adapter `--always-approve` with none passed, and the Antigravity adapter (`agy`, plan 28) `--dangerously-skip-permissions`, so all three are the Claude case: the scrubbed environment is the whole of their isolation. Grok and Antigravity were verified against the installed CLIs on 2026-10-26 (grok 1.0.70, agy 1.4.7): Grok's `streaming-messages-json` is Claude Code's stream-json format, which the Grok adapter parses with the Claude parser; Antigravity's `stream-json` is its own (`init`, `step_update`, `result`), with an agent's text arriving as deltas the adapter joins per step. Both probe login through `<cli> models`. The Gemini adapter was built from its published reference only (the `gemini` binary is not installed here) and has no login probe; `meld doctor`'s `cli-flags` check against the installed `--help` is what proves any adapter's flags before a run.
- `.meld/STANDARDS.md`, the product's own quality bar, is rendered into the `## Product standards` section of every worker brief and both role prompts; the framework's own default, used when the file is absent or empty, lives in `brief.DEFAULT_STANDARDS`.
- `.meld/CONTEXT.md` (plan 35), what the AIs should know before they plan or build -- existing documentation, partial work and where it stands, constraints, files to read first -- is rendered whole into both role prompts (`## Product context`) and capped at `brief.MAX_CONTEXT_CHARS` into every worker brief with a pointer to the file, and its text is a `## Context` section under the goal on the coordination issue when `setup` creates it. The wizard asks for it; an existing file is the product's and is never overwritten. The orchestrator prompt reads the context and the files it names before proposing a plan: partial work is where the plan starts, not something to redo.
- Everything under `$MELD_HOME` is disposable state. The directory is per product (plan 42): `MELD_HOME` set wins whatever the product; otherwise `~/.meld/products/<owner>/<name>` once the configuration names the repository (`state.meld_home(env, repo)`; every command passes the configured repo, `load_context` for the roles, a detached supervisor is handed its home explicitly), and bare `~/.meld` only before a repository exists -- the wizard's viewer token lives there, and the wizard moves to the product's home the moment the person names the repository (`SetupSession.home_for`), so its keys, logs and runs land where every later command looks. Before this a second product on one machine silently shared `~/.meld` with the first: run records keyed by issue number, supervisor pids, worktrees.
- **GitHub App auth** (plan 6a, alternative to a PAT bot per `[groups.<g>].auth = "app"`; the cached installation token carries the App and installation it was minted for and is ignored for any other, plan 46, after a re-created App left the roles posting under the old one for an hour): a short-lived RS256 JWT is signed by the `openssl` CLI (the App's private key reaches it through a 0600 temp file, never argv), exchanged for an installation access token minted over HTTPS; the token is cached 0600 under `$MELD_HOME/cache/<group>/app-token.json` and re-minted with 5 minutes to spare, plus once more on a 401. Installation tokens are **scoped to the product repository** — the mint names it in the request body, so the token carries no authority over anything else the App is installed on, and the response's own repository list is what proves coverage (a 422 is GitHub saying the installation does not include the repo). `MELD_APP_KEY_*` is scrubbed from workers alongside `MELD_TOKEN_*`. `meld doctor` verifies an App group from the minted token's own `permissions` (Contents, Issues, Pull requests, Commit statuses: read & write) rather than a probe call.
- **What the guardrails are not.** A worker runs on the host as the user, inside a worktree, with the user's own permissions: it can read any file that account can read and run any command it can run. The scrubbed environment, the scope and deletion checks, and the claim lock keep autonomous work on task; they are not a containment boundary. Meld belongs on a machine, or under an account, whose contents the user would hand to the model (plan 11, section 21 item 16).

## 19. Testing

**The dress rehearsal (plan 48).** The whole of meld end to end on one machine, in the suite, with no network and no money: `tests/test_rehearsal.py` runs the real wizard (`cli.setup_viewer`) against a stand-in GitHub served over loopback (`rehearsal.github.FakeGitHub`: one repository, backed by a bare git repository so pull requests, files, commits and squash merges are real; labels, milestones, issues, comments, events, reviews, statuses, check runs, Apps, installations and tokens in memory, identity by token), with a `gh` on PATH that talks to it (`rehearsal.ghshim`) and stand-in `claude` and `codex` binaries on PATH that the real adapters launch (`rehearsal.cli`); the stand-ins answer the doctor's probes and play orchestrator, PM and worker by policy from `meld status` alone (`rehearsal.actor`), writing transcripts in the real CLIs' formats. The run creates the repository, pushes the folder, sets up the board, creates and installs both Apps through the wizard's own flow (the manifest the page posts becomes the code GitHub would redirect with), starts the real detached supervisors, proposes, agrees and posts the joint plan, has the person approve it, claims, tags, builds (the first worker launch dies of "model at capacity" and is retried with the same tags), collects, opens the pull request, reviews it from the other group, merges it and closes the issue. A `PROTOCOL-VIOLATION` or a `NEEDS-HUMAN` on the way fails the test: a stand-in that does only what `legal` lists must never be refused and never need a person, which is the property the first real run's codex orchestrator found missing (plan 47). `MELD_REHEARSAL_GITHUB` is the one seam in product code: `appauth.api_base()` sends the App calls there. The rehearsal costs about forty seconds of the suite.

- **Rules** (`test_rules_issues.py`, `test_rules_prs.py`, `test_rules_challenges.py`): every state, verb, party, and N in {2, 3}, from recorded board fixtures. This is the highest-coverage module.
- **Grammar** (`test_grammar.py`): every header verb, required fields, round counters, amend cap, majority and tie handling, malformed and unauthorized comments.
- **Review and merge** (`test_review.py`, `test_merge.py`): submitting a collected verdict as a GitHub review and a `meld/review/<group>` status, idempotent retries, stale-head detection, push-fix, the ping-pong cap; `merge`'s quorum math including human approvals and the head-sha guard.
- **Audit, challenge, and results** (`test_audit.py`, `test_challenge.py`, `test_results.py`): posting `AUDIT` and reopening a failed issue; opening, answering, and closing a challenge under the closer rules; verdict-file storage, superseding, and submission.
- **Dispatch** (`test_dispatch.py`): a fake adapter binary records arguments and writes fake results; tests worktree creation, brief rendering, timeout kill, post-run PR opening, reap.
- **Memory** (`test_memory.py`): decision rendering, hash match for auto-approval, recall ranking.
- **Run reliability** (`test_runners.py`, `test_actions.py`, `test_doctor.py`): a role whose transcript ends in `usage_limit` freezes instead of relaunching and posts `LIMITED` once; a persisted freeze survives a supervisor restart; a launch that raises `OSError` backs off and leaves the other role running instead of ending `meld run`; an identical refusal re-derived on a later launch refuses without a second comment; doctor warns below `logs.warn_free_mb` of free space. The supervisor's clock and its launcher are both injected, so no test sleeps for a freeze or fills a disk.
- **Transcripts and the viewer** (`test_transcript.py`, `test_viewer.py`, `test_viewer_streams.py`, `test_state.py`, `test_config_write.py`): the event vocabulary and tail reader over recorded JSONL fixtures for both CLIs; the viewer's token, `Host`, and routing checks, driven in-process against the same board fixtures the rules tests use, with a `Request` in and a `Response` out and no socket; stream discovery, SSE replay from a `seq`, trim recovery and terminal synthesis over `tmp_path` logs with injected `now`, `sleep` and writer liveness; the liveness tri-state over injected `alive` and `start_of` probes; the config writer's round trip (plan 8d); each adapter's parse over every event type that CLI emits. Two tests bind an OS-assigned loopback port: one proves the wiring from bytes on a connection to `Viewer.handle` and back, the other that a `Content-Length` over the cap is refused before any body is read; no test launches a CLI, and none depends on wall-clock time — `now` is injected everywhere. One test does sleep: the `O_APPEND` case polls a real child process's log until it has written, against a bounded deadline, because the thing under test is that a live writer survives a truncation.
- **Smoke** (`tests/smoke/`, opt-in): one tiny real task per adapter against a scratch repo.

No test claims to measure decision quality. That is done by watching the first milestones and converting each bad decision into a prompt edit or a new invariant.

**The short way (plan 32).** In a clone of the product repository, run `meld` (bare `meld` is `meld start`). ## 21. Future work (explicitly out of v1)

### Borrowed from prior art (approved 2026-09-03)

A survey of existing multi-agent coding systems (Symphony and its forks, Gas Town/Beads, Code Conductor, claude-code-review-council, ai-pair, Claude Code Review) found no project combining Meld's mechanisms, but five of their ideas are adopted for the later plans:

1. **Lease-plus-heartbeat claims** (from Beads). A claim carries a TTL that the PM's loop renews while the worker runs; an expired claim auto-reverts the issue to `ready` and posts a note. Replaces bare first-label-wins as the crash-recovery path. Landed in plan 2 with dispatch and collect, with a TTL variation: the lease is fixed at dispatch to the worker's deadline plus `lease.grace_minutes` rather than renewed on a heartbeat while the worker runs (section 11); `tick` still fills in a lease that's missing and still releases one that has expired.
2. **Citation verification before a finding is shown** (from claude-code-review-council). The reviewer worker's contract requires every cited file and line to be opened and checked against the checkout before it appears in the review; uncheckable citations are dropped and noted. Landed in plan 2's reviewer prompt.
3. **Role-matched review** (from ai-pair). When more than one group reviews a PR, the review request assigns each a different primary concern (correctness and security, tests and conventions, architecture) so reviewers surface distinct issues. Landed in plan 3: `review_concern` assigns one once there are three or more groups (with two, there is exactly one reviewer, so nothing to rotate).
4. **Neutral check runs** (from Claude Code Review). Cross-group review results are published as a GitHub check run with a neutral conclusion, visible but never blocking on its own; merge remains gated by the quorum rule in `rules.py` and the human. Landed in plan 3 with `review` and `merge`, with one variation: a personal token cannot create a check run, so each group's review is published as a **commit status** instead (`meld/review/<group>`, `success`/`failure`/`pending`) — visible on the PR and never blocking unless a human adds it to the repository's required checks, which keeps the same intent. The originally-intended check run landed for App groups in plan 6a: an installation token can create one, so an App group's review publishes a neutral `meld/review/<group>` check run alongside its commit status (section 13 step 3). PAT groups are unchanged, and the quorum still reads only the status.
5. **Repo-local verification bar** (from Claude Code Review's `REVIEW.md`). A product may add `.meld/REVIEW.md` stating what counts as evidence for that repo; it is rendered into every worker's brief, not just reviewer and auditor. Landed in plan 2 with brief rendering.

24. **No CLI form clears a `## Scope` or `## May delete` section.** An omitted repeatable option means "not given", so `meld tag` can replace a declaration but never remove one (plan-7 decision 12); `board.replace_section` itself removes a section given an empty list, so the seam is a clearing form on the CLI — `--scope ''` was rejected because a blank path is exactly what the same call has to refuse. Until then, a scope is removed by editing the issue body, which is where it lives anyway.
25. **`"meld:needs-human"` is spelled out in four modules.** `board.STATUS_LABELS` and `setup.LABELS` both carry the literal, as they do for every status label (an `assert` ties the two dicts together), but `dispatch.py` and `tagging.py` then declare their own `NEEDS_HUMAN = "meld:needs-human"` module constants rather than importing one — unlike `CHALLENGED_LABEL`, `NUDGED_LABEL`, and `PLAN_APPROVED_LABEL`, which live in `board.py` and are imported from there. Exporting one constant the same way is a tidy-up, not a behaviour change.
26. **A `meld recall` coordination hit carries no `status`/`superseded_by`.** Only decision and lesson hits do; a coordination-issue hit is a GitHub search result with no memory file behind it to mark. Consumers read both keys with `.get`, so nothing breaks — but a caller reading `hit["status"]` on the wrong kind of hit would.
27. **`tests/test_memory.py` borrows `_contents` and `memory_pr_on_board` from `tests/test_review.py`** through imports inside the test bodies (a pre-existing pattern, extended by plan 7's supersession tests). A `conftest.py` home for both helpers would make the dependency one-directional.
28. **A decision supersession is authorized by the flag, not by the agreed text** (HANDOFF decision 14). `meld decide <ref> --supersedes NNNN-<slug>.md` needs one verified `[joint] DECISION` on `<ref>` and nothing else, so any group holding one may retire *any* decision file — including one it did not write and that nobody agreed to retire. The other PMs auto-approve from provenance plus hash, and the record is the PR body's `supersedes:` line, the file's `- Supersedes:` header, and git history. Requiring the agreed text itself to name the file it supersedes would close it, and that is a grammar change. The blast radius is bounded by everything else the verifier pins (flat paths, the old file byte-identical to origin plus exactly one trailer naming the new file and its date, no second supersession, and — since the plan-7 fix wave — no write to a decision path that already exists), and by reversibility: a wrong supersession is visible after merge and undone by a counter-supersession, memory being superseded rather than edited.
29. **An unlisted operator's `meld tag --held` stamps nothing.** `rules._tag` accepts any human `gh` login, but the ask such a human posts parses with `ok=False` (not a listed human), so the hold stays locked until a listed party posts `NEEDS-HUMAN #N`; it fails closed and `flag_ignored_comments` surfaces the comment. Checking `cfg.is_human` in `_tag` would refuse it up front.
30. **A decision whose agreed prose ends with a `---` line followed by a `Status: superseded by …` line as the file's last line reads as superseded at birth.** Any end-anchored trailer marker keeps this residual; only a verified `[joint] DECISION` becomes a decision file, so a worker cannot reach it.
31. **One review run per group per head.** In the first live run (2026-09-11, `smidley/meld-playground`) codex's PM reviewed one unchanged head of PR #40 four times in 47 minutes — every dispatch was legal because `rules._review` checked only the run slot — spending four large-tier runs and tripping the ping-pong cap on one substantive verdict, which a human then had to reconcile by dismissing the duplicates. **Landed as a live-run hotfix** (Meld PR #18): `rules._review` refuses a head the group's bot has already reviewed (two slots when the PR touches `review.security_paths`; a `DISMISSED` review frees the slot), and `PullRequest.changes_requested_total` counts distinct (reviewer, head) pairs. Residuals: the security slot is a count, not a worker type, so a PM that dispatches a second `reviewer` instead of `--worker security` on a security-path PR is stopped only by the prompt; and the slot is spent by the *posted* verdict, so between `meld collect` (verdict stored) and `meld review` (verdict posted) a second run of the same head is still legal — closing that window needs a `submitted` flag on `RunRecord` (the store's `mark_submitted` surfaced on the board), which is plan-8 work.

## 22. Observability: transcripts and the local viewer

A run that cannot be watched can only be reconstructed afterwards from what it happened to post. The first live run made the cost concrete: two groups published 530 coordination comments in ten hours, 109 of them the same refusal retried, and the only way to see why was to read a log after the process that wrote it had died. This section makes a run watchable while it runs, and gives the human one surface for the three things they actually do: watch, answer, and configure.

### Normalized transcripts

Both adapters already append a run's output to `$MELD_HOME/logs/<group>/<role>-<stamp>.log`. Two changes make that file readable as it grows.

First, the Claude adapter launches with `--output-format stream-json --verbose` rather than `--output-format json` (section 16). `--verbose` is not optional: `claude -p` refuses `stream-json` without it. The log becomes JSONL, one event per line, and the closing `{"type": "result"}` event carries the fields the single blob carried before. Nothing loses data, because nothing read that blob: a worker's outcome is the `.meld-result.json` it writes in its worktree (section 11), Codex's final message is `.meld-last-message.txt`, and the log was never the source of truth for correctness. What the change fixes is section 17's failure tail. Under `--output-format json` a Claude run's entire log is one line, so the "last `worker.log_tail_lines` lines" a PM posts when a worker dies without a result was one unreadable 5 KB JSON object.

Second, each adapter gains `parse_events(line: str, now: str) -> list[Event]`. It returns a list because one line is not one event: a Claude `assistant` line carries a content array, and a single line routinely holds a sentence and the tool call that follows it. Sequencing is not the adapter's business either -- it returns events with `seq` unset and `Tail` stamps the monotonic number -- so an adapter has exactly one job, which is translation. `transcript.py` owns the types and everything above them, and no module outside `adapters/` learns either CLI's vocabulary.

```
Event(seq: int, at: str, kind: str, text: str, tool: str | None, ok: bool | None, meta: dict)
kind in {run_started, message, thinking, tool_call, tool_result, usage, run_finished, usage_limit, log_truncated, cli_error, raw}
```

| Event | Claude (`stream-json`) | Codex (`--json`) |
|---|---|---|
| `run_started` | `type: system`, `subtype: init` | `type: thread.started` |
| `message` | `type: assistant`, text block | `item.completed`, `item_type: agent_message` |
| `thinking` | `type: assistant`, thinking block | `item.completed`, `item_type: reasoning` |
| `tool_call` | `type: assistant`, `tool_use` block | `item.started`, `item_type: command_execution` |
| `tool_result` | `type: user`, `tool_result` block | `item.completed`, `item_type: command_execution` (`exit_code`) |
| `usage` | `type: result` (its `usage` block) | `turn.completed` |
| `run_finished` | `type: result` | not emitted: a Codex transcript ends at `usage`. Synthesizing a terminal event from process exit is a reader's job, not an adapter's, and is left to plan 8b |
| `cli_error` | not emitted | `turn.failed` (its `error.message`, `ok=False`) |
| `usage_limit` | a `result` marked `is_error` whose text is a limit, or a raw stderr line that is one | `turn.failed` whose `error.message` is a limit, or a raw stderr line that is one |
| `raw` | any non-JSON line, any unknown `type`, and a known line whose every content block was unknown | any non-JSON line (the CLI's own startup errors on stderr) and any unknown `item_type` |
| (dropped) | `stream_event` | `turn.started` |

Three rules keep this honest. A line an adapter does not recognize becomes `raw`, and one it recognizes as carrying nothing (Codex's `turn.started`, a Claude `stream_event`) becomes no event at all; `parse_events` never raises, so a CLI that adds an event type degrades the view instead of breaking the failure tail. `Tail` tracks a byte offset and yields only complete lines, so a half-written JSONL line is never parsed. And `at` comes from the CLI's own timestamp when it has one, else from an injected clock, so no test depends on wall time.

**`usage_limit` is the one kind a supervisor acts on.** A role that exhausts its subscription's quota does not crash in any way an exit code distinguishes from a clean finish, so the runner cannot tell the difference without reading what the role said. Each adapter recognises its own CLI's limit answer and emits `usage_limit`, with `meta["resets_at"]` set to an ISO instant when the CLI named one and absent when it did not. Recognition is the adapter's business for the same reason event translation is: the prose belongs to the CLI, and a rule about it outside `adapters/` would be a rule about a particular CLI in the wrong layer. What the adapters share is the recognition itself — `is_limit`, `reset_at` and `limit_event` in `adapters/base.py` — so both agree on what counts as a limit and on how a reset instant is read, while each keeps its own rule for which of its own lines to hand them (the table's `usage_limit` row). The runner reads the exited role's own transcript tail through `Tail`, and one `usage_limit` event turns a relaunch into a freeze (section 17).

`meld tail <group>/<role>` and `meld tail --run <issue>` render a live transcript to the terminal, with no server and no page. That is the surface for a headless box, the thing the tests drive, and the fallback whenever the viewer is not running.

**Log volume is a first-order constraint, not a detail.** A streamed log is one to two orders of magnitude larger than a result blob: the first live run's Codex orchestrator wrote 1.8 MB in a single launch, and an exhausted disk is what killed both supervisors that night, mid-milestone, with no signal on the board. Capping it takes care, because the child process holds the log's file descriptor: `popen_detached` hands the open file to the CLI as its stdout and the run outlives the `meld` process that started it (section 11), so nothing meld-side can rename the file out from under the writer. What works instead is truncation in place. `open_log` opens with `O_APPEND`, so every write recomputes the offset from the file's end; `transcript.trim_log`, called from `meld tick` and from the viewer's own poll, reads the file's tail into memory, truncates the original to zero, and only then writes that tail to `<name>.1`, replacing any previous `.1` — in that order, because on the exhausted disk this exists for the sidecar write is the operation that fails, and it transiently adds up to a keep-window before it does. A `.1` that could not be written is reported as a trim anyway: the freed space is the incident, the tail only the post-mortem. The writer's next line lands at the new end with no fd invalidated and no process restarted. `Tail` closes the loop from the reading side: a file shorter than the offset it holds means the log was trimmed, so it emits `log_truncated` and resumes from zero, which is also how it survives a truncation nothing in meld performed. `meld doctor` reports total bytes under `logs/` and warns past `[logs] warn_total_mb`, and separately warns when free space on the volume `$MELD_HOME` sits on falls below `[logs] warn_free_mb` — the cap bounds one run's log, not the total across launches, so the volume is the thing that actually runs out.

### The viewer

`meld watch` serves one page and prints its URL. It is a tool a person runs, not a service the framework depends on: no role may start it, nothing reads from it, and every verb it offers also exists on the CLI. Section 2's "polling only" non-goal rules out webhooks and anything reachable from off the machine; a loopback page that a human starts and closes is neither.

| Route | Method | Purpose |
|---|---|---|
| `/` | GET | the page, the only HTML served |
| `/api/state` | GET | `status.render_status`, plus supervisor liveness, each role's standing freeze (`limit.json`, section 17), budget spend, free disk, and log bytes |
| `/api/streams` | GET | the live runs: group, role, issue, pid, started, log path |
| `/api/events` | GET | `text/event-stream` for one run or for every run at once, resumable from a cursor |
| `/api/action` | POST | one human verb, as the `human` party |
| `/api/config` | GET, PUT | the parsed `.meld.toml`, and a validated write |

**Streams.** `/api/streams` lists one transcript per configured role — its recorded current launch's log, else the newest log on disk for that role, marked `unknown` because a log with no record of its writer is exactly "could not confirm" — plus every worker run still on record; and it is the viewer's turn of the log cap: `sweep_logs` runs on every call, the same call `meld tick` makes. A stream is named by its path under `logs/`, `<group>/<file>.log` and nothing else, so a request cannot reach outside that directory. `/api/events` replays from the `seq` the client last saw (`Last-Event-ID`, which the browser sends on its own reconnects, else `after=`); a client that has seen more events than the file now holds was reading a log that has since been trimmed, and is told so with one `log_truncated` frame before the file is replayed from the start. The same renumbering happens when a trim lands under an open connection: the stream says so and restarts its count at the file's first event, so a later reconnect's count means the same thing. When the writer is confirmed dead and the transcript, after its last unterminated line is flushed, does not end in `run_finished`, `usage_limit` or `cli_error` — a Codex run ends at `usage` — the stream synthesizes one `run_finished` marked `synthesized` and closes with an `end` frame. While the writer is alive or unknown the stream stays open on a comment heartbeat. One connection carries every transcript. A browser allows about six connections to an origin, so a page that opened one per transcript starved its own polls; `/api/events` with no `stream` names every transcript `/api/streams` would list, refreshed as the connection runs so a role that relaunched into a new log joins it, and each frame names the stream it belongs to. Each stream keeps its own idle count, so one talkative transcript never delays another's end. The `id:` line therefore carries the whole cursor — `<stream>=<count>` for every stream the connection has sent, joined by `|` — so the browser's own reconnect resumes all of them at once and the client still holds no resume logic. `event: end` names one stream and does not end the connection: a role relaunches into a new log and the next refresh picks it up. A reader whose stream is no longer listed and has already ended is dropped, which bounds both the reader set and the cursor over a long session.

**Authentication and binding.** The server binds `127.0.0.1` on an OS-assigned port unless `[viewer] port` says otherwise. A 32-byte URL-safe token is minted per launch, printed in the URL, and required on every request including the page load; a request without it gets 403 and an empty body. The `Host` header must name a loopback host and the served port, which is what stops a page in the user's browser from reaching the API by rebinding DNS to 127.0.0.1. No CORS header is ever sent. The token lives in the process and in the URL the human pasted, never on disk. The token *is* the human, so one that leaked could already post every verb `/api/action` offers for as long as the viewer runs; what `/api/config` adds is persistence -- a login written into `[humans].accounts`, or a group's `token_env` pointed at some other variable that the next `meld` process would send to GitHub as a bearer, outlives the viewer that wrote it. The trust boundary does not move, but it is worth saying out loud.

**What the page may do.** Reading is unrestricted within `$MELD_HOME` and the configured repo: transcripts, board, status, config — and, since plan 17, the coordination thread itself: `/api/state` carries the newest `THREAD_LAST` parsed, authorized comments as data (`chat.thread_entries`, the same thread `meld thread` prints, each flagged `housekeeping` or `agreement` by the grammar so the page keeps no verb lists), and the page shows them as turns by their parties, colour-coded, appended by comment id and never rebuilt, with housekeeping hidden by default. Since plan 18 `/api/state` also carries `decisions` (`chat.decisions`): everything waiting on the human — the plan awaiting approval, each needs-human ask, budget alert, disagreement, plan addition, and challenge the human may settle — as one item with a title, a short summary and its choices, each choice the exact `/api/action` body it runs plus whether it needs a message; a choice is listed only when `rules.py` would allow it, and the page renders each item as a card with buttons. The page decides nothing: the choice bodies are composed server-side from the same rules, and a refusal still comes back verbatim. `/api/state` also carries `headline` (`chat.headline`, plan 19): one plain sentence from the status JSON and the decisions — the phase, the issue counts by status, workers running, open PRs and how many are ready to merge, and whether anything waits on the person — shown first under the page's header and printed first by `meld chat`. Each decision carries the `comment_id` it came from, so a card's title scrolls the conversation to that turn (widening the filter if it is hidden); and a transcript column shows `message` events by default, with `tool_call`, `tool_result` and `thinking` behind a "show tool calls" checkbox (plan 20). Plan 21 laid the page out as a hierarchy: the header (repo, milestone, phase, the headline sentence, the groups as chips), the decisions, then the conversation beside the work as four lanes (to do, in progress, in review, done — an issue is a card with its holder in that group's colour and its verb buttons), and a tab row whose drawer holds the transcripts, the pull requests, the agreements, the action bar and the configuration form; prose is proportional, transcripts and inputs monospace. A verb button anywhere fills the bar and opens its tab. Plan 22 made the bar a list of intents in plain words (`INTENTS` in the page's script: ask, directive, halt, resume, provided, resolved, revert, approve or amend a proposal, the five challenge actions, claim, release, merge, approve the plan, acknowledge an addition, and an advanced "post a header verb"), each naming its inputs and explaining what will happen before Run; `posting.post` numbers an `ASK` or `DIRECTIVE` given no ref (`next_ref`, the numbering `meld chat` always used), so the page never asks a person to invent one. The conversation follows the newest turn unless the reader scrolled up (a "newest" button resumes), its filter is worded for a person ("the conversation" hides the PMs' status reports and bookkeeping), and the work lanes show activity from `status.runs` (which now carries each run's `worker`): a card with a live build run pulses and names whose worker is building it, a card in review names its PR and the review's state, a card that changed lane slides in, and a group's chip blinks and says what it is building or reviewing. Plan 23 gave `tag` its form: an intent whose model and effort choices come from the catalogue `/api/config` serves, grouped by CLI (a human tags for whichever group will claim, and `meld tag` validates a human's choice against no group), sending only the fields the person changed; a row's `tag` is a button like the other verbs. Writing is the set of verbs `rules.py` *may* grant the `human` party (section 14): `claim`, `release`, `post`, `tag`, `challenge`, `decide`, `remember`, `plan approve`, `plan ack`, and `merge`. `/api/action` implements all ten, but `decide_rule` and `remember_rule` both open `if actor.party.kind not in ("group", "pm")`, so `decide` and `remember` are refused for a human today — no button for either ever renders, because the page draws its buttons from the `legal` lists `rules.py` computes, never from this set. The two dispatch entries stay regardless: the honest answer to a human's `decide` is `rules.py`'s own refusal, rendered verbatim, and removing them would make the viewer a second authority on what a human may do. The human's overrides are not separate commands. `HALT`, `RESUME`, `REVERT`, `DIRECTIVE`, `RESOLVED`, `PROVIDED`, `ACK`, and `APPROVE` are header verbs that `post` carries (section 7), so the page offers them as the grammar already defines them and `grammar.py` validates the header exactly as it does for a comment typed at the CLI. Worker-authored text is the only thing `neutralise_closers` guards, so nothing the page posts as `human` passes through it. **The viewer holds no legality logic.** `POST /api/action` names a party, a verb, and a ref; `rules.py` decides; a refusal is rendered verbatim, including the rule it names. `meld status` therefore remains able to list every legal verb, and a button the page offers for a verb rules refuses is a rendering bug, never a second authority. **Every reference is a link (plan 26).** The repository, the milestone, each issue and pull request number, each thread comment and each decision card link to the thing itself on GitHub (`ghUrl`: `/milestone/<m>`, `/issues/<n>`, which GitHub forwards to a pull request, `/issues/<coordination>#issuecomment-<id>`), opened in a new tab with no referrer. They are the one place the page points off the machine, and they are navigation a person chooses: nothing is ever fetched from them, the no-external-reference guard still forbids every script, stylesheet, font and fetch that is not the viewer's own, and a page without a repository shows the same references as plain text. **A configured group that is not running says what it needs (plan 27).** `/api/state` re-reads `.meld.toml` whenever its modification time changes, so a group saved through the form or by hand is on the page without a restart (a file that no longer loads leaves the last good configuration in place and is reported as `config_error`), and carries `setup` per group -- its CLI on PATH, its token in the viewer's environment (an App group needs none), whether its supervisor is running -- read from this machine alone, never the network. The header lists each group that is configured but not running with what is missing and the command that starts it, `meld run <group> --detach`, because a saved group starts nothing by itself: the second live run's owner added two groups through the form and saw nothing. **Each issue's journey (plan 29).** `chat.journey` reads `meld status`'s own JSON -- the issue, its build runs, its pull request's approvals, checks and audits, the review and audit runs on it, the quorum -- into seven steps, claimed, built, pull request, reviewed, merged, audited, closed, each done, now or next with a detail, plus one sentence for what is happening ("codex is reviewing PR #55, 12 min in", "PR #55 waits for a review (0 of 2 approvals)", "blocked: the worker could not finish") and one for what follows; `chat.progress_line` says where every open issue stands under the milestone bar (or, past three, how many sit at each step). `/api/state` carries both as `journeys` and `progress`; a card draws the steps as a strip and prints the sentences; the page decides nothing about any of it. The owner's words: the page said two of three issues were done and nothing about how the third was getting there. **Usage and limits (plan 31).** A freeze record carries the provider's own words (`text`, from the last `usage_limit` event) beside `at` and `resets_at`; `runners.freeze_deadline` is the one arithmetic for when a freeze ends (the named instant, capped at six hours, else the retry interval) and `limits.freeze_view` reads it without `_frozen`'s side effects. `limits.usage_totals` sums every transcript under `$MELD_HOME/logs/<group>` through that group's adapter -- tokens in, out and served from cache, dollars where the CLI reports them, runs -- cached by file size and refreshed by the viewer on its own thread every minute, never on the request path. `/api/state` carries both as `limits`; the header shows one line per group and, for a frozen role, what the provider said, when the freeze ends and when the supervisor tries again. The owner watched two groups freeze with nothing on the page saying why or until when.

**What it may not do.** Start or stop a group's supervisor, kill a run, edit a run record, write into a worktree, or post as any party other than `human`. Supervisor liveness is reported and never changed (section 21).

**Actions.** `POST /api/action` takes a JSON object naming the party (`human`, and the server refuses any other), the verb, and that verb's own arguments, and calls the same function the matching `meld` command calls — `claim`, `release`, `post`, `tag`, `challenge`, `decide`, `remember`, `plan-approve`, `plan-ack`, `merge`. An argument the verb cannot use is 400 and never reaches it; so is a call the verb itself calls malformed, raised after it is entered — a verb the party may not post, a framework-only or command verb, a missing ref, a body the grammar rejects (`PostError`, whose own docstring is "a usage error: the call is malformed, not a legal call that the rules refuse"); a `Refused` is 409 carrying the refusal, the verb, the target and the rule, exactly as the CLI prints them; a failure of GitHub, git, the configuration or the filesystem is 502; and anything else at all is 500, because a page someone is pressing buttons on has to answer even when the answer is that something unforeseen broke — an unhandled exception would instead drop the connection and print a traceback in their terminal. A human's refusal posts no `PROTOCOL-VIOLATION`, so nothing a person tries on the page reaches the board unless it was legal. A successful action drops the cached `/api/state`, because the board has just moved. The body is capped at one mebibyte at the transport, before the token and `Host` check.

**Liveness is a tri-state.** `/api/state` reports each supervisor as `alive`, `dead`, or `unknown`, each with the reason that produced it, and pairs every pid with the process start time it was recorded against. A bare boolean is what made the first live run announce a dead audit worker as running: the pid had been reused. "Could not confirm alive" and "confirmed gone" are different facts and the page shows which one it has. The evidence is written by the processes themselves: `meld run` records its own pid and process start time at `$MELD_HOME/state/<group>/supervisor.json` and each role launch's at `state/<group>/<role>/current.json` (with the log it writes, its launch number and reason), and every worker's run record carries `proc_start`. The start time is `ps -o lstart=`'s own string, compared for equality and never parsed — the same for the same process on every call, different for a reused pid. `alive` needs a live pid and a matching start time; a pid that is gone, or a live one whose start time differs, is `dead`; a live pid with no recorded start time to compare against, or one `ps` cannot read, is `unknown`. A record is never deleted — a dead pid in one is the fact "confirmed gone", which is more than "no record" can say — and the next launch overwrites it. A record that cannot be written is swallowed, never raised: observability does not outrank the run it observes.

### The configuration form

`GET /api/config` answers with the configuration canonicalised — every field the schema defines, at its effective value, plus any key `unknown_keys` names carried over from the file verbatim, or the bare raw parse when the file does not parse into a `Config` at all — the path it came from, and the model catalogue `models.toml` holds, so the form offers model and effort choices that cannot be wrong rather than rejecting them afterwards. `PUT /api/config` takes that same object back. One shape in both directions: the page sends what it was given with a few values changed, and a key the schema does not know is refused by name rather than dropped — `Config.from_dict` reads with defaults and ignores what it has never heard of, which is right for a parser reading a newer file and wrong for a form that must not swallow a field a person typed. `GET` also names a version of the file it read -- a digest of its content, so identical content is never a collision and nothing in the payload depends on a clock -- and `PUT` has to give it back. A panel held open while the file changed underneath it is refused with a 409 naming the collision, rather than saving the copy it is still holding and quietly reverting whatever the file gained meanwhile. The page deliberately does not re-read on every panel open: closing and reopening it would then discard a person's in-progress edits, trading a rare loss for a frequent one. And because two states block every save no matter what a person changes -- a key the schema does not define, which the form would otherwise render as an ordinary editable box, and a file too broken to canonicalise, where the form silently shows the raw parse instead -- `GET` names both: `unknown` lists the keys, `error` carries the parser's own complaint, and the page shows them as a refusal on open rather than letting the first Save be where the person finds out the file has to be hand-edited first. Both are diagnosis rather than settings, so `PUT` ignores them as it ignores `path`, `models` and `note`.

`tomllib` reads; the standard library cannot write TOML, so `config.py` gains a canonical serializer for the known schema. That asymmetry is a feature rather than a workaround: a form that can only emit named fields, in a fixed order, under a comment header re-rendered from a template, cannot corrupt a table it does not understand. It writes every field the schema defines, defaults included, because a form that shows a field and then does not write it is lying and because a round trip is only exact if nothing is omitted. The cost is plain and worth saying: the first save turns a hand-written minimal file into the full explicit one, and the comments in it are not preserved.

A write is refused unless the candidate parses into a `Config`, that `Config` renders and parses back into an equal one, and `meld doctor`'s configuration checks pass against it; only then does it replace the file through `atomic.write_atomic`, so a refusal at any step leaves the original untouched. What "parses into a `Config`" means for a number is stricter than `int()`: every numeric setting carries a floor, because a field a person can type a 0 into is a field the parser has to have an opinion about. The rule is whether `0` is a lie. It is refused where it cannot mean what it says, because the code coerces it into something else or acts on it in a way the word does not describe: `review.quorum = 0` is clamped to 1 by `effective_quorum` and always was; `audit.batch_merges = 0` cannot mean a batch of nothing, since `audit.due` already requires a pending merge, so it can only mean 1; `polling.interval_seconds = 0` does not poll quickly but deletes the backoff, because `waiting.py` doubles it from zero forever; `worker.log_tail_lines = 0` posts the whole transcript, because `lines[-0:]` is every line. It is kept where it means something, and there only a negative is refused: no budget of that tier, no grace on a lease, no amendment round, no waiting on age before an audit. That first clause is about lying rather than about harm, deliberately -- silently not doing what a field says is the failure this surface exists to prevent, so an honest `0` survives even when it is drastic, and a dishonest one goes even where, as with the quorum clamp, nothing was misbehaving. A second and narrower clause floors a `0` that is a runaway even where it is honest: a zero poll interval reads as exactly what it does and still never stops, and `notify.repeat_after_minutes = 0` honestly means "repeat every pass" -- but what it repeats is a nudge posted to a Slack workspace the person running meld may not own, so the loop runs away at something outside meld and at other people's attention. The test there is not cost, which would floor half the table; it is the absence of a stopping condition, pointed outward. Three of the floored settings -- `runners.roster_refresh_minutes`, `silence_grace_minutes` and `summary_cadence_minutes` -- are read by no loop at all: they reach the product only as the cadence a role's prompt states it should keep, and a `0` there states a rule that cannot be followed as written. `_at_least` also refuses a float and a bool, so a `2.5` typed into a concurrency comes back named rather than silently becoming 2 -- though a group's inert App settings stay deliberately lenient (`_loose_int`), so the refusal is `_at_least`'s rather than the parser's everywhere. A worker timeout is the same rule in the shape a duration takes -- greater than zero, because a worker launched on `"0m"` is past its deadline the instant it starts, which is `runners.restart_hours = 0` in different clothes. That floor sits at `from_dict`'s own read of `[timeouts]` rather than inside `parse_duration`, whose contract belongs to its other callers: zero is a well-formed duration, and whether it is a usable one is the question this table answers. The configuration checks are the ones that are a function of the configuration and the model catalogue alone — each group's `models:` and `timeout-ceiling:` — and `meld doctor` and this route share one definition of them, because a form that could pass a check the CLI fails would be a second opinion about a settled question. Everything else `meld doctor` does needs the network, a binary, a token, or the machine, and a form must not refuse a budget change because the network is down. A render that cannot reproduce its own input is reported as the serializer bug it is, naming the fields that differ, and writes nothing.

What the form offers is what a running product may change: the budgets, the concurrencies, the models and efforts, the timeouts, the polling and runner intervals, the log caps, the viewer's own port. A group's identity — its `cli`, its bot, its authentication, its token variable, its App and key settings — and `[repo]` and `[humans]` are shown and not editable: changing them mid-milestone orphans a group's claims and its open pull requests, and the remedy is `meld setup`, not a text box on a page. A group's `git_name` and `git_email` are editable wherever the file already carries them, because they are a label on a commit rather than a claim about who anyone is -- but only there: `dumps` omits an absent optional string rather than writing an empty one, so the canonical `GET` has no field to render and adding one for the first time is still a hand edit. Emitting `""` for an absent optional string would round-trip safely and put `git_name = ""` into every file anyone ever saves, which is worse than the gap. The route still accepts the read-only fields, so the round trip is lossless and opening them later needs no new route. A group *added on the page* is the exception that proves the rule (plan 25): "Add a group" takes a name and one of the adapters the server names (`adapters` in the `GET` payload, `adapters.ADAPTER_NAMES`) and builds a `[groups.<name>]` block from that CLI's catalogue defaults -- its first large-tier model at a high effort for both roles, the conventional `meld-<name>-bot` login and `MELD_TOKEN_<NAME>` variable, the default concurrencies -- whose identity stays editable until it is saved, because nothing has claimed anything in its name yet; "Remove" drops a group from the file on Save the same way. Each group card also shows its `env` and `cli_config` tables as a box of `key=value` lines, and "Add a group" takes an optional model server: for a Codex group it writes the `-c` overrides that name a custom provider at that URL, for a Claude group the base URL and placeholder token (plan 28). Both pass the same four gates as every other write. The form itself is sections in plain words -- a heading and a line of why per table, a label per key, one card per AI group -- with the raw table and key on hover, and a table or key the schema gains but the words do not know still renders under its raw name. And a write reconfigures nothing already running: the file is what the next `meld` process reads, while the supervisors and the page itself keep the configuration they started with, which is why `GET` reads the file rather than the configuration this process is holding.

**The overview (plan 24).** The page is a picture before it is a list. The work lanes (plan 49) take the width to the left of the conversation, which (plan 57) is a sticky column on the right with the viewport's height and its own scroll, so the page scrolls the work and the conversation never fights it; the lanes drop to two when the work column is narrower than about 820 px and the pair stacks below 980 px. The milestone bar and the budget bars are rows, never one line, so no browser can lay them over each other. **Signs of life (plan 58):** `/api/state` carries `activity`, what every live role and worker is doing from the newest event in the tail of its transcript (`transcript.last_event`, `chat.activity_words`: waiting for the board to change, checking the board, reading files, editing app.js, thinking, wrote a message) with the log's last-write time, and `pulse`, the newest of them; the map's role and worker nodes say it with an age that counts up on the page, a line under the strip says it ("codex orchestrator is reading a result, just now"), and the strip's silence clause counts a process writing as life. The activity dots are a band on the page above the work, not a drawer tab, and the conversation is hidden until Show conversation in the work's heading asks for it (remembered in the browser; a turn asked for shows it). **The settings pane (plan 59)** is a list of sections on the left (the file's tables in plain words, then one entry per AI group and Add an AI) and one section at a time on the right; each setting is a row with its words, its key in the file under them, and its control; an edited row and its section's entry are marked, and a foot that stays in view carries Save, the count of edits waiting, and the result. Four lanes across most of the page instead of four squeezed into half of it, and each card's journey shows its seven step names under their bars (claimed, built, PR, reviewed, merged, audited, closed) rather than seven unnamed slivers, so how far along an issue is reads at a glance. What appears or goes does so smoothly: a section toggled with `.hidden` fades and slides, the drawer slides by height, the task dialog fades, the configuration details opens by height, and `prefers-reduced-motion` turns all of it off. **Questions for the person are a conversation (plan 51):** `chat.decisions` gives each open question `from` (who asks), `reply` (what a typed reply posts: `RESOLVED` for a needs-human ask, a `DIRECTIVE` for a disagreement or a budget alert, nothing where the answer is a button) and `choices` (quick replies, or the ways to send a typed ruling); the page shows one bubble per question, the newest selected, and one reply box under them, so the person types an answer and sends it instead of choosing between a Provided and a Resolved button, which the owner found confusing. The header draws the agents as an inline SVG map -- a node per group with its liveness, its two roles with theirs, and one node per running worker saying what it is on, wired left to right -- over a milestone progress bar and one budget bar per group and tier, and under them the coordination thread as a timeline: a lane per voice, a dot per post sized and dimmed for housekeeping, ringed for a post that needs attention (`NEEDS-HUMAN`, `BUDGET`, `PROTOCOL-VIOLATION`, `CHALLENGE`, `DRIFT`, `HALT`), a click showing that turn. A running worker carries a ring, and its card a bar, of elapsed over allowed time, measured against the state's own stamp and never the browser's clock. Clicking an issue opens the task view: a graph of the issue, its build runs, its pull requests and the review and audit runs on them, each run node naming its group, worker, model, effort and outcome and opening its transcript; `/api/state` carries each run's `model`, `effort` and `outcome` and the role processes (`processes`, from `runners.processes`) for it. The work lanes show the flow: a card that changed lane travels from where it was to where it is, a dashed line under each lane heading drifts in the direction of work and races for a minute after a card arrives there. Transcript columns are ordered alive, unknown, dead, finished ones hidden unless asked for, each following its newest line until the reader scrolls up. Everything is drawn node by node with `createElementNS`; no markup strings, no library, and the SVG namespace URL is the one external-looking string the page's no-external-reference guard admits. Nothing moves for decoration, and nothing moves under `prefers-reduced-motion`. A `NEEDS-HUMAN` whose ref is not a needs-human issue -- a merged PR, a bare number, no ref at all -- is a decision too (`chat.inbox`), until a person posts on that ref.

**The status strip and the agent rows (plan 54).** The first thing on the page is one line in one colour, `chat.status_strip`, computed beside `headline()` from the same `meld status` JSON plus the viewer's `processes` and `limits`, so the page and `meld chat` cannot disagree about where the run stands. It carries a level (`ok` green, `attention` amber, `bad` red, `quiet` grey), the sentence, an `/api/action` body where the state has one obvious act (approve the plan, resume after a halt) and a `detail`: what the state itself adds (the merged PRs still owed an audit when the milestone is complete) or else the next state down the precedence. The precedence is fixed: halted, then questions for the person (the plan ready for approval, or "2 questions need you — oldest 25 min"), then a role that has stopped or is crash-looping (launched more than five times and dead, or back from a crash or capacity exit: "codex's PM has stopped (restarted 38 times)") or out of quota (one group amber with its reset time, every group red with the next try), then a blocked issue or silence (no post and no run started for longer than `runners.silence_grace_minutes`, which the state carries as `silence_grace_minutes` beside `last_post_at`), then moving ("Building milestone 1 — 2 workers running, 1 of 3 issues done"), then done. Times are 12-hour in the machine's zone; counts are pluralised. Under it, instead of the SVG map, `chat.agent_rows` gives one row per configured group in the plain words of the review (running, stopped, partly running, out of quota until 5:09 pm, restarted 38 times; never awake, dead, frozen or dispatched): the group's state and a summary of its supervisor and two roles, what its workers are doing ("building #3", "reviewing PR #12", "checking PR #12 after merge"), its reset time when frozen, its restarts, its dollars where the CLI reports them (None where it does not, so the page says so once rather than showing a token count that looks like a bill), its tokens in, out and from cache, and its runs against the cap per tier used ("9 of 20 large"). The state carries both as `strip` and `agents`; `headline` stays for `meld chat`.

### Testing

Everything here is testable without a CLI, a port, or a clock. `test_transcript.py` drives the event vocabulary, `Tail`'s partial-line and rotation behaviour, and a golden render from recorded, redacted JSONL captures under `tests/fixtures/transcripts/`; each adapter's `parse_events(line, now) -> list[Event]` is tested over every event type that CLI emits plus an unknown type, an unknown content block or item type inside a known line, and a non-JSON line, all of which must become `raw`. `test_viewer.py` drives the handler in process: a missing token, a wrong token, a rebinding `Host`, SSE resumption from a `seq`, and, for every mutating route, that it refuses exactly what `rules.py` refuses against the same board fixtures the rules suites use, and that an atomic replace leaves the original file intact when validation fails. `test_config_write.py` covers round-trip equality field by field and refusal of an unknown key.

## 23. Glossary

- **Group**: one AI system (CLI + bot account + config) with an orchestrator, PM, and workers.
- **Party**: who is speaking in the grammar: a group, a group's PM, `human`, or `joint`.
- **Quorum**: the number of distinct non-author groups whose approval a PR needs; `min(review.quorum, N-1)`.
- **Board**: the typed snapshot of the milestone's issues, PRs, coordination comments, and run records that `rules.py` evaluates.
- **Brief**: the rendered `.meld-brief.md` a worker reads first.
